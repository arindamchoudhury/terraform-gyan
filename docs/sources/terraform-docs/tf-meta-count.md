# `count` reference

> **Source:** [developer.hashicorp.com/terraform/language/meta-arguments/count](https://developer.hashicorp.com/terraform/language/meta-arguments/count)
> **Added:** 2026-08-01
> **Source updated:** undated language reference; fetched 2026-07-10 against v1.15.x (latest), re-verified byte-identical 2026-08-01
> **Tags:** meta-arguments, count, count.index, instance-addressing, conditional-creation, tuple, action-blocks
> **Type:** documentation

The per-argument reference behind [[tf-meta-arguments]]. Already quoted there for the two corrections it supplies to the index page — the real block list, and the `count`/`for_each` mutual exclusion. Written up in full here because it is the authority for I1 addressing rules, and because it has a defect of its own.

## Usage

Default is one object per `resource` block, per `ephemeral` block, per `module` block, and one invocation per `action` block. `count` takes a whole number and produces that many.

> "Each instance has a distinct infrastructure object associated with it, and each is separately created, updated, or destroyed when the configuration is applied."

```hcl
resource "aws_instance" "server" {
  count = 4 # create four similar EC2 instances

  ami           = "ami-a1b2c3d4"
  instance_type = "t2.micro"

  tags = {
    Name = "Server ${count.index}"
  }
}
```

The page also endorses `count` as a creation switch:

> "You can use the `count` argument as a conditional for creating resources. For example, setting `count = var.creator ? 3 : 0` instructs Terraform to create three instances of the resource when a variable named `creator` is set to true."

!!! note "The conditional-creation pattern is endorsed here, and it is the one Terraform is missing a feature for"
    `count = condition ? 1 : 0` is the only way to make a single resource optional. It works, but it forces the block into indexed addressing forever — `aws_instance.server[0]`, not `aws_instance.server` — and every reference and `moved` block has to carry the index.

    **OpenTofu 1.11 added `enabled`** as a first-class on/off switch precisely to avoid this — an argument inside the `lifecycle` block, not a top-level meta-argument. The address stays unindexed and a disabled resource is `null`. Terraform has no equivalent. Verified on OpenTofu 1.12.4: [[opentofu-enabled-argument]]. See also [[opentofu-feature-history]] and [[tf-meta-arguments]].

## Expressions in `count`

> "The `count` meta-argument accepts numeric expressions, but unlike most arguments, the `count` value must be known **before** Terraform performs any remote resource operations. `count` cannot refer to any resource attributes that are only known after a configuration is applied, such as a unique ID generated by the remote API when an object is created."

This is the concrete form of the "meta-arguments are processed early" rule recorded on [[meta-arguments-lifecycle]] from TID Ch2 §2.7. `depends_on` states the same constraint with the reason: the graph must exist before expressions can be evaluated ([[tf-meta-depends-on]]). `count` states it as a plan-time-known requirement without the reason.

Practical consequence: `count = length(var.subnet_ids)` is fine, `count = length(aws_subnet.this)` is fine, `count = length(data.aws_instances.x.ids)` is fine only if that data source can be read during plan.

## Referring to instances

Setting `count` creates an extra `count` object in the block's scope, with exactly one attribute:

- **`count.index`** — the distinct index number **starting at 0** for this instance.

Terraform distinguishes the *block* from the *instances* it produces:

| Address | Refers to |
|---|---|
| `aws_instance.server` / `module.web` | the block |
| `aws_instance.server[0]`, `aws_instance.server[1]` / `module.web[0]` | individual instances |

> "This is different from resources and modules without `count` or `for_each`, which can be referenced without an index or key."

Child-module resources inherit the prefix: with `count` on the `module` block, plan output shows `module.<NAME>[<KEY>].<resource>`. Without `count`/`for_each` the module index is absent, "as the module's name suffices to reference the module."

One easily-missed sentence: **inside nested `provisioner` or `connection` blocks, `self` refers to the current resource *instance*, not the block as a whole.**

!!! warning "The page never says what type the block reference is — and it is not a list"
    `aws_instance.server` on a `count` block evaluates to a **`tuple`**, not a list. `for_each` yields an **`object`**, not a map. Verified on Terraform **1.15.8**; see [[conditional-branch-evaluation]], which also records that [the docs openly conflate the two](https://developer.hashicorp.com/terraform/language/expressions/types).

    It rarely bites, because a tuple auto-converts to a list wherever one is expected — splats, `length()`, and `list(object(...))` type constraints all work. It bites when a mixed-type conversion is forced, or when you reason about the value's declared type rather than its behavior.

## Choosing between `count` and `for_each`

The page's whole guidance, verbatim in substance:

- **`count`** — "when you want to create nearly identical instances."
- **`for_each`** — "when some instance arguments must have distinct values that can't be directly derived from an integer index."
- **"You cannot use both a `count` and `for_each` argument in the same `resource` or `module` block."**

!!! danger "The real reason to prefer `for_each` is a pitfall this page never mentions"
    Nothing on this page warns that `count` instances are keyed by **position**. Remove the middle element of the list driving `count` and every instance after it shifts down an index, so Terraform plans a destroy-and-recreate for all of them. `for_each` keys by a string, so removing one entry touches one instance.

    That is the single most important thing to know about `count`, and the reference page's only nod to it is the neutral phrase "can't be directly derived from an integer index." TID Ch4 §4.8 is where the pitfall is actually explained ([[04-expressions-iterations]]).

    Rule of thumb: `count` for a fixed pool where identity is genuinely positional, or for the `? 1 : 0` switch. `for_each` for everything keyed by a name.

## Supported constructs

Terraform configuration blocks:

- `data` blocks
- `ephemeral` blocks
- `module` blocks
- `resource` blocks

Query configuration blocks:

- `list` blocks

This list is the authority that corrects [[tf-meta-arguments]], whose index-page table omits `data` from `count` while listing it for `for_each`. The omission is a docs defect, not a real restriction.

!!! warning "This page contradicts itself about `action` blocks"
    The **Supported constructs** list above does **not** include `action`. But the page's own opening paragraph says a `module` block "invokes an action defined in an `action` block once" and that "when `count` appears in an `action` block, Terraform invokes the action the number of specified times." The Example use cases section then has an entry titled **"Invoke an action multiple times."**

    So `action` is supported, and the canonical list on this page is missing it — the same class of defect as the index page's missing `data`, one level down. Captured 2026-08-01 against v1.15.x; both the intro and the use-case section would have to be wrong for the list to be right.

    `action` blocks are not covered anywhere else in these notes yet.

## Example use cases

**`count` on a module block**, with the index selecting from a local list. Note this example also carries a `depends_on`, so it doubles as the module-level `depends_on` case from [[tut-dependencies]]:

```hcl
locals {
  instance_names = ["web", "api", "batch"]
}

module "ec2_instance" {
  source  = "terraform-aws-modules/ec2-instance/aws"
  version = "6.0.2"
  count   = length(local.instance_names)

  name          = local.instance_names[count.index]
  ami           = data.aws_ami.latest_amazon_linux.id
  instance_type = "t2.micro"

  depends_on = [aws_s3_bucket.example]
}
```

**`count` from an input variable's length**, the standard one-per-subnet pattern:

```hcl
variable "subnet_ids" {
  type = list(string)
}

resource "aws_instance" "server" {
  count = length(var.subnet_ids)

  ami           = "ami-a1b2c3d4"
  instance_type = "t2.micro"
  subnet_id     = var.subnet_ids[count.index]

  tags = {
    Name = "Server ${count.index}"
  }
}
```

Both examples are the *positional* case in its purest form — and both are exactly what breaks when an entry is removed from the middle of `instance_names` or `subnet_ids`.

The remaining two use cases defer to other pages: **invoking an action multiple times** (`action` block docs) and **creating multiple query lists** (`list` block docs). Neither is captured here.
