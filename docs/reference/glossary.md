# Glossary

Terms are appended here as book chapters are written.

<!-- term: definition (source chapter) -->

| Term | Definition | Source |
|---|---|---|
| Infrastructure as Code (IaC) | Provisioning and managing infrastructure from declarative, version-controlled configuration files instead of manual steps. | [[terraform-intro]] |
| Provider | A plugin that lets Terraform manage a platform/service through its API; thousands are published on the Terraform Registry. | [[terraform-intro]] |
| Vendor | Informal term for the external system/API a provider wraps (AWS, Cloudflare, Okta). Not a formal Terraform construct — the mapping to providers isn't 1:1 (one vendor → many providers; utility providers wrap no vendor), and provider version ≠ vendor API version. | Book Ch2 / TID Ch1 §1.2.4 |
| Write → Plan → Apply | The core Terraform workflow: define resources, generate an execution plan, then apply approved changes in dependency order. | [[terraform-intro]] |
| State file | Terraform's record of real infrastructure; the source of truth it diffs against configuration to decide changes. | [[terraform-intro]] |
| Resource graph | Dependency graph Terraform builds to create/modify non-dependent resources in parallel. | [[terraform-intro]] |
| Module | Reusable, configurable collection of infrastructure; sourced from the Registry or authored locally. Formally: any set of Terraform configuration files in a single directory. | [[terraform-intro]], [[tut-module]] |
| Root module | The directory you run Terraform commands from. Every configuration has one, so every configuration is already a module. | [[tut-module]] |
| Child module | A module called by another configuration via a `module` block; Terraform loads and processes its files on encountering the block. | [[tut-module]] |
| No-code ready module | A module published to the HCP Terraform registry that teams without Terraform expertise provision through the HCP Terraform UI, within org standards and policies. | [[tut-module]] |
| Immutable infrastructure | Approach of replacing rather than mutating resources, reducing upgrade/modification complexity. | [[terraform-intro]] |
| Sentinel | HashiCorp's policy-as-code framework; enforces compliance/governance policies before Terraform applies changes. Available in Terraform Enterprise and HCP Terraform. | [[terraform-use-cases]] |
| HCP Terraform Operator | Kubernetes Operator that manages cloud and on-prem infrastructure through a Kubernetes CRD plus HCP Terraform. | [[terraform-use-cases]] |
| Consul-Terraform-Sync (NIA) | Network Infrastructure Automation tool; auto-generates Terraform config to reconfigure an SDN when a service registers with Consul. | [[terraform-use-cases]] |
| TACOS | "Terraform Automation and Collaboration Software" — informal industry term for CI/CD platforms purpose-built for running Terraform (HCP Terraform, Terraform Enterprise, Spacelift, Scalr). | TID Ch1 |
| BSL (Business Source License) | The "shared source" license HashiCorp moved Terraform to (from MPL) starting with v1.6; code stays viewable/auditable but usage is restricted, notably against competitive hosted/embedded offerings. | TID Ch1 |
| DAG (directed acyclic graph) | The data structure Terraform builds from resource dependencies to order plan actions; circular dependencies break this model and require manual workaround. | TID Ch1 |
| Workspace (CLI) | One deployment of a Terraform codebase against a specific backend + input variables — like one "installation" of a program; a codebase can have unlimited workspaces sharing a backend. | TID Ch1 |
| Provider `for_each` (OpenTofu) | OpenTofu 1.9 feature: instantiate an aliased provider config multiple times from a map/set (e.g. one per region). Resource `for_each` must be a subset of the provider's. | [[ot-provider-for-each]] |
| Early variable evaluation (OpenTofu) | OpenTofu 1.8 feature: reference `var`/`local` inside `backend`/`provider` blocks, resolved at `tofu init` before state exists. | [[ot-early-eval-backend]] |
| `-exclude` (OpenTofu) | OpenTofu 1.9 CLI flag: inverse of `-target` — plan/apply everything except the given addresses. No Terraform equivalent. | [[ot-exclude-flag]] |
| Dynamic `prevent_destroy` (OpenTofu) | OpenTofu 1.12 feature: bind the `lifecycle.prevent_destroy` flag to a variable/expression; Terraform requires a literal. | [[ot-dynamic-prevent-destroy]] |
| Block | The primary HCL construct ("noun") — a typed, optionally-labeled container of arguments and subblocks. The book lists 12 block types (`terraform`, `provider`, `resource`, `data`, `variable`, `locals`, `module`, `import`, `moved`, `removed`, `check`, `output`); Terraform **1.10 added a 13th, `ephemeral`**. | TID Ch2 |
| Argument vs. subblock | Argument = `name = value`, once per block, exports as an attribute. Subblock = nested block, no `=`, repeatable, *not* exported as an attribute. | TID Ch2 |
| Attribute (computed) | A read-only value a block exposes only after plan/apply reads it back from the provider (e.g. `aws_instance.arn`, `instance_state`); distinct from arguments, which auto-export as attributes. | TID Ch2 |
| Data source | A read-only block that looks up and exposes existing data; same shape as a resource but never creates or modifies. Dynamic-count lookups can return zero results; most single-match lookups error on no match. | TID Ch2 |
| Output value | An `output` block that exposes an attribute from a config for other tools/workflows to consume; printed on every plan/apply, stored in state, read back with `terraform output`. Four uses: child→parent exposure (`module.<child>.<output>`), root CLI display, cross-config read via `terraform_remote_state`, and passing to automation. Supports `sensitive` (redact) and `ephemeral` (omit from state; child modules only). | [[tf-aws-manage]], [[tf-outputs]] |
| Replacement (`-/+`) | A planned action that destroys then recreates a resource because a forced-new attribute changed (e.g. moving an EC2 instance to a new VPC). Distinct from an in-place `~` update. | [[tf-aws-manage]] |
| `terraform destroy` | Destroys *all* resources a workspace manages (equivalent to `apply -destroy`); reverse-dependency order, irreversible, gated by a "there is no undo" confirm. Removing a resource from config + `apply` destroys only that resource. | [[tf-aws-destroy]] |
| Meta argument | An argument built into HCL (not the provider) that changes how *Terraform plans* a block rather than the infrastructure. Six of them: `depends_on`, `count`, `for_each`, `lifecycle`, `provider`, `providers`. Because Terraform core defines them, every resource type supports them regardless of provider; most also work on `module` blocks. Processed early, so mostly requires literal / plan-time-known values. | TID Ch2, [[tf-meta-arguments]] |
| `count` vs `for_each` | Both expand one block into many instances. Use `count` for nearly identical instances (integer index); use `for_each` when instance arguments need distinct values not derivable from an index. **They cannot both appear in the same `resource` or `module` block.** `count` is supported on `data`, `ephemeral`, `module`, `resource`, and (in query configs) `list` blocks. | [[tf-meta-arguments]] |
| Hidden dependency | A real ordering constraint between two objects where the dependent one never reads any attribute of the other, so no edge exists in the DAG. Terraform **cannot infer or warn about it** — `plan` and `validate` both pass. Declared with `depends_on`. Symptom is an apply-time race: passes locally, fails in CI, or fails once and succeeds on rerun. | [[tf-meta-depends-on]], [[dependency-graph]] |
| `depends_on` cost | Not free. The docs call it a **last resort**: it makes plans more conservative, forcing more values to `(known after apply)` and replacing more resources than necessary — "especially likely" for `module` blocks. An expression reference tells Terraform *which value* the dependency derives from; `depends_on` makes the whole upstream object opaque. | [[tf-meta-depends-on]] |
| `terraform graph` | Emits the dependency DAG as Graphviz **DOT**. Default view is `resource`/`data` blocks only; <code>-type=plan&#124;apply&#124;plan-destroy&#124;plan-refresh-only</code> exposes provider and `(expand)` nodes; `-draw-cycles` reddens cycle edges (needs an explicit `-type`); `-plan=tfplan` graphs a saved plan. Implicit and `depends_on` edges render identically. | [[tf-cmd-graph]] |
| `lifecycle` block | Resource subblock (once per resource) controlling management behavior: `create_before_destroy`, `prevent_destroy`, `ignore_changes` (incl. `all`), `replace_triggered_by`. | TID Ch2 |
| `required_providers` vs `provider` block | `required_providers` (inside `terraform`) declares *what to install* + version constraint; the separate `provider` block *configures* it (auth + scoping). Root-module only. | TID Ch2 |
| Provider alias | A named non-default `provider` configuration (`alias = "west"`), letting one program hold multiple connections to a vendor (regions/accounts); blocks select it via the `provider` meta argument, written `<PROVIDER_NAME>.<ALIAS>`. Cannot be combined with the (deprecated) `version` argument in the same block. | TID Ch2, [[tf-provider-block]] |
| Default provider configuration | The `provider` block **without** an `alias`. Resources/data/modules that omit the `provider` meta-argument use it. If no block exists — or if every block is aliased — Terraform invents an **implied empty default configuration**, which errors at apply for any provider that has required arguments. Cannot be suppressed, but it is lazy: the error fires only when something binds to it. | [[tf-provider-block]] |
| `configuration_aliases` | Argument inside a child module's `required_providers` declaring which aliased provider configurations it expects the caller to pass via `providers = { … }`. Without it, referencing `aws.west` in the module is an error. | [[tf-provider-block]] |
| `providers` map | The `module`-block argument that supplies provider configurations to a child. Keys are configuration names used **inside the child**, values are configuration names **in the parent**, both unquoted (`aws` for a default, `aws.usw2` for an alternate). It **remaps** what a name means inside the module rather than adding a provider to it, so one module can be retargeted per caller without editing it. Also valid on Stacks' `component` and `removed` blocks. | [[tf-meta-providers]] |
| Provider config inheritance | A root `provider` block's *configuration* is implicitly passed to child modules; the provider's `source` and `version` requirements are **not** inherited and must be redeclared in each child's `required_providers`. | [[tf-provider-block]] |
| Provider inference | Terraform guessing a missing provider from a resource's name prefix, assuming the `hashicorp` namespace (`aws_instance` → `hashicorp/aws`). Discouraged — declare providers explicitly to pin versions. | TID Ch2 |
| `action_trigger` | A `lifecycle` rule (Terraform 1.14) that invokes provider **actions** on lifecycle events. `events` + `actions` required, `condition` gates the run. Valid events are only `before_create`, `after_create`, `before_update`, `after_update` — **there is no destroy event**, so destroy-time work still needs a destroy-time provisioner. Docs bug: the spec snippet says `conditions`, which Terraform rejects; the argument is `condition`. | [[tf-block-resource]] |
| `removed` block | Config-driven way to take a resource out of state (preferred over `terraform state rm`). **Destroys the real object by default** — `lifecycle { destroy = false }` is the opt-out that merely forgets it. Was forget-only in v1.7, so older material describes the opposite. `destroy = true` is also required for a nested destroy-time provisioner to run. | [[tf-block-removed]] |
| `terraform_remote_state` | Built-in **data source** reading another configuration's **root-level** outputs from its backend (nested-module outputs need an explicit passthrough `output`). Same built-in provider as `terraform_data`; those two are its only members. **Security:** reading outputs requires read access to the *entire* state snapshot, which holds secrets in plaintext — anyone who can fetch the outputs can fetch the whole object directly. Prefer `tfe_outputs` on HCP, or publish shared data to a store with its own ACLs. | [[tf-remote-state-data]] |
| `tfe_outputs` | Data source in the HCP Terraform/Enterprise provider for reading another workspace's outputs. Recommended over `terraform_remote_state` because it "does not require full access to workspace state to fetch outputs." | [[tf-remote-state-data]], [[tf-style-guide]] |
| Built-in provider | `terraform.io/builtin/terraform` — needs no `required_providers` entry or `provider` block. Ships exactly two things: the `terraform_data` resource and the `terraform_remote_state` data source (plus the `provider::terraform::*` functions). | [[tf-remote-state-data]], [[tf-terraform-data]] |
| `terraform_data` | Terraform's built-in "state-only" resource (since 1.4). Implements the standard resource lifecycle but takes no action; served by the built-in provider `terraform.io/builtin/terraform`, so it needs **no provider download**. Arguments: `input` (change → in-place update) and `triggers_replace` (change → replacement). Attributes: `id`, `output`. Two uses: give `replace_triggered_by` a resource address to reference (plain variables and locals are illegal there), and host a `provisioner` that has no logical resource. Supersedes `null_resource` and its `triggers` map. | [[tf-terraform-data]], [[tf-configure-resource]], TID Ch2 |
| `import` / `moved` / `removed` blocks | Refactoring blocks: `import` (v1.5) brings existing infra under management, `moved` (v1.1) re-associates renamed/relocated state, `removed` (v1.7) drops an item from management without destroying it. | TID Ch2 |
| Dependency lock file (`.terraform.lock.hcl`) | File `init` writes recording the exact provider versions + checksums selected; plan/apply use the locked version, not the newest allowed. Commit it for reproducibility across team/CI. Locks **providers only** — module versions are never recorded, so pin modules with an exact constraint. | Book Ch 2, [[tf-dependency-lock]] |
| Trust on first use (lock file) | The lock file's checksum model: verify a provider however you like the first time you add it, after which `init` errors if a package for that same version stops matching a recorded checksum. | [[tf-dependency-lock]] |
| `zh:` vs `h1:` hashes | The two lock-file hashing schemes. `zh:` ("zip hash", legacy) is a SHA256 of the official `.zip` from the registry protocol — useless for mirrors using unpacked directories. `h1:` ("hash scheme 1", preferred) is a SHA256 of the package *contents*, so it verifies a `.zip`, an unpacked dir, or a recompressed `.zip` alike. Both are per-platform: one of each per OS/arch build. Terraform adds `h1:` opportunistically, one platform at a time, as `init` runs on each; OpenTofu 1.12 pre-populates every platform's `h1:` on first install. | [[tf-dependency-lock]], [[ot-dependency-lock]] |
| `constraints` (lock file field) | The record of every version constraint Terraform weighed when selecting. **Not** used to make installation decisions — present only to explain the past decision to a human reader. | [[tf-dependency-lock]] |
| `terraform providers lock` | Command that pre-populates the lock file with `zh:`+`h1:` checksums for chosen `-platform=` targets, so a config locked on one OS still installs and verifies on another. | [[tf-dependency-lock]] |
| Source address | A provider's global address `[HOSTNAME/]NAMESPACE/TYPE` (e.g. `registry.terraform.io/hashicorp/aws`, short form `hashicorp/aws`); hostname defaults to the public registry. | Book Ch 2 |
| Version constraint (`~>`) | Pessimistic operator: `~> 6.0` allows `>= 6.0, < 7.0`; `~> 6.53.0` allows `6.53.x` but not `6.54.0`. Root modules pin a bounded major; child modules specify only a minimum. | Book Ch 2 |
| `required_version` | Floor constraint (inside `terraform`) on the *CLI* version — set to the oldest feature the config uses (e.g. `>= 1.2`), not the newest available; over-pinning locks out otherwise-compatible CLIs and module consumers. | Book Ch 2 |
| `.terraform/` directory | Hidden cache of downloaded provider/module binaries, recreated by `init`; platform-specific and disposable — never committed. | Book Ch 2 |
| Local name | The module-local key for a provider in `required_providers` (the `aws` in `aws = { … }`); doubles as the resource-type prefix (`aws_instance`). Keep it equal to the type unless two providers collide. | Book Ch 2 |
| Provider plugin (gRPC) | A provider is a standalone Go binary Terraform core launches as a subprocess and talks to over gRPC. Core stays vendor-agnostic — it parses HCL, builds the graph, plans, and manages state, then delegates every vendor-specific call to the provider. The provider *is* the abstraction boundary that lets one engine manage any platform. | Book Ch 5 / [[providers]] |
| Resource address | The `TYPE.NAME` pair a `resource` block's two labels form (`aws_instance.web`); how state tracks the resource and how other blocks reference it. The type prefix names the provider. | Book Ch 5 |
| Utility provider | A provider that wraps no vendor — `random`, `null`, `time`, `tls`. Its resources are local-only (compute a value into state, no cloud object). Still declared in `required_providers`. Distinct from the one type built into core, `terraform_data`. | Book Ch 5 |
| Saved plan (`-out`) | A plan frozen to a file with `plan -out=FILE`, then executed exactly with `apply FILE` (no re-plan, no prompt). Guarantees what was reviewed is what runs; the CI/CD review-then-apply backbone. Perishable — embeds specific resource states. | Book Ch 3 |
| Implicit refresh | The in-memory read of tracked objects from providers that `plan`/`apply` run before diffing, so out-of-band drift is detected. In-memory only — a bare `plan` does not persist the refreshed values to state. | Book Ch 3 |
| Forced-new attribute | A resource argument the provider cannot patch live; changing it forces a `-/+` destroy-and-recreate rather than a `~` in-place update (e.g. an EC2 instance's `subnet_id`). | Book Ch 3 |
| Dependency graph | The graph Terraform builds at plan time from attribute references; apply walks it in dependency order (destroy in reverse), running independent operations in parallel (default 10). You declare *what*, the graph decides *when*. | Book Ch 3 |
| Implicit dependency | An ordering relationship created when one resource references another's attribute (`subnet_id = module.vpc.private_subnets[0]`); preferred over explicit `depends_on`, which is a fallback for dependencies invisible to Terraform. | Book Ch 3 |
| Meta-argument | An argument defined by Terraform core rather than by a provider, controlling *how* a block is managed rather than what it builds. Six exist: `count`, `for_each`, `depends_on`, `lifecycle`, `provider`, `providers`. Every resource supports them regardless of provider, and all are evaluated before the dependency graph is built. | Book Ch 10 |
| Block address vs instance address | `aws_s3_bucket.site` names the block; `aws_s3_bucket.site[0]` (count) or `aws_s3_bucket.site["logs"]` (for_each) names one instance. A block with neither meta-argument takes no index at all, so adding `count` to an existing block changes every address it owns. | Book Ch 10 |
| Reindex footgun | Removing the element at index *i* of a `count` list shifts every later instance down a slot, so Terraform destroys **`n - i` objects** (the one you removed plus every object after it) and recreates `n - 1 - i` of them. Measured: three buckets, remove the middle → `1 to add, 2 to destroy`; six buckets, remove index 1 → `4 to add, 5 to destroy`. Under `for_each` the same removal is `1 to destroy`. | Book Ch 10 |
| `each.key` / `each.value` | The instance key and value inside a block that sets `for_each`. Identical for a set. Keys must be plan-time known, non-impure, and **never sensitive** — Terraform always discloses them in UI output, so a secret cannot be an instance key. | [[tf-meta-for-each]] |
| `for_each` chaining | Using one `for_each` resource directly as another's `for_each` (`for_each = aws_vpc.example`), so `each.value` is a whole upstream object. Declares that both blocks' instance keys always change together, rather than deriving them independently from the same source. | [[tf-meta-for-each]] |
| `count.index` | The zero-based index available inside a block that sets `count`. Distinguishes the *block* address (`aws_instance.server`) from an *instance* address (`aws_instance.server[0]`); a block with neither `count` nor `for_each` takes no index. Instances are keyed by **position**, so removing a middle element re-indexes everything after it. | [[tf-meta-count]] |
| Explicit dependency | An edge asserted by hand with `depends_on`, for an ordering requirement that leaves no trace in the configuration. Carries two costs: a more conservative plan (spurious `known after apply`, over-replacement) and a longer apply from work the graph could have parallelized. | [[tf-meta-depends-on]], [[tut-dependencies]] |
| `apply -replace=ADDR` | Force one resource to be destroyed and recreated, shown as `-/+` in the plan for review first. Supersedes the deprecated out-of-band `taint`/`untaint`. | Book Ch 3 |
| `apply -refresh-only` | Reconcile state with real-world drift *without* proposing infrastructure changes; the supported replacement for the old standalone `terraform refresh`, since it shows the drift and asks before writing state. | Book Ch 3 |
| `-target` / `-exclude` | Targeting options restricting an operation to (or away from) named addresses + their dependencies. Exceptional-use only — they plan against a partial view and hide drift. `-exclude` (negative targeting) is OpenTofu-only (1.9+); mutually exclusive with `-target`. | Book Ch 3 |
| Input variable | A `variable` block — data sent *into* a module (the "function argument"), referenced with `var.NAME`. Arguments: `type`, `description`, `default`, `sensitive`, `nullable`, `ephemeral`, repeatable `validation`. Optional when it has a `default`; without one Terraform prompts (or errors in non-interactive runs). | TID Ch3, [[tf-input-variables]] |
| Variable precedence | Order Terraform applies when one variable gets values from several sources (highest→lowest): `-var`/`-var-file` + HCP Terraform vars → `*.auto.tfvars` (lexical) → `terraform.tfvars.json` → `terraform.tfvars` → `TF_VAR_` env vars → the `default` argument. | [[tf-input-variables]] |
| `TF_VAR_` env var | `export TF_VAR_<name>=<value>` assigns an input variable from the environment — used in CI/CD to inject values without files. Low precedence (just above `default`). An `TF_VAR_` with no matching `variable` block is **silently ignored**. | [[tf-input-variables]] |
| `const` (variable lifecycle) | Attribute that makes a variable evaluate at **init** instead of plan — required to use a variable in a module/provider `source` or `version`, since those are read before a plan exists. Restricts the variable to a known, constant value. | [[tf-input-variables]], [[tf-block-variable]] |
| `variable` reserved names | A `variable` label must be unique in its module and cannot be any of: `source`, `version`, `providers`, `count`, `for_each`, `lifecycle`, `depends_on`, `locals`. | [[tf-block-variable]] |
| `nullable` (variable argument) | Whether a caller may assign `null`. Default **`true`**; `nullable = false` forbids `null` and makes a `null` fall back to the `default`. Nested elements of a collection/structural type may still be `null`. | [[tf-block-variable]] |
| `validation` block (variable) | Custom rule beyond the type constraint, checked at plan time. `condition` (must be `true`) and `error_message` are both required; a false condition halts the operation. | [[tf-block-variable]] |
| `deprecated` (variable/output, TF 1.15+) | Deprecation message for evolving a module's public API without breaking consumers. On a **variable**: shown when set in a root module or a child caller passes a value. On an **output**: child-modules-only, shown when another module uses the output — the defining module sees no warning. Suppress nested warnings for a module call with `ignore_nested_deprecations` in the `module` block. | [[tf-block-variable]], [[tf-block-output]] |
| `precondition` (output) | A block inside `output` that validates the value before Terraform exposes it or stores it in state; `condition` (must be `true`) + `error_message`, checked at plan. The output-side counterpart to a variable's `validation` block. | [[tf-block-output]] |
| Output `type` (TF 1.15) | Optional type constraint on an `output` value (unset → any). Typing module outputs improves matching between validation, plan, and apply. | [[tf-block-output]] |
| Ephemeral value (TF 1.10+) | A value available only during a single operation and **never written to state or plan**. Three forms: the `ephemeral` argument on variables/child-module outputs, the `ephemeral` block, and a write-only resource argument. Referenceable only in ephemeral contexts (locals, ephemeral var/output, write-only arg, ephemeral/provider/provisioner blocks). | [[tf-manage-sensitive-data]] |
| `ephemeral` block / ephemeral resource (TF 1.10+) | A provider-defined resource that exists only during the current operation and is never stored (e.g. `ephemeral "random_password"`). Referenceable only from other ephemeral contexts, such as a write-only argument. | [[tf-manage-sensitive-data]] |
| Write-only argument (TF 1.11+) | A managed-resource argument (conventionally `_wo`, paired with `_wo_version`) that Terraform passes to the provider during an operation then discards — never persisted to state/plan. Bump `_wo_version` to re-send the value. | [[tf-manage-sensitive-data]] |
| Local variable | A `locals` block value — internal to its module (the "function local"), referenced with `local.NAME`. The `locals` block takes no label, can repeat across files, and locals may reference variables, resource attributes, function outputs, and other locals; duplicate names error. Module-scoped: pass to a child as an argument to share. | TID Ch3, [[tf-locals]] |
| Variable-as-constant | All Terraform "variables" are set once per run and cannot change mid-run — Terraform is declarative and executes by dependency order, not source order. Compute new **locals** instead of reassigning. | TID Ch3 |
| Type constraint | The value passed to a `type` argument that restricts a variable: keywords `string`/`number`/`bool`/`any`, collections `list(T)`/`set(T)`/`map(T)`, structural `tuple([...])`/`object({...})`, and `null`. Optional (Terraform is loosely typed) but a quality signal. | TID Ch3 |
| Collection vs structural type | The two families of complex type. **Collection** (`list`/`map`/`set`) holds one element type across any number of elements, so converting a mixed value unifies it. **Structural** (`tuple`/`object`) holds a fixed schema where each position or key has its own type, so mixed values survive. | [[tf-expr-type-constraints]] |
| Complex-type literals | HCL has only two: brackets always build a `tuple`, braces always build an `object`. `list`, `set`, and `map` have no literal and arrive only via conversion (`tolist`/`toset`/`tomap`), a declared `type`, or a provider schema. | [[tf-expr-type-constraints]] |
| Object vs map | `object({k=T,...})` fixes its keys and lets each key be a different type (drops keys not in the constraint); `map(T)` allows arbitrary keys but all values share one type (ideal for `tags`). | TID Ch3 |
| Set vs list vs tuple | `list(T)` = ordered, indexed, one element type. `set(T)` = unordered, no duplicates. `tuple([...])` = fixed length, each element its own type. | TID Ch3 |
| `optional()` attribute | Object type-constraint modifier: `optional(T)` defaults a missing key to `null`, `optional(T, default)` to the given value. Graduated from experimental in Terraform 1.3. | TID Ch3 |
| `validation` block | Repeatable subblock inside `variable` with a boolean `condition` (must reference the tested variable) and an `error_message`. Since Terraform 1.9 the condition may reference *other* variables/locals/data too. | TID Ch3 |
| Sensitive value | A `variable`/`output` marked `sensitive = true` is masked in logs/plan/CLI, and the flag follows derived values. **Still stored plaintext in state** — masking affects display only. | TID Ch3 |
| Root vs shared vs submodule | Root = the entry-point module Terraform runs from (only place a `provider` block is legal). Shared = pulled from Git/registry. Submodule = shipped inside a parent's `modules/` dir, referenced with `//`. | TID Ch3 |
| HCL (HashiCorp Configuration Language) | The language every `.tf` file is written in; built from exactly two constructs — arguments and blocks. Shared across HashiCorp tools and identical in Terraform and OpenTofu. | Book Ch 4 |
| Identifier | A name for an argument, block type, or label. May contain letters, digits, `_`, and `-`; the first character must not be a digit. Unicode identifier syntax plus the ASCII hyphen. | Book Ch 4 |
| Label | A quoted word after a block type. Block types take zero labels (`terraform`, `locals`), one user-chosen label (`variable`, `output`, `module`, `provider`), or two (`resource`/`data`: subtype + name). | Book Ch 4 |
| Reference string | The address that names a block for use in other blocks: `aws_instance.web` (resource — no `resource.` prefix), `data.aws_ami.ubuntu`, `var.region`, `local.tags`, `module.net.out`. A reference is what creates a dependency edge. | Book Ch 4 |

| Expression | Anything to the right of an `=` — a literal, reference, operator chain, function call, conditional, `for`, or splat. The unit Terraform evaluates to produce a value. | TID Ch4 |
| Conditional (ternary) | `cond ? a : b` — Terraform's `if/then/else`. Both branches must be **type-compatible**, and that check is **unconditional**: `true ? 1 : ["a"]` errors even though the taken branch is fine (otherwise Terraform auto-converts to a common type; prefer explicit `tostring()` etc.). But only the **taken** branch is *evaluated* — a runtime error in the untaken branch (indexing an empty `count`, a bad index) does **not** fire, even when the condition is unknown at plan time. | Pure vs impure function | Pure = same inputs → same output (`merge`, `max`); impure = varies per call (`uuid`, `timestamp`). | `flatten()` / `setproduct()` | The two functions that shape a nested or combinatorial input into the flat collection `for_each` needs. `flatten` replaces nested list elements with a flat sequence, recursively and at any depth. `setproduct` returns every combination of two or more collections, each element a **tuple** indexed positionally (`p[0]`, `p[1]`). Rule of thumb: `flatten` when the pairing is already in the data, `setproduct` when it is not. | Ch 7 §8 |
| `merge()` | Function combining maps; later keys override earlier ones. Canonical use: `merge(var.tags, { Name = … })` to let callers add tags while the module sets its own. | TID Ch4 |
| `try` / `can` | `try(a, b, …)` returns the first non-erroring argument (defaults, optional-resource attribute access). `can(expr)` returns a boolean — `false` if `expr` errored — and belongs in `validation` conditions almost exclusively. Neither should mask real errors. | TID Ch4 |
| Resource graph (node types) | Terraform's internal DAG; state is a snapshot of it. Three node types: **Resource** (one per instance, data sources included), **Provider Configuration** (one per provider config), **Resource Meta** (cosmetic grouping when `count > 1`). **Modules are not nodes** — boundaries are flattened, so a resource in module B can precede one in module A. | TID Ch5 |
| Speculative plan | A plan run **without** `-out`, i.e. one you don't intend to apply — for dev, testing, and PR checks. Common to pair with `-lock=false` since there's no corruption risk. | TID Ch5 |
| Planning mode | Which kind of plan Terraform computes: **default** (reconcile infra to code), **destroy** (`-destroy`, all `-`, DAG walked in reverse), **refresh-only** (`-refresh-only`, sync state to reality only, ignores code edits). Default and destroy both begin with a refresh. | TID Ch5 |
| State locking (`-lock`) | Terraform tells the backend only the current process may use the state, so two concurrent applies can't corrupt it. Managed automatically; `-lock=false` disables it (acceptable only for speculative plans). Silent on success, and a failure to acquire **stops the run**. | TID Ch5 · [[tf-state-locking]] |
| Lock ID (nonce) | The identifier Terraform prints when unlocking fails, and the required argument to `terraform force-unlock`. It is a **nonce for one lock acquisition**, not a reusable name — so you can't force-unlock blind, and a stale ID won't release the current lock. | [[tf-state-locking]] |
| Eternal drift (always-detected changes) | A **provider bug** where a plan always reports a change no apply can settle, because the provider doesn't round-trip a value cleanly (int→float, bool→string, list re-order, case change, missing→empty). Rare now. Workaround: match your input to what the API returns, then file a provider bug. | TID Ch5 |
| Cascading change / `# forces replacement` | One edit rippling through the DAG to replace downstream resources (`-/+`), flagged in the plan as `# forces replacement`. Mitigate by reviewing plans, adding the triggering attribute to `lifecycle.ignore_changes`, or shortening dependency chains. | TID Ch5 |
| Unknown value / `(known after apply)` | A placeholder for an attribute the remote system decides only at apply (a generated ID, an assigned IP). Propagates: known + unknown = unknown. Rendered `(known after apply)` in plans. **`count`/`for_each` cannot be unknown** — they must resolve at plan time. | Book Ch 7 |
| String template directive (`%{}`) | Control flow inside a string: `%{ if cond }…%{ else }…%{ endif }` and `%{ for x in coll }…%{ endfor }`. Distinct from interpolation `${}` (insert a value). A trailing `~` strips surrounding whitespace; `$${`/`%%{` emit literals. | Book Ch 7 |
| Grouping mode (`for … : k => v…`) | A `for` object result normally needs unique keys. Appending `...` after the value expression collects all values sharing a key into a list, producing a map of lists (e.g. invert username→role into role→[usernames]). | Book Ch 7 |
| `coalesce` vs `try` vs `lookup` | Three fallback functions for different failures: `coalesce(a,b)` → first **non-null/non-empty** (a evaluates fine); `try(a,b)` → first that **evaluates without error**; `lookup(map,key,default)` → value or default when a **key is missing**. `null` is a success for `try`, so wrap with `coalesce` to also treat null as missing. | Book Ch 7 |
| Dynamic secret | A credential generated on demand and expiring on a lease, rather than a value stored until someone changes it. The secrets platform logs into the backend with a privileged account and runs a creation statement per lease, then a revocation statement at expiry. Terraform stores the *instructions* (`infisical_dynamic_secret_sql_database` and similar); minting a lease is a separate, out-of-band step. | [[infisical-terraform-secrets]] |
| Secret rotation (two-user pattern) | Keeping a standing credential but replacing its password on a schedule. Implemented with **two** backend users: one live, one idle. Rotation sets a new password on the idle user and switches the mapped secret keys over, so consumers migrate without downtime and nothing redeploys. | [[infisical-terraform-secrets]] |
| SOPS | File encryption, not a secrets manager. Encrypts values inside a YAML/JSON file with an age, PGP, or cloud KMS key; keys stay readable so committed ciphertext still diffs meaningfully. No access control, audit log, or rotation of its own. Community Terraform provider decrypts at plan time. | [[infisical-terraform-secrets]] |
| Machine identity / OIDC auth | A non-human principal that authenticates with a short-lived, CI-minted OIDC token instead of a stored client secret. The platform matches the token's claims against a binding (e.g. `repo:org/repo:ref:refs/heads/main`), so only that repo and branch can authenticate; the identity ID itself is public and safe to commit. | [[infisical-terraform-secrets]] |
| Configuration management (vs. provisioning) | The tool category that configures machines that already exist (Ansible, pyinfra, Chef, Salt), as distinct from provisioning them (Terraform). Diffs against the **live host** every run rather than a persisted state file — which is why it has no state problem, and also why it can't detect resources it didn't create. The recommended replacement for a `provisioner` block. | [[pyinfra]] |
| Terraform → config-management handoff | The provisioner alternative: Terraform builds hosts and publishes their addresses as a root output; a config tool reads `terraform output -json` as its **inventory** and takes over outside the apply. Buys untainted failures and Terraform-free re-convergence; costs an ordering dependency between two runs. | [[pyinfra]] |
| Inventory (config management) | A config tool's list of target hosts plus their per-host data — the analogue of what Terraform's outputs describe. Sourced from Terraform via `terraform output -json` (pyinfra's `@terraform` connector) or from the state file (Ansible's `terraform_provider` plugin); the two differ sharply in what they expose. | [[pyinfra]] |
| Data source read timing (refresh vs apply) | When a `data` block is queried. **Default:** during the pre-plan **refresh**, so real values appear in the plan. **Deferred to apply** (all attributes show `(known after apply)`) when any argument depends on a resource changing in the current plan, on a computed value, on a custom condition over such a value, or on `depends_on`. Deferral cascades to every resource downstream. | Book Ch 8 |
| Local-only (specialized) data source | A `data` source that generates data existing only during the operation, recomputed every plan, with **no remote API call** — e.g. `aws_iam_policy_document` (renders policy JSON), `local_file` (reads a file), the legacy `template_file` (superseded by `templatefile()`). | Book Ch 8 |
| `lineage` | A UUID-shaped ID written into state the first time a snapshot is stored at a location, and **never changed** afterwards. Actually 128 bits from `crypto/rand`, with no RFC 4122 version/variant bits set. A safety guard against overwriting one project's state with another's — but only compared where two independently obtained snapshots meet (`state push`, backend migration, applying a saved plan, remote-backend conflict detection), never during a routine plan/apply. `-force` bypasses it. Paired with `serial`. | TID Ch6 |
| Backend | Where state is stored, plus an optional API for locking it. Written as a `backend` block in `terraform {}`; omit it and you get `local`, which keeps `terraform.tfstate` in the working directory, locks via system APIs, and runs operations on your machine. Remote backends (`s3`, `gcs`, `azurerm`, HCP Terraform) move the file to shared storage without changing any state command's behaviour. | Book Ch9, Ch15 / [[tf-state-backends]], [[tf-backend-local]] |
| State snapshot | One complete state document, written out whole. Terraform never patches state in place or appends a delta: each write serialises the entire state and replaces the stored copy, which is why the local backend keeps the previous one as `terraform.tfstate.backup`. A single apply usually writes several. | Book Ch9 |
| `serial` | Integer in state bumped **+1 per persisted snapshot that differs from the previous one** — a count of *writes*, not of applies, since one apply can persist several snapshots as resources complete. The first snapshot ever persisted is `serial` 1 (the 0 from `NewStateFile` is in-memory only and never written). **Not predictable from resource count:** writes coalesce when resources finish close together, so identical from-scratch applies of one configuration landed on 1, 1, and 4 (Terraform 1.15.8; the same config repeatedly ends at 1 on OpenTofu 1.12.4). Use it to identify the newest of several backup/versioned states, nothing else; cloud-block backends use it to refuse overwriting a newer state with an older one. Bump it by 1 on a hand-edited backup to `state push` without `-force`. | TID Ch6 / Book Ch9 |
| State backend | The built-in Terraform subsystem that decides **where state lives** and how it's locked/accessed (`local`, `s3`, `gcs`, `azurerm`, `consul`, `pg`, `http`, `kubernetes`, `remote`, `cloud`, …). Configured in a `backend` block in the **root** module only; not extensible by third parties. Pick by the tech the team already runs. | TID Ch6 |
| Partial backend configuration | A `backend` block with the per-environment/secret arguments omitted (often left nearly empty), filled at init via `-backend-config=<file>` or `-backend-config="k=v"`. CLI flags beat the file; values are cached under `.terraform/`. Keeps credentials out of committed code and makes one config serve many environments. | TID Ch6 |
| S3-native state locking (`use_lockfile`) | S3-backend locking via an S3 **conditional-write** `.tflock` object in the bucket, enabled with `use_lockfile = true` — no DynamoDB table. **Terraform 1.10** (opt-in, takes both locks alongside DynamoDB), **GA in 1.11** where `dynamodb_table` was deprecated; **OpenTofu 1.10**, which has *not* deprecated `dynamodb_table`. Matching version numbers on different schedules: Terraform's 1.10 predates OpenTofu's by about seven months. | [[version-facts]], [[release-feature-map]], [[opentofu-release-feature-map]] |
| Local state fallback | What a **non-local** backend does when persisting state to it fails: rather than lose the run's result, Terraform writes the state to local disk. Recovery is manual — `terraform state push` it once the backend error is fixed. The exception to the "remote backend never persists state to disk" guarantee, so it leaves a plaintext state file on a machine that guarantee otherwise excludes. | [[tf-state-backends]] |
| Retained dependencies (state `dependencies`) | The copy of each resource's most recent dependency set that Terraform saves in state. Exists for **destroy ordering**: once a resource is deleted from the configuration, the edges that would have given its destroy order are gone with it, so the order comes from state instead. The rejected alternative — a built-in ordering hierarchy per resource type — would require Terraform to know the ordering semantics of every resource in every provider, plus ordering *across* providers. | [[tf-state-purpose]] |
| One-to-one mapping rule | Terraform's assumption that each configured resource instance binds to exactly **one** remote object. Guaranteed automatically while Terraform does the creating and destroying. Broken the moment you add or remove bindings by hand — `terraform import` of an externally-created object, or `terraform state rm` to "forget" one. After either, restoring the invariant is the operator's job: delete the forgotten object, or re-import it against another instance. | [[tf-state]] |
| State drift | Divergence between Terraform state and real infrastructure caused by out-of-band changes; detected on refresh (plan start or `plan -refresh-only`). Four categories: accidental manual, intentional manual, conflicting automated, Terraform errors — each with its own fix (plain `apply`, get-into-code, `ignore_changes`, `import`/restore). | TID Ch6 |
| `-refresh-only` planning mode | `plan`/`apply` flag (0.15.4+) that reconciles **state to reality** and nothing else — no configuration-driven changes proposed, no remote object touched. The plan reports drift in the past tense (`# aws_instance.example has been changed`) where a normal plan reports intent in the future tense; the apply prompts before writing, which `terraform refresh` never does. Counters stay `0 added, 0 changed, 0 destroyed` because they count infrastructure actions, not state writes. Drifted **outputs** are rewritten too. | [[tut-resource-drift]], [[tf-cmd-refresh]] |
| `moved` block | Config-driven state relocation (Terraform ≥ 1.1): `from`/`to` a resource or module address so Terraform **renames the state entry instead of destroy+recreate**. No-op once `from` is gone; safe to leave in code. Essential for refactoring shared modules without breaking consumers. Preferred over `terraform state mv`. | TID Ch6 |
| `removed` block | Config-driven state removal (Terraform ≥ 1.7): `from` an address plus a required `lifecycle { destroy = true|false }` — drops the entry from state, optionally keeping the real resource. Replaces the old "comment out + `terraform state rm`" workaround. | TID Ch6 |
| Configuration-driven import | Adopting existing infrastructure by writing an `import` block (`id` = the provider-specific identifier, `to` = the state address) and running the normal plan-and-apply, rather than the `terraform import` command. Terraform ≥ 1.5. Preferred because it is previewable in a plan, works unattended in CI/CD, and can generate a starting configuration. | [[tut-state-import]] |
| `-generate-config-out=<file>` | `terraform plan` flag (1.5+) that writes best-guess HCL for every `import` block whose resource has no configuration yet. The draft contains **all possible arguments including defaults and nulls**, so it must be pruned; a generated `null` for a collection attribute (e.g. Docker's `env`) reads as a change and can force replacement. | [[tut-state-import]] |
| State-only provider | A provider whose resources compute values programmatically and persist them **only in state**, with no external API or file — `random`, `time`, `null`, `tls`, `cloudinit`. Enabled by Terraform being stateful; impossible in a stateless engine. | TID Ch6 |
| State attribute cache | The copy of every resource attribute stored in state. Documented as "the most optional feature of Terraform state… only as a performance improvement" — normally overwritten by the refresh at the start of each run. **`-refresh=false` promotes it to the source of truth**, which makes all out-of-band drift invisible to the plan. | [[tf-state-purpose]] |
| `terraform.tfstate.backup` | The previous state snapshot, written automatically by the **local backend** each time it persists a new one. Appears on the second write, not the first, and carries the previous `serial`. Not a backup strategy — it survives only as long as the working directory. | [[tf-state]], [[tf-backend-local]] |
| `keepers` / `triggers` (state-only) | A map argument on `random`/`time` resources; changing any value **regenerates** the persisted random/time value. This is how state-only resources stay stable across plans (avoiding the perpetual drift an impure function like `timestamp()`/`uuid()` would cause) yet remain refreshable on demand. `terraform_data` uses `triggers_replace`, `null_resource` uses `triggers`. | TID Ch6 |
| Deposed object | During a `create_before_destroy` replacement, the prior object is moved aside in state under a generated **deposed key** so both objects can exist at once, then destroyed. Rendered as `aws_s3_bucket.app (deposed object 6fc41790): Destroying...`. A failed apply can leave one behind, still in state and still billed; the next plan destroys it. **`terraform state list` does not show deposed objects** (it prints only current objects) — use `terraform show -json` and read `deposed_key`. | Book Ch 11 |
| Forced create-before-destroy | Terraform propagates `create_before_destroy` from a resource to everything it depends on, transitively, and records it in their state. An explicit `create_before_destroy = false` on a propagated resource is **silently discarded** — measured on TF 1.15.8 and OpenTofu 1.12.4; only `TF_LOG=trace` reports `ForcedCBDTransformer: forcing create_before_destroy on for …`. | Book Ch 11 |
| `+/-` vs `-/+` (plan symbols) | Replacement order, read left to right. `-/+ destroy and then create replacement` is the default; `+/- create replacement and then destroy` means `create_before_destroy` is active. Nothing else in the plan announces the rule. | Book Ch 11 |
| `ignore_changes` (create vs update) | The listed attributes are **considered when planning a create** and ignored only when planning an **update**. It suppresses the plan, not the refresh, so configuration and state legitimately diverge until the next replacement. `all` is a bare keyword: `ignore_changes = all` is valid, while both `[all]` and `["all"]` are `Unsupported attribute` errors. | Book Ch 11 |
| Type constraint | A rule written in a `type =` argument that every incoming value must satisfy. Not a type and not a gate — a **conversion step** with three outcomes: convert the value, silently discard part of it, or reject it. Legal only in a `variable` `type`, a module `output` `type` (1.15+), and `convert()` (1.15+, Terraform-only). | Book Ch 12 |
| Type keyword vs type constructor | A **keyword** is a bare symbol naming one static type (`string`, `any`). A **constructor** takes a parenthesised argument (`list(string)`, `object({…})`). A constructor written without its argument means a *kind* of type, so `type = list` silently means `list(any)`. | Book Ch 12 |
| Attribute discard (object constraint) | An `object(...)` constraint keeps only the attributes it declares and **silently deletes** the rest, by design, so a whole resource object can satisfy a narrow constraint. The cost: a caller's misspelled attribute becomes a no-op with no error. OpenTofu 1.12.4 emits `Warning: Object attribute is ignored` for module calls and variable defaults but **not** for `.tfvars`; Terraform 1.15.8 says `Success!` in every case. | Book Ch 12 |
| `optional(type, default)` vs `nullable` | Two mechanisms called "default" that disagree about `null`. A variable's `default` covers **absence only** — an explicit `null` is kept, since `nullable` defaults to `true`. An `optional()` attribute default covers absence **and** an explicit `null`, always, with no opt-out. So a non-null `optional()` default is guaranteed never `null` inside the module; a variable default is not. Measured on 1.15.8. Stable since Terraform 1.3. | Book Ch 12 |
| Top-down default application | With nested `optional()` attributes, the outer default is applied first and the inner defaults are then applied to that result. This is what makes `optional(object({…}), {})` deliver a fully populated sub-object rather than an empty one. | Book Ch 12 |
| `dynamic` block | Generates repeated **nested blocks** from a collection — what a `for` expression is to values. | Terraform Plugin Framework | The current SDK for writing providers in Go (`terraform-plugin-framework`, **v1.19.0**, 2026-03-10). Speaks **protocol version 6** for you, so provider authors never write gRPC. Successor to SDKv2; the interface is a small core (`Metadata`, `Schema`, `Configure`, `Resources`, `DataSources`) plus opt-in extensions (`ProviderWithFunctions`, `…WithEphemeralResources`, `…WithListResources`, `…WithActions`, `…WithStateStores`). | TID Ch12, pkg.go.dev |
| Schema (provider plugin) | A component's declaration of its typed attributes — required/optional/computed, sensitivity, deprecation, defaults, descriptions. **At least one of `Required`, `Optional`, `Computed` must be true**, or the framework fails with "Invalid Attribute Definition". `Default` and `PlanModifiers` exist only on *resource* schemas; a provider attribute's "default" is the `os.Getenv` fallback in `Configure`. | TID Ch12 §12.3.1, framework v1.19.0 |
| `Diagnostics` | The error/warning collection carried on the `resp` of nearly every provider function. Append to it repeatedly (`AddError`, `AddAttributeError` with a `path.Root(…)`), then check `HasError()` once at the end — so the user sees every problem, not just the first. | TID Ch12 §12.3.2 |
| `tflog` | The framework's logging package. Its levels map onto what `TF_LOG` selects, and `MaskFieldValuesWithFieldKeys` redacts secrets from provider logs (separate mechanism from schema `Sensitive`). Never use `log.Fatal` in a provider: the plugin dies without returning diagnostics and can corrupt state. | TID Ch12 §12.3.2 |
| Acceptance test (provider) | A test named `TestAcc…`, run via `resource.Test`, that calls the **real Terraform binary** against the **real service** — so it can cost money. Gated on `TF_ACC=1`, which the scaffolding template's `make testacc` sets. Unit tests (`resource.UnitTest`, `Test…` prefix) touch nothing external and are how provider-defined functions are tested. | TID Ch12 §12.3.3, scaffolding `GNUmakefile` |
| `dev_overrides` | `provider_installation` block pointing a provider address at a local directory of built binaries, bypassing registry, version and checksum checks. Keep `direct {}` alongside it or no *other* provider resolves. `terraform init` still tries to install a published version (so it fails for an unpublished provider) while `apply` ignores the lock entry and uses your build. Terraform reads `~/.terraformrc`; **OpenTofu reads `~/.tofurc`**, falling back to `.terraformrc` only when `.tofurc` is absent. | TID Ch12 §12.2.2, HCDocs CLI config, OpenTofu 1.12.5 source |
| `UseStateForUnknown()` | Resource plan modifier that reuses the state value for a computed attribute instead of printing `(known after apply)`. Applied to attributes that cannot change after creation (ids, timestamps), it removes most of the noise from a plan. | TID Ch12 §12.6.1 |
| `tfplugindocs` | `hashicorp/terraform-plugin-docs` — generates provider documentation from the schemas, including every `MarkdownDescription`, and folds in whatever is under `examples/`. Run through `go generate`; the provider-side counterpart to `terraform-docs`. | TID Ch12 §12.8.1 |
| `cloudinit_config` | Data source that renders a multi-part Cloud-Init payload (`part` blocks with `content_type`) for a resource's `user_data`. `yamlencode` on a Terraform object is what makes the configuration dynamic rather than a static blob. The sanctioned alternative to a provisioner for launch-time configuration. | TID Ch10 §10.8.3 |
| Heredoc (`<<-EOF`) | HCL multiline string form, used to embed a shell script or config file without `\n` escapes. The `-` is what strips leading indentation, so the block can be indented to match the surrounding code. | TUR Ch2 |
| User Data | A shell script or cloud-init directive passed to an EC2 Instance that runs **only on its very first boot**. The once-only semantics are why `user_data_replace_on_change` exists. | TUR Ch2 |
| `user_data_replace_on_change` | `aws_instance` argument. Terraform's default is to update an instance in place, which would leave a changed User Data script never executed; setting it `true` forces replacement instead, so the new script actually runs. Not needed on an ASG, which launches new instances anyway. | TUR Ch2 |
| `forces replacement` | The marker to search for in plan output when a resource shows `-/+`. It names the attribute whose change caused the replacement — the only place the plan says *why* rather than *what*. | TUR Ch2 |
| Default VPC | The VPC present in every AWS region of every account created after 2013, used implicitly by any resource that names no VPC. Its subnets are all **public**, which is why the TUR examples are reachable from a home machine and why the book flags them as unsuitable for production. | TUR Ch2 |
| `health_check_type = "ELB"` | ASG argument delegating health checks to the load balancer's target group instead of the default `"EC2"`, which only notices an instance that is completely down. The ELB check catches a running-but-not-serving instance, which is the common failure. | TUR Ch2 |
| `-lock-timeout=<TIME>` | Plan/apply option telling Terraform how long to wait for a held state lock before giving up, e.g. `-lock-timeout=10m`. Without it a locked state fails the run immediately. | TUR Ch3 |
| `env:` (workspace key prefix) | The folder the S3 backend puts non-default CLI workspaces under, so `example1`'s state lands at `env:/example1/<key>` while the `default` workspace writes to the bare `key`. Configurable with `workspace_key_prefix`. The concrete proof that a workspace is just a different state path. | TUR Ch3 |
| `terraform console` | Read-only interactive REPL for evaluating expressions and functions against the current state. Read-only, so experimenting cannot change infrastructure — the fastest way to learn an unfamiliar built-in. | TUR Ch3 |
| Bulkhead (isolation) | Brikman's metaphor for state isolation: as a ship's bulkheads stop one leak flooding every compartment, separate configurations with separate backends and separate credentials stop one environment's mistake reaching another. Separate state alone is not a bulkhead — separate credentials are. | TUR Ch3 |
| Production-Grade Infrastructure Checklist | Brikman's 15-row list of what "ready for production" means — install, configure, provision, deploy, HA, scalability, performance, networking, security, metrics, logs, backup, cost, docs, tests. Its value is the instruction attached: document which rows you implemented, which you skipped, and why. | TUR Ch8 |
| Yak shaving | The chain of unrelated prerequisite tasks between you and the job you meant to do. Named as one of the three reasons DevOps estimates are wrong, alongside industry immaturity and the essential complexity of the checklist. | TUR Ch8 |
| Examples-first (module design) | Writing `examples/` code before any module code, so the module's API is designed from the caller's view instead of surfacing from the implementation. The examples then double as manual test harness, automated test fixture, and executable documentation. | TUR Ch8 |
| `check` block | Terraform **1.5+** assertion that lives outside any resource and reports as a **warning, not an error**, so a failure does not block the apply. Can load a **scoped data source** referenceable only from inside the block. The fourth condition mechanism alongside `validation`, `precondition` and `postcondition`. | Terraform v1.5.0 changelog |
| Cross-object `validation` | Since Terraform **1.9.0** and OpenTofu **1.9.0**, a variable's `validation` condition is a general expression that may reference other variables, data sources and resources. Before that it could reference only its own variable, which is why `precondition` existed for cross-variable checks — the reasoning most pre-2024 material still gives. | TF v1.9.0 / OT v1.9.0 changelogs |
| String directive (`%{...}`) | Control flow inside a string — `%{ for x in c }…%{ endfor }` and `%{ if cond }…%{ else }…%{ endif }`. Distinct from interpolation `${...}`, which inserts a value. | TUR Ch5 |
| Strip marker (`~`) | The tilde in `%{~ for … ~}`, which eats whitespace on the side it faces. Needed because every space and newline inside a heredoc reaches the final string. | TUR Ch5 |
| `one(concat(a[*], b[*]))` | The idiom for reading an attribute off whichever of two mutually exclusive `count`-gated resources exists. `concat` joins the two splats, one of which is empty; `one` returns the single element, `null` for none, and errors on more than one — so it self-checks instead of drifting out of sync with the `count` condition. | TUR Ch5 |
| `instance_refresh` | ASG block that has **AWS** roll instances when the launch template or configuration changes, with a `strategy` and `min_healthy_percentage`. The native replacement for the `create_before_destroy` + `min_elb_capacity` zero-downtime workaround. Trap: it never starts when the `launch_template` block sets `version = "$Latest"` — point `version` at the template's `latest_version` attribute instead. | TUR Ch5, AWS provider docs |
| `min_elb_capacity` | ASG argument making Terraform wait for that many new instances to pass load-balancer health checks before destroying the old ASG. Half of the pre-`instance_refresh` zero-downtime technique; `wait_for_capacity_timeout` (default 10 min) bounds the wait and triggers automatic rollback. | TUR Ch5 |
| Reusable module | A module written to be called by other modules rather than applied directly. Distinguished from a root module by two things it must not have: a `provider` block, and any assumption about the directory it runs in. It has no state of its own — its resources live in the caller's state. | Book Ch 14 |
| Abstraction test | The heuristic for whether a grouping deserves to be a module: *“If you have trouble finding a name for your module that isn't the same as the main resource type inside it, that may be a sign that your module is not creating any new abstraction.”* Paired with the complexity test, the target is a module nameable in a phrase that is neither a paragraph nor a resource type. | [[tf-modules-develop]] |
| Scoping axes (encapsulation, privileges, volatility) | The three questions that decide which resources belong in one module: what is always deployed together, which segregation-of-duties boundary it sits inside, and how often it changes. The last two are blast-radius arguments and so decide state boundaries as well as module boundaries. | [[tut-pattern-module-creation]] |
| Assumption / guarantee | The two directions of a module's contract. An **assumption** must hold for a resource to be usable and belongs on an input, as a `validation`. A **guarantee** is what the rest of the configuration may rely on and belongs on an **output**, as a `precondition`. An object type enforces shape; only a validation enforces content. | [[tf-modules-composition]] |
| Dependency inversion (modules) | Designing a module to *receive* its dependencies as inputs rather than create them, so the caller can wire the same module in different ways — and so the module neither knows nor cares whether an id came from a resource, a data source, or another configuration's state. | [[tf-modules-composition]] |
| Data-only module | A module containing no managed resources, only data sources, whose value is encapsulating *how* the information is retrieved. Give it the same output names as the corresponding management module and the two become swappable with a one-line `source` change. | [[tf-modules-composition]] |
| Shim module | A module kept in place after its contents are split out, containing nothing but calls to the new modules plus the `moved` blocks that re-address existing objects. It is how a published module splits without breaking consumers: their code is unchanged and their plan stays empty. Licensed by the docs only when all the modules share maintainers and ship in one package. | [[tf-modules-refactoring]] |
| `deprecated` (variable / output) | Argument marking a module's input or output as on its way out; callers get a warning naming the replacement. Terraform **1.15**; OpenTofu had it experimentally in **1.10** and stable in **1.11**. Consumer-side only — the declaring module never sees its own warning, and a *root* module output carrying it is an error rather than a warning. | Book Ch 14 |
| Typed output | A `type` constraint on an `output` block, making a module's return values a checked promise readable without reading the implementation. Terraform **1.15**. Rejected outright by OpenTofu 1.12.5 (`An argument named “type” is not expected here`), so a dual-engine module cannot use it. | Book Ch 14 |
| `configuration_aliases` | Declaration inside a module's `required_providers` naming additional provider configurations the module expects to be handed. The caller supplies them through the `providers` map. Necessary because aliased provider configurations are never inherited. | [[tf-modules-providers]] |
| Backend | The component that stores state and, optionally, provides a state-locking API. Those are its only two responsibilities: it runs nothing and holds no variables. Configured in a `backend` block in the root module, one per configuration; the default is `local`. Backends are built into the CLI and cannot be added as plugins, so the catalogue is a finite list per release. | [[tf-state-backends]], Book Ch 15 |
| Partial configuration | A `backend` block that omits some or all arguments, with the rest supplied at `init` through `-backend-config`. The sanctioned answer to a backend block being unable to reference variables. The documented filename convention is `*.<backendname>.tfbackend`; the block itself may be completely empty. | [[tf-backend-configure]], Book Ch 15 |
| `.tflock` object | The lock on an object-store backend: a sibling object next to the state object, written with a conditional PUT that fails if it already exists, and deleted when the operation ends. Both S3 and GCS surface the collision as **412** (`PreconditionFailed` / `ifGenerationMatch … conditionNotMet`). Distributed state locking on both clouds is this one object, with no lock service behind it. | Book Ch 15 |
| `use_lockfile` | The S3 backend argument enabling native lock-object locking. **Defaults to `false`**, so a valid S3 backend block that omits it is silently unlocked. Introduced Terraform 1.10, GA 1.11, OpenTofu 1.10; it replaces `dynamodb_table`, which Terraform deprecates and OpenTofu does not. | [[tf-backend-s3]], Book Ch 15 |
| Lock ID (nonce) | The identifier `force-unlock` requires as a positional argument. It names one specific lock acquisition rather than the lock generally, so a stale ID will not release the current lock and there is no blind-unlock form. Terraform prints it in the `Lock Info` block when acquisition fails. | [[tf-state-locking]], [[tf-cmd-force-unlock]] |
| `-migrate-state` vs `-reconfigure` | The two answers to `init`'s "Backend configuration changed" error. `-migrate-state` copies the current state into the new backend; `-reconfigure` discards the association and starts against the new backend as it is. Only the latest state version migrates, and the migration leaves a complete plaintext copy of the old state on local disk. | [[06-state-management]], Book Ch 15 |
| `workspace_key_prefix` | The S3 backend argument controlling where non-default workspaces store state: `<workspace_key_prefix>/<workspace_name>/<key>`. Defaults to the literal **`env:`**, inherited from the pre-1.0 name for workspaces. GCS has no equivalent because its addressing is `<prefix>/<workspace>.tfstate` for every workspace including the default. | [[tf-backend-s3]], [[tf-backend-gcs]] |
| `encryption` block (OpenTofu) | OpenTofu 1.7+ client-side encryption of state and plan files, applied before the backend sees them and also covering `terraform_remote_state` reads. Pairs a `key_provider` with a `method`. `enforced = true` prevents a missing `TF_ENCRYPTION` from silently writing plaintext, and the `unencrypted` method plus a `fallback` block is the documented migration path in both directions. Terraform has no equivalent at any version. | [[ot-state-encryption]] |
| `state_store` block | An unreleased Terraform block that would let a *provider* supply state storage, replacing the fixed built-in backend catalogue. In the config parser since 1.13 and still behind experimental gating in 1.16.0-rc1, in no changelog, and with no OpenTofu counterpart. Recognise the name; do not plan around it. | [[release-feature-map]] |
| `state pull` / `state push` | The manual state round-trip: `pull` writes the current snapshot to stdout, `push` writes one back. Used where the `init` migration is unavailable, such as moving local state onto a `cloud`-block platform. The push is rejected on **differing lineage** (two independently created states) or a **higher destination serial** (changes since your snapshot); `-force` bypasses both. HashiCorp calls it "extremely dangerous and should be avoided if possible". | [[tf-state-backends]], Book Ch 15 |
| `cloud` block | The alternative to a `backend` block, and mutually exclusive with it. Configures HCP Terraform, Terraform Enterprise, or a compatible platform such as Scalr, Env0 or the self-hosted Terrakube. It does more than store state: it overrides `plan` and `apply` to run remotely. `hostname` defaults to `app.terraform.io` on Terraform and has no default on OpenTofu, and it is the single argument that redirects an otherwise identical configuration to a self-hosted instance. Such platforms front an object store you own rather than storing state themselves. | [[06-state-management]], [[terrakube-migrating]] |
| `errored.tfstate` | The file Terraform writes to the working directory when an apply succeeded but persisting the new state to the backend failed. Recover with `terraform state push errored.tfstate`; do **not** re-run apply first, because that forks the state. If this write also fails, the whole snapshot is printed to stderr instead. On an ephemeral CI runner both fallbacks are hazards: the file dies with the container, and stderr is the job log. OpenTofu encrypts both when an `encryption` block is configured; Terraform cannot. | Book Ch 15 |
| `sensitive` across configurations | A `sensitive = true` output is redacted in its own configuration and its flag is written into the state object, but `terraform_remote_state` ignores that flag on read. Measured on Terraform 1.15.8: the consuming configuration receives an ordinary unmarked string and prints it, where referencing a locally-sensitive value from an unmarked output is a hard error. Sensitivity is enforced within a configuration and dropped across the state boundary. | Book Ch 15 |
