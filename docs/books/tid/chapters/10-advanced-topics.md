## 10.1 Names and domains

The framing that makes this section worth the pages: **naming is code**. If the scheme is generated by the module rather than typed by the user, it cannot drift, and at hundreds or thousands of resources that is the difference between a searchable estate and a pile.

### 10.1.1 Naming considerations

A good name has four properties, and only one of them is technically enforced:

| Property | Why | Enforced? |
| --- | --- | --- |
| **Unique** | Many systems refuse duplicate names outright | Yes — by the platform |
| **Human readable** | Humans maintain the system; `prod-api-lb` beats `abd236a` | No |
| **Identifiable** | The name should say what the thing *is* and where it lives | No |
| **Sortable** | Listing and filtering cluster naturally with a shared prefix | No |

The distinction between *readable* and *identifiable* is the one people miss. `large-finch` and `current-walrus` — the [petname](https://github.com/dustinkirkland/golang-petname) style used by the `random_pet` resource — are perfectly readable and tell you nothing. `prod-api-lb` is both.

Sortability is why the environment goes in the **prefix**, not the suffix: `prod-` and `dev-` prefixes make every production resource sort together and filter with one substring.

### 10.1.2 Hierarchical naming schemes

All four constraints point at the same answer, and it is one Terraform already uses on itself:

| System | How it nests | Example |
| --- | --- | --- |
| DNS | Domains split into subdomains | `db.auth.example.com` |
| Terraform | Resource names inherit the module path | `module.lb.module.logs.aws_s3_bucket.main` |

A Terraform address *is* a hierarchical name — depth in the module tree defines it, and it is what you see in plan output and in state. Mirror that structure in the names you generate.

**The pattern, top down.** The root module hardcodes the application name (it is the same in every environment) and takes the environment as a variable. Everything below is built from that base:

```hcl
locals {
  application = "acme"
  base_name   = "${local.application}-${var.environment}"   # acme-dev
}

module "api" {
  source = "./service"
  name   = "${local.base_name}-api"       # acme-dev-api
}

module "database" {
  source = "./db"
  name   = "${local.base_name}-db"        # acme-dev-db
}
```

**The pattern, further down.** Service modules do not think about environments at all. They take the assembled `name` as an input and keep appending:

```hcl
variable "name" { type = string }        # e.g. acme-dev-api

module "load_balancer" {
  source = "./alb"
  name   = "${var.name}-lb"              # acme-dev-api-lb
}

resource "aws_ecs_cluster" "main" {
  name = "${var.name}-cluster"
}
```

The rule for the primary resource: a module with one obvious main resource (a `db` module's database instance) may use `var.name` unchanged; everything else takes `var.name` as a prefix plus a descriptor.

!!! tip "`random_string` beats `random_id` and `random_password` for name suffixes"
    Some resources need randomness baked into the name. `aws_secretsmanager_secret` cannot be destroyed and re-created cheaply, because a deleted secret holds its name through a recovery window — **7 to 30 days, defaulting to 30**, or `0` to force immediate deletion. (The book says "a full week" in Ch9 and points back to it here; a week is the floor, not the default — [Ch9](09-testing-refactoring.md) records the same defect.) And `aws_s3_bucket` needs randomness to avoid **S3 namespace squatting**, since bucket names are globally unique — a predictable name can be registered first in someone else's account.

    The provider's own steer, on the `random_string` page, is *"for unique ids please use `random_id`, for sensitive random values please use `random_password`"* — but for names the book's exception holds. `random_password` marks the result **sensitive**, which then poisons every name derived from it. And `random_id` is denser only in its `b64_url` form (6 bits per character), whose `-` and `_` many name fields reject; the `hex` form everyone actually interpolates carries **4 bits per character**, against roughly 5.2 for a lowercase-alphanumeric `random_string`.

    ```hcl
    resource "random_string" "suffix" {
      length  = 6
      special = false     # secret names restrict the character set
      upper   = false     # lowercase is easier to type and to grep
    }

    resource "aws_secretsmanager_secret" "main" {
      name = "${var.name}-${random_string.suffix.result}"
    }
    ```

    Put this **inside the module**, so users of the module never have to know the constraint exists.

Three caveats the section closes on:

- **Deep nesting makes long names.** Mitigate with short descriptors (`db`, not `database`) — and by not nesting deeply in the first place.
- **Don't put the resource type in the name.** An S3 bucket named `logging_bucket` is redundant; `logs` is enough, because bucket-ness is inherent to the thing.
- **You do not control third-party modules.** Where a module comes from outside the team, the scheme has to bend. Agree on shared patterns internally where you can.

### 10.1.3 Domains

Domains have the same goals as names with two differences that matter.

First, the **top-level domain must be an input**. Names are invented; domains are owned. The module cannot assume one.

Second, the components are assembled **in the opposite order**, because DNS is most-specific-first:

```hcl
locals {
  base_name   = "${local.application}-${var.environment}"                  # acme-dev
  base_domain = "${var.environment}.${local.application}.${var.domain}"    # dev.acme.example.net
}

module "api" {
  source = "./service"
  name   = "${local.base_name}-api"
  domain = "api.${local.base_domain}"                                      # api.dev.acme.example.net
}
```

A separate `dns_zone` variable carries the Route 53 zone, because **the zone and the base domain are often but not always the same** — the zone is where records get created, the domain is what they are named.

> 💭 (mine): the author's `.com`-for-public / `.net`-for-internal split is a personal convention, not a rule. The durable half is the *idea* — machine-generated internal domains are ugly by design, so keep customer-facing names on a separate, deliberately chosen domain.

## 10.2 Network management

Most modules **consume** a network: accept a VPC ID and a list of subnet IDs, pass them through. Creating one — reusably, for callers who have not told you how many availability zones they want — is where the language gets a workout.

### 10.2.1 Subnetting with CIDR

CIDR ("cider") notation combines a base address with a prefix length saying how many leading bits identify the *network*; the remainder addresses hosts or gets spent on smaller networks.

`192.168.0.0/16` reserves 16 of 32 bits, leaving 65,534 usable addresses. Take two more bits for the network and you get **four** subnets of 16,382 addresses each — every bit borrowed doubles the subnet count.

| | `/16` (whole) | `/18` (2 bits borrowed) |
| --- | --- | --- |
| Subnet mask | `255.255.0.0` | `255.255.192.0` |
| Wildcard mask | `0.0.255.255` | `0.0.63.255` |
| Networks | 1 | 4 |
| Max addresses each | 65,534 | 16,382 |

`cidrsubnet(prefix, newbits, netnum)` does the arithmetic — the original CIDR, how many bits to borrow, and which of the resulting networks you want:

```console
> cidrsubnet("192.168.0.0/16", 2, 0)
"192.168.0.0/18"
> cidrsubnet("192.168.0.0/16", 2, 1)
"192.168.64.0/18"
> cidrsubnet("192.168.0.0/16", 2, 3)
"192.168.192.0/18"
> cidrnetmask("192.168.0.0/18")
"255.255.192.0"
```

These belong to a small family of IP functions — `cidrsubnet`, `cidrsubnets`, `cidrhost` and `cidrnetmask` — that work identically on every provider, which is the point: the *resources* differ per cloud, the subnet maths does not.

### 10.2.2 Common topologies

Three questions decide the shape, and you answer them once for the organisation and then encode the answer as a module:

- **Segmentation** — a security control. Split what may be reached from the internet from what may not.
- **High availability** — spread across Availability Zones (AWS/Azure) or Regions (GCP). Three locations is the usual standard.
- **Size** — enough room to grow, without burning address space.

**Two-segment** is the common case: a public subnet whose resources get public IPs (load balancers, the NAT service) and a private subnet that does not. Private-to-internet traffic egresses through NAT on the public side; internet-to-private is simply not routable. In a three-tier app, the load balancer is public and the API container, database and cache are private.

**Three-segment** adds an **isolated** subnet with no internet path at all, in or out — bridges into it are created explicitly, service by service. The reason to pay for that is extremely sensitive data.

!!! note "Segmentation is one layer, not the layer"
    The chapter's own NOTE, and worth keeping: network segmentation does not replace security groups or host firewalls on each service. It is the outer ring, not the only one.

### 10.2.3 Location module

The build order is bottom-up: get the per-AZ submodule working, then wrap it. Both submodules take **the same inputs and expose the same outputs**, which is the design decision the whole thing rests on — the parent can swap between them freely.

**`az_2` — public + private.** One bit splits the block in half:

```hcl
locals {
  private_subnet_cidr_block = cidrsubnet(var.cidr_block, 1, 0)
  public_subnet_cidr_block  = cidrsubnet(var.cidr_block, 1, 1)
}
```

The public subnet sets `map_public_ip_on_launch = true` and carries an EIP plus `aws_nat_gateway`. The private subnet leaves that flag off and gets a route table with a catch-all `0.0.0.0/0` route pointing at the NAT gateway — outbound yes, inbound no. Both subnets are tagged `Network = "Public"` / `"Private"` so tools outside Terraform can find them.

!!! danger "⚠️ `map_public_ip_on_launch` is not what makes a subnet public — and the chapter never builds the thing that does"
    The chapter's annotation on that line reads "This is the field that makes this a public subnet". AWS says otherwise, in the VPC user guide's own words: *"The subnet type is determined by how you configure routing for your subnets"*, and a **public subnet** is one with *"a direct route to an internet gateway"*. Auto-assigning a public IPv4 address is a separate subnet setting. A subnet with public IPs and no internet-gateway route is not public; it is a subnet full of instances holding addresses that route nowhere.

    That would be a wording quibble if the internet gateway showed up later. It does not. **`aws_internet_gateway` appears nowhere in Chapter 10** — the submodules build only a private route table, the parent module (Listing 10.8) creates `aws_vpc`, the AZ data source, the two module calls and outputs, and nothing associates a route table with the public subnet at all. So the public subnet inherits the VPC's main route table, which is local-only; the NAT gateway sitting in it has no path out; and the private subnets routing through that NAT gateway have no internet access either.

    The §10.2.3 NOTE says the internet gateway "is the responsibility of the high-level module that we'll be creating in the next section" — the next section does not create it. Treat this module as a subnetting exercise, not a working network: to run it you need an `aws_internet_gateway`, a public route table with `0.0.0.0/0` pointing at it, and an association per public subnet.

**`az_3` — plus isolated.** Thirds are not a thing you can subnet into, since every split is a power of two. The trick avoids wasting a quarter of the block:

```hcl
locals {
  private_subnet_cidr_block  = cidrsubnet(var.cidr_block, 1, 0)              # half → private
  intermediary_block         = cidrsubnet(var.cidr_block, 1, 1)              # half → split again
  public_subnet_cidr_block   = cidrsubnet(local.intermediary_block, 1, 0)    # quarter → public
  isolated_subnet_cidr_block = cidrsubnet(local.intermediary_block, 1, 1)    # quarter → isolated
}
```

Private gets the big half because it holds the most work. The isolated subnet has no NAT gateway and no route out, which is the entire difference between it and the private one.

!!! note "These submodules are not meant to be called directly"
    Called on their own they are incomplete — in AWS nothing reaches the internet until an internet gateway exists, and that belongs to the parent module. This is a general shape for layered modules: the lower layer is allowed to be unusable alone as long as the layer above completes it.

### 10.2.4 High-level module

The parent's job is to turn "how many AZs do you want?" into subnets, and to let the same code serve a cheap dev environment and a highly available production one.

```hcl
variable "availability_zones" {
  type = number
  validation {
    condition     = var.availability_zones > 0 && var.availability_zones <= 4
    error_message = "The number of availability zones must be at least 1 and no more than 4."
  }
}

locals {
  # 1 AZ → no split at all; 2 → 1 bit; 3 or 4 → 2 bits.
  subnet_bits  = var.availability_zones == 1 ? 0 : (var.availability_zones > 2 ? 2 : 1)
  subnet_count = pow(2, local.subnet_bits)                    # pow(2, 0) = 1

  spare_subnet_cidr_blocks = [
    for i in range(var.availability_zones, local.subnet_count)
    : cidrsubnet(var.cidr_block, local.subnet_bits, i)
  ]
}
```

Three techniques worth naming:

- **Borrowed bits are computed, not asked for.** The user says "three zones"; the module works out that three zones need two bits and therefore four networks.
- **Leftovers are returned, not hidden.** Ask for 3 and you get 4 networks; the unused one comes back as `spare_subnet_cidr_blocks` via a `for` over `range()`, so the caller can decide what to do with it. Swallowing spare address space silently is how estates run out of room. (That is the intent. See the defect below for what the printed code does instead.)
- **`count` as a binary toggle** picks the topology — the Ch4 technique, used here on modules:

```hcl
module "two_tier_subnets" {
  source            = "./modules/az_2"
  count             = var.enable_isolated_subnet ? local.subnet_count : 0
  availability_zone = data.aws_availability_zones.available.names[count.index]
  vpc_id            = aws_vpc.main.id
  cidr_block        = cidrsubnet(var.cidr_block, local.subnet_bits, count.index)
}
```

The `aws_availability_zones` data source with `state = "available"` supplies the zone names, so an unavailable zone is never selected.

!!! danger "⚠️ The count is `subnet_count`, so asking for three zones builds four"
    Both module blocks take `count = … ? local.subnet_count : 0`, and `subnet_count` is `pow(2, subnet_bits)` — the number of networks the CIDR was **divided into**, not the number of zones the user asked for. The two only agree at 1, 2 and 4.

    Evaluated on Terraform 1.15.8 with the chapter's own expressions:

    | `availability_zones` | `subnet_bits` | Modules created | Reported spare | Overlap |
    | --- | --- | --- | --- | --- |
    | 1 | 0 | 1 | — | — |
    | 2 | 1 | 2 | — | — |
    | **3** | 2 | **4** | `192.168.192.0/18` | **`192.168.192.0/18`** |
    | 4 | 2 | 4 | — | — |

    At three zones the module builds a **fourth** location — an extra set of subnets, a fourth NAT gateway, a fourth bill — and then reports the CIDR that fourth location is using as *spare*, so the same range is simultaneously allocated and advertised as free. The fix is `count = var.availability_zones`; `subnet_count` should only ever feed `cidrsubnet`'s `newbits` and the spare-block range.

    Worth noting where it bites: three is the value the chapter itself calls the standard for high availability, and it is the only value in the module's own validated 1–4 range that is wrong.

!!! danger "⚠️ Listing 10.8's two toggles are inverted, and the module returns nothing"
    As printed, `two_tier_subnets` takes `count = var.enable_isolated_subnet ? local.subnet_count : 0` and `three_tier_subnets` takes `count = var.enable_isolated_subnet ? 0 : local.subnet_count`. So **asking for an isolated subnet builds the two-tier module**, which has no isolated subnet — while the `local` a page later selects `module.three_tier_subnets` when the same variable is true. The code contradicts itself; no annotation is needed to see it, since only `az_3` has an isolated subnet.

    Reproduced on **Terraform 1.15.8** and **OpenTofu 1.12.5** with stub submodules, and the two failure modes are not equally kind:

    | `enable_isolated_subnet` | Result |
    | --- | --- |
    | `true` | **Error:** `This object does not have an attribute named "isolated_subnet_id"` — the selected branch is the empty list, which unification typed as the *az_2* shape |
    | `false` | **No error.** Subnets are created and every output is `[]` — the caller gets an empty `private_subnet_ids` and never learns why |

    Swapping the two `count` expressions fixes both branches; with that one change the outputs populate correctly on both engines, so **the pattern is sound and only the toggle direction is wrong**.

    The silent branch is the interesting one, and it generalises past this listing: `module.x` with `count = 0` is an **empty tuple**, so a ternary between a populated module list and an empty one takes its element type from whichever branch has instances. Select the empty branch and you get a well-typed empty list rather than a type error. That is why a splat over the wrong module yields `[]` instead of complaining — and why an integration test asserting *"outputs are non-empty"* catches this and `terraform validate` does not.

Outputs then hide the switch entirely — a local picks whichever module is live, and splat collects across its instances:

```hcl
locals {
  subnet_module = var.enable_isolated_subnet ? module.three_tier_subnets : module.two_tier_subnets
}

output "private_subnet_ids" {
  value = local.subnet_module[*].private_subnet_id
}

output "isolated_subnet_ids" {
  # az_2 has no isolated subnet, so this one cannot be blind.
  value = var.enable_isolated_subnet ? local.subnet_module[*].isolated_subnet_id : []
}
```

!!! tip "Why `count` and not `for_each` here"
    The book's stated reason, and it is the important one: `count.index` works against values that are **not known at plan time**, whereas `for_each` keys must be. The zone names come from a data source and the CIDRs are computed from them, so `for_each` would risk the "keys must be known" error on a first plan. The Ch4 caveat still applies — `count` reindexes on removal — but here the collection only grows or shrinks at the end.

The payoff is the caller's view: four arguments, and dev versus prod is a variable change rather than a different module.

```hcl
module "network" {
  source                 = "./top_level"
  enable_isolated_subnet = true
  availability_zones     = 3
  cidr_block             = "192.168.0.0/16"
}
```

## 10.3 Provisioners

Provisioners create files and run commands, locally or remotely, when a resource is created or destroyed.

!!! warning "The chapter opens by telling you not to use this"
    Verbatim in spirit: *using provisioners is most likely a bad idea*. They add points of failure, extend deploy time, and behave unpredictably; modules using them are less portable and harder to debug. HashiCorp's own docs say the same thing — provisioners are **a last resort**, and the recommendation is purpose-built solutions instead.

    Read §10.3.6 before writing one. Everything between here and there is how they work, not an argument that you should reach for them.

### 10.3.1 Connections

Running anything remotely needs a `connection` block, and where you put it decides its scope:

- On the **resource** — applies to every provisioner in that resource. This is the usual placement.
- Inside a **`provisioner`** — applies to that one only.

`self` refers to the resource being created, which is how you feed the machine's own address to the provisioner:

```hcl
resource "aws_instance" "direct" {
  ami           = data.aws_ami.ubuntu.id
  instance_type = "t2.micro"

  connection {
    type        = "ssh"
    user        = "ubuntu"           # depends on the AMI
    private_key = file("~/.ssh/id_rsa")
    host        = self.public_ip     # only works if Terraform can reach it
  }
}
```

!!! danger "Never commit the private key"
    The chapter's NOTE and it deserves the stronger admonition: private keys are credentials. `file("~/.ssh/id_rsa")` reads from the operator's machine, which is fine; a key checked into the module is a breach. See **A6** for the ephemeral-value path when the credential must come from a secret manager.

Two transports: **SSH** for Unix, **WinRM** for Windows. Both support a lot of routing options, including a **bastion host** and a SOCKS5 proxy, which is how a runner on the CI network reaches instances that only have private addresses:

```hcl
connection {
  type                = "ssh"
  user                = "ubuntu"
  private_key         = file("~/.ssh/id_rsa")
  host                = self.private_ip        # bastion puts us inside the network
  bastion_host        = var.bastion_host
  bastion_user        = var.bastion_user
  bastion_private_key = file("~/.ssh/id_rsa")
}
```

And the cost, stated plainly by the book: this codes a **network topology decision into the module**. Either you decide for all your users whether a bastion is used, or you thread a pile of variables through. Remote provisioners are less portable than any alternative.

A connection also does not have to point at its own resource. Any resource can carry a provisioner, including ones with nothing to log into — a DNS record can provision the machine it points at:

```hcl
resource "aws_route53_record" "resource" {
  # …
  connection {
    type        = "ssh"
    user        = "ubuntu"
    private_key = file("~/.ssh/id_rsa")
    host        = aws_instance.other.public_ip    # a different resource entirely
  }
}
```

!!! info "OpenTofu — `winrm` is deprecated and on the way out"
    OpenTofu **1.12** deprecated the `winrm` connection type for the `remote-exec` and `file` provisioners ([opentofu#3899](https://github.com/opentofu/opentofu/issues/3899)). The stated reason is ecosystem health: the Go WinRM libraries are unmaintained. It still works in 1.12 but **warns on every use**, and OpenTofu expects it to become an **error in 1.13** — which, checked against `repos/opentofu` on 2026-08-16, is still unreleased (`## 1.13.0 (Unreleased)` in the changelog, nothing tagged), so treat the removal as scheduled rather than shipped.

    The migration path is SSH: modern Windows Server ships OpenSSH. Terraform 1.15 has made no equivalent move — if you have Windows provisioning today, this is a divergence that will bite on an OpenTofu upgrade and not on a Terraform one.

### 10.3.2 Command provisioners

Two provisioners run commands, and despite doing near-identical jobs they are shaped differently.

**`remote-exec`** runs on the remote machine and needs a connection. Three ways to supply the script, **one per provisioner block**:

| Argument | Takes | Behaviour |
| --- | --- | --- |
| `script` | a path relative to the defining file | uploaded, then run |
| `scripts` | a list of paths | uploaded, run in the order given |
| `inline` | a list of command strings | no file needed; best for one-liners |

```hcl
provisioner "remote-exec" {
  inline = ["sudo apt-get update", "sudo apt-get install -y nginx"]
}

provisioner "remote-exec" {
  script = "${path.module}/scripts/install.sh"
}
```

Multiple provisioners in one resource run **in the order they are written**.

**`local-exec`** runs on the machine running Terraform, needs no connection, and takes only `command` — there is no `script` argument. Emulate one by invoking the script from the command:

```hcl
provisioner "local-exec" {
  command = "bash ${path.module}/register_instance.sh '${self.id}'"
}
```

!!! note "📌 The book's argument list is incomplete"
    Checked against [HCDocs “Provisioners”](https://developer.hashicorp.com/terraform/language/resources/provisioners/syntax) on 2026-08-16: both `local-exec` and `remote-exec` also accept **`environment`** (a map of env vars, which beats interpolating secrets into a command string), **`interpreter`** (run something other than the default shell), **`working_dir`**, and **`quiet`** (suppress echoing the command to the log). None appear in the chapter, and `environment` in particular is the difference between passing a value and printing it.

### 10.3.3 File provisioners

`file` puts content on the remote machine, from a local path or from a string:

```hcl
provisioner "file" {
  destination = "/etc/hostname"
  content     = "api.${var.domain}"       # generate the file inline
}

provisioner "file" {
  destination = "/etc/nginx/nginx.conf"
  source      = "${path.module}/nginx.conf"   # copy a local file
}

provisioner "remote-exec" {
  inline = ["sudo systemctl start nginx"]     # then restart the service
}
```

Directories can be uploaded too, but **the destination directory must already exist**. Since provisioners run in written order, a `remote-exec` before the `file` block creates it, and one after sets permissions.

!!! tip "The trailing slash on `source` changes what gets uploaded"
    The rule the chapter leaves out, read from `internal/communicator/ssh/communicator.go` (`UploadDir`): with **no** trailing slash the source directory name is created inside the destination, and **with** one the directory's *contents* are copied into the destination. So `source = "conf/"` → `destination = "/etc/nginx/"` gives `/etc/nginx/<files>`, while `source = "conf"` gives `/etc/nginx/conf/<files>`. The chapter's example uses the trailing-slash form and is therefore correct, but silently — get it wrong and you nest a directory you did not mean to.

### 10.3.4 Provisioner control

Two arguments change *when* a provisioner runs and what happens when it fails.

**`when = destroy`** flips it from create-time to destroy-time. Note the value is a **bare keyword, not a string**:

```hcl
provisioner "local-exec" {
  when    = destroy                                    # not "destroy"
  command = "bash ${path.module}/deregister_instance.sh '${self.id}'"
}
```

!!! warning "Destroy-time provisioners share the `prevent_destroy` trap"
    The configuration is what carries the instruction, so **deleting the resource block deletes the provisioner along with it** — and then nothing runs at teardown. It works for a *natural* destroy: `terraform destroy`, or a replacement Terraform decides on. It does not work as a guarantee, because the guarantee lives in the code you just removed.

> ⚠️ A second way to lose a destroy-time provisioner, which the chapter does not mention: with **`create_before_destroy = true`** on the resource, the destroy-time provisioner **does not run at all** ([[tf-meta-lifecycle]]). So the guarantee has two holes — deleting the block, and a lifecycle rule set for an unrelated reason, possibly propagated onto the resource from a dependent one.

**`on_failure`** takes `fail` (the default) or `continue`. On `fail`, Terraform errors, stops the apply, and **taints the resource** so the next plan destroys and re-creates it — which is the sharpest argument against `remote-exec`: a flaky script does not merely fail, it condemns a perfectly good server.

### 10.3.5 `terraform_data`

The "resource that does nothing" from §6.8.4. Its most common use is exactly this: hosting provisioners that do not belong to any particular resource. Before it existed the same trick used `null_resource`, and untouched examples of that are still everywhere.

What makes it a better host than a real resource:

- **`triggers_replace` takes any expression**, so the provisioner can be keyed on any attribute of any resource or data source — not just the lifecycle of the thing it happens to be attached to.
- **Multiple dependencies collapse into one run.** Several triggers together mean the script runs once when any of them changes, rather than once per resource.
- **`self` exists but is useless for connecting.** The chapter says there are "no self values we can use here", which is loose: measured on Terraform 1.15.8, a provisioner on `terraform_data` resolves `self.id` and `self.output` fine. What it cannot give you is an address, because the resource has no machine behind it — so the `connection` must name another resource explicitly.

```hcl
resource "terraform_data" "provisioners" {
  connection {
    type        = "ssh"
    user        = "ubuntu"
    private_key = file("~/.ssh/id_rsa")
    host        = aws_instance.main.public_ip     # no self here
  }

  provisioner "remote-exec" {
    script = "${path.module}/scripts/initialize.sh"
  }

  depends_on = [aws_instance.main, aws_db_instance.main]
}
```

!!! tip "Migrating off `null_resource` is a `moved` block, not a rewrite"
    Verified in both engines' built-in provider source (`internal/builtin/providers/.../resource_data.go`): moving state from `null_resource` to `terraform_data` is explicitly supported, and it is the **only** move that provider accepts. So the upgrade is a `moved` block plus deleting the `null` provider from `required_providers`, with no destroy/create of whatever the provisioner touched.

### 10.3.6 Alternatives to using provisioners

The section the chapter told you to read first. Its centre is **immutable infrastructure**: do not update running machines, replace them. The image is built and tested in advance; launch-time work is limited to configuration that genuinely cannot be baked in.

| Purpose | Do this instead |
| --- | --- |
| Install software | Pre-install it in the machine image |
| Configure a launched instance | Cloud-Init |
| Add environment-specific files | Cloud-Init writes them at launch |
| Custom shutdown sequence | A shutdown service, baked into the image or installed by Cloud-Init |
| Save machine metadata to a file | Output variables, or the `local` provider |

**Cloud-Init** is the standard mechanism (see §10.8.3 for the Terraform side). Every cloud has its own way of passing the data in, and in Terraform it is usually one argument on the resource.

Where provisioners still earn their place: platforms without Cloud-Init support — Windows being the common case — and genuine edge cases. The rule the chapter leaves you with is to always ask whether there is a better way first.

> 💭 (mine): the learning-path framing is sharper than the book's here. The alternative to a provisioner is a **handoff**, and `terraform output -json` is the seam: Terraform publishes addresses, a configuration tool consumes them as inventory, and nothing runs inside the apply. That also dodges the taint-on-failure problem in §10.3.4 entirely.

## 10.4 External provider

Provisioners run commands; they cannot **fetch data**. When a source has no provider and no data source, the `external` provider bridges the gap by shelling out to a program and reading its output back as an attribute.

!!! warning "Also a last resort, for different reasons"
    Fewer footguns than provisioners, but real cost: you own a script, and every environment that runs the configuration must be able to execute it. The provider docs add a case the book does not — **Terraform Enterprise makes no guarantee about which language runtimes exist** beyond standard shell utilities, so an external data source in a TFE-run configuration is a bet on the worker image.

### 10.4.1 The `external` data source

One data source, no resources — deliberately. This is for querying, not for managing infrastructure.

| Argument | Type | Notes |
| --- | --- | --- |
| `program` | list of strings | Command first, arguments after — the same shape as Docker's `ENTRYPOINT`/`CMD`. **Required.** |
| `query` | `map(string)` | Serialised to JSON and sent on **stdin**. Omitted means an empty JSON **object** `{}` arrives — the chapter says "an empty JSON array", which is wrong: the provider marshals a `map[string]string`, so `{}` is the only thing it can produce ([`internal/provider/data_source.go`](https://github.com/hashicorp/terraform-provider-external/blob/main/internal/provider/data_source.go), and the docs say "the program will receive an empty object as its input"). Matters if your parser type-checks its input. |
| `working_dir` | string | Defaults to the current working directory |

The program returns a JSON object of strings on stdout, which surfaces as the `result` attribute:

```hcl
data "external" "main" {
  program = ["bash", "${path.module}/script.sh"]
}

output "specific_result" {
  value = data.external.main.result["specific_key"]
}
```

!!! note "📌 The failure contract is in the docs, not the chapter"
    From the [provider docs](https://registry.terraform.io/providers/hashicorp/external/latest/docs/data-sources/external) (checked 2026-08-16): the program **must exit zero** on success. On failure it should write a human-readable message to **stderr** and exit non-zero — stdout is ignored in that case, and the stderr text is what your users will see in the Terraform error. The docs also recommend `jq` for any shell implementation, because hand-rolled JSON quoting in Bash is where these scripts break.

### 10.4.2 Wrapper program languages

A real trade, with no clean answer:

| | Bash | Python / Java / … |
| --- | --- | --- |
| Portability | Near-universal on Unix | Needs a runtime, often dependencies |
| Maintainability | Degrades fast with complexity | Libraries, structure, tests |
| JSON handling | Needs `jq` | Standard library |

The book's resolution is about **audience**, which is the right axis: an external-provider module is usually a system-specific workaround rather than something you publish, and for your own delivery orchestrator you can install whatever you like. If it *is* meant for redistribution, use Bash or do not use the external provider at all.

!!! tip "Thinking about Go? Write a provider instead"
    The chapter's own tip. If the team already knows Go, the external provider is the worse version of a real provider — see Ch12.

### 10.4.3 Writing wrapper programs

The flow is fixed regardless of language: **query JSON in on stdin → result JSON out on stdout**.

Terraform has no square-root function, so the chapter writes one. With a single argument, the query can be skipped entirely and the value passed as a command-line argument:

```bash
#!/usr/bin/env bash
a=$(bc <<<"scale=0; sqrt($1)")
echo "{\"value\":\"$a\"}"      # the result must be a JSON object, even for one value
```

```hcl
data "external" "main" {
  program = ["bash", "${path.module}/square_root.sh", "128"]
}
```

For many inputs, arguments get unwieldy and `query` earns its place. Keys are arbitrary; values come in as strings and **must go back as strings**:

```python
import json, math, sys       # standard library only, for portability

data = json.load(sys.stdin)
json.dump({k: str(math.sqrt(float(v))) for k, v in data.items()}, sys.stdout)
```

```hcl
data "external" "query" {
  program = ["python", "${path.module}/square_root.py"]
  query   = { "0" = "128", "1" = "256", "random" = "1024" }
}
```

### 10.4.4 Alternatives to external providers

Work down this list before writing a script:

- **The `http` provider** if the script is really an API call — it builds HTTP requests directly in Terraform, `curl`-style.
- **Provider-defined functions.** Since Terraform 1.8 / OpenTofu 1.7 providers ship their own functions; the thing you were about to shell out for may already exist as `provider::x::fn()`.
- **A data source you missed** in a provider you already use.
- **Your own provider** — appealing if the team knows Go, overkill otherwise (Ch12).

## 10.5 Local provider

Provisioners write files on remote machines. The `local` provider handles the machine Terraform is running on.

### 10.5.1 Functions

`local` was one of the first providers to use provider-defined functions, and it defines exactly one useful thing: `direxists`. `fileexists` has always been built in; there was never a directory equivalent.

```hcl
locals {
  file_exists = fileexists("${path.module}/example.txt")
  dir_exists  = provider::local::direxists("${path.module}/scripts/")
}
```

!!! note "📌 Correction — OpenTofu had provider functions in 1.7, not 1.8"
    The chapter's NOTE says the capability arrived in "Terraform and OpenTofu 1.8.0". Terraform 1.8 is right; **OpenTofu shipped it in 1.7.0** ([opentofu#1439](https://github.com/opentofu/opentofu/pull/1439), confirmed in that release's changelog in `repos/opentofu`). OpenTofu was ahead here, not level.

    The `local` provider's own [`direxists` docs](https://registry.terraform.io/providers/hashicorp/local/latest/docs/functions/direxists) add two details the book omits (checked 2026-08-16): it **errors** rather than returning `false` if the path is a *file*, and unlike `fileexists` it does **not** expand `~` — pair it with `pathexpand()` if you need that.

### 10.5.2 Data sources

`local_file` and `local_sensitive_file` are the same data source twice; the sensitive variant marks the content so Terraform will not print it. Both take a single `filename`.

```hcl
data "local_file" "foo" {
  filename = "${path.module}/config.txt"
}

data "local_sensitive_file" "key" {
  filename = "${path.module}/private.key"
}
```

Why bother, when `file()` exists? Two reasons: a data source can carry **`depends_on`, conditions and provisioner dependencies**, which a function call cannot; and it exposes derived attributes:

| Attribute | Description |
| --- | --- |
| `content` | The file's contents as a UTF-8 string (sensitive in the `_sensitive_` variant) |
| `content_base64` | The contents, base64-encoded — the one to use for binary files |
| `content_base64sha256` / `content_base64sha512` | The SHA-256 / SHA-512 checksum **of the content**, base64-encoded |
| `content_sha1` / `content_sha256` / `content_sha512` / `content_md5` | The same checksums in hex |
| `id` | Hex SHA-1 of the content |

!!! note "📌 Read the `content_base64*` names carefully"
    The chapter's table glosses these as "the hash of the base64 content", which inverts the operation. Per the [provider docs](https://registry.terraform.io/providers/hashicorp/local/latest/docs/data-sources/file) (checked 2026-08-16), `content_base64sha256` is *"Base64 encoded SHA256 checksum of file content"* — hash the raw content, then base64 the digest. It is the `base64sha256()` function's output, and it is what AWS APIs that want a base64 digest (`source_code_hash`, ETag comparisons) expect. Hashing the base64 text would give a different value and break those.

If you need a checksum alongside the content — a common trigger for redeploying something — this is shorter than computing it yourself.

### 10.5.3 Resources

The same two names also exist as **resources**, which write files.

!!! danger "Local files and remote state disagree about reality"
    If Terraform does not run from the same machine every time, the file is absent on the next run and Terraform **reports drift forever**. That makes `local_file` unsuitable for most production use: CI runners are ephemeral, so a file written on one is gone by the next apply.

Where it does work is local development: generating configuration for the environment you just built. The chapter's example is a [dev-VPN module](https://github.com/tedivm/terraform-aws-dev-vpn) that stands up an AWS VPN and drops the OpenVPN client config straight into the module directory — useless in production, genuinely handy while debugging.

```hcl
resource "local_file" "main" {
  content  = "Hello World!"
  filename = "${path.module}/hello.txt"
}

resource "tls_private_key" "main" {
  algorithm = "ECDSA"
}

resource "local_sensitive_file" "key" {
  content  = tls_private_key.main.private_key_pem
  filename = "${path.module}/private_key.pem"
}
```

> ⚠️ That second pair also writes a private key **into your state file** as well as onto disk. `local_sensitive_file` hides it from output; it does not encrypt it. See **A6** and OpenTofu's state encryption in **E3**.

## 10.6 Checks and conditions

Ch9 tested modules during development. This section tests infrastructure **that is already running** — the same assertions, evaluated on every plan and apply, forever.

### 10.6.1 Preconditions and postconditions

Both live inside the `lifecycle` block, available on every resource and data source. Both take a `condition` (any boolean expression) and an `error_message`. Both **stop Terraform** when they fail, which is what makes them safeguards rather than reports. You may have as many of each as you like, one per block.

Both are evaluated **once per instance** under `count`/`for_each`, with `count.index` / `each.key` in scope, so a rule written once covers every instance with no index bookkeeping.

!!! danger "⚠️ Correction — `self` is a *postcondition* keyword, not a condition keyword"
    The chapter introduces `self` under the shared "Preconditions and postconditions" heading, as the way "to refer to the resource the condition is defined in". That is true of postconditions only, and the reason is obvious once stated: a **precondition runs before the object exists**, so there is nothing for `self` to point at.

    Settled in source rather than inferred — `internal/terraform/eval_conditions.go` binds a self reference for exactly one rule type, `addrs.ResourcePostcondition`, above the comment *"Only resource postconditions can refer to self"*. OpenTofu's `internal/tofu/eval_conditions.go` carries the same line, so this is not a divergence. HCDocs agrees by example: its `self.tags[...]` sample is a postcondition, and its precondition sample reaches for another resource's attributes instead.

    Every example the chapter actually prints is consistent with this — its `self` usage is in the postcondition on `data.aws_ami` — so the slip is in the prose, not the code.

```hcl
resource "aws_lb" "example" {
  load_balancer_type = var.type
  ip_address_type    = var.ip_address_type
  # …

  lifecycle {
    precondition {
      condition     = var.type == "application" ? true : var.ip_address_type != "dualstack-without-public-ipv4"
      error_message = "The ip_address_type can only be set to dualstack-without-public-ipv4 when the Load Balancer Type is application."
    }
  }
}
```

**Why this pattern existed.** Before Terraform 1.9, a variable `validation` block could only reference **its own variable**. Any rule spanning two variables had nowhere to live — so it moved onto a resource as a `precondition`, which could see everything. Since 1.9 the same expression is legal in `validation`:

```hcl
variable "ip_address_type" {
  type    = string
  default = "dualstack"

  validation {   # legal only on Terraform 1.9+ / OpenTofu 1.9+ — refers to another variable
    condition     = var.type == "application" ? true : var.ip_address_type != "dualstack-without-public-ipv4"
    error_message = "The ip_address_type can only be set to dualstack-without-public-ipv4 when the Load Balancer Type is application."
  }
}
```

The chapter's guidance is to prefer the variable `validation` now, because that is where a developer looks first — while keeping preconditions for rules that genuinely belong next to the resource they protect.

!!! info "OpenTofu — cross-object validation landed at the same version number, coincidentally"
    OpenTofu added references to vars, data and locals inside `validation` in **1.9.0** ([opentofu#2216](https://github.com/opentofu/opentofu/pull/2216)) — the same number as Terraform 1.9, but arrived at independently. Matching numbers here are luck, not a shared release train: the engines' minor versions have not tracked each other since the fork. Check the feature, not the number ([[feature-coverage-matrix]]).

**Postconditions** are identical in syntax but run *after* creation or update — the place to reject a result rather than an input. The chapter's example is an AMI lookup that refuses a deprecated image:

```hcl
data "aws_ami" "ubuntu" {
  # …
  lifecycle {
    postcondition {
      condition     = timecmp(timestamp(), self.deprecation_time) == -1
      error_message = "Unable to find an AMI that is not deprecated."
    }
  }
}
```

> 💡 Note the aside on `timestamp()`: a condition is one of the few safe places for it, because the value is never stored, so it cannot produce perpetual drift.

### 10.6.2 Checks

`check` blocks are top-level, and were introduced in **Terraform 1.5.0** (confirmed in that release's changelog in `repos/terraform`; OpenTofu inherited them at the fork). They exist for continuous validation of long-lived infrastructure.

Three differences from `postcondition`, and the first is the point of the feature:

| | `postcondition` | `check` |
| --- | --- | --- |
| On failure | **Stops** the run | **Warns** and continues |
| Assertions per block | One (add more blocks) | Many `assert` blocks |
| Own data sources | No | **Yes** — scoped to the check |
| `self` | Available | Not available — reference the object by address |

```hcl
check "ami_check" {
  assert {
    condition     = timecmp(timestamp(), data.aws_ami.ubuntu.deprecation_time) == -1
    error_message = "Unable to find an AMI that is not deprecated."
  }

  assert {
    condition     = data.aws_ami.ubuntu.imds_support == "v2.0"
    error_message = "Unable to find an AMI that enforces IMDSv2."
  }
}
```

**Scoped data sources** are what make checks powerful. A `data` block declared inside a `check` is visible only there, and — crucially — **its failure is a warning too**, not an error. That is what makes a live health check safe to put in a configuration:

```hcl
check "health_check" {
  data "http" "api" {
    url             = var.healthcheck_endpoint
    request_headers = { Accept = "application/json" }

    depends_on = [module.api]     # ← not optional, see below
  }

  assert {
    condition     = data.http.api.status_code >= 200 && data.http.api.status_code < 300
    error_message = "Healthcheck failed with status code ${data.http.api.status_code} and content ${data.http.api.request_body}."
  }
}
```

!!! warning "Always give a scoped data source a dependency"
    With no implicit dependency — as when the URL comes from a variable rather than a module output — the check runs on the **very first plan**, before the infrastructure it is checking exists, and reports a failure that means nothing. `depends_on` is the fix. Scoped data sources accept `depends_on` and `provider`, and no other lifecycle arguments.

Putting the whole family in order, weakest binding to strongest:

| Mechanism | Runs | On failure | Sees |
| --- | --- | --- | --- |
| Variable `validation` | Before anything | Blocks | Its own variable; other vars/locals/data on 1.9+ |
| `precondition` | Before create/update | Blocks | Everything except `self` — the object does not exist yet |
| `postcondition` | After create/update | Blocks | Everything, **plus `self`** |
| `check` | Every plan and apply | **Warns** | Everything, plus its own scoped data sources. No `self` |

> 💡 One more from source: when a check's condition cannot be evaluated yet, the assertion does not fail — Terraform emits a *"Check assertion known after apply"* warning and resolves it during the apply. Preconditions and postconditions have no such escape.

## 10.7 OpenTofu and Terraform compatibility

The chapter's own compatibility report: every example in the book was tested on both engines and ran unchanged. The honest caveat follows immediately — the relationship will evolve, and divergence is expected.

### 10.7.1 Tofu files

The mechanism that makes a module serve both engines even after they diverge. Terraform reads `.tf` and knows nothing about `.tofu`; OpenTofu reads both, and **where a `.tofu` file shares a name with a `.tf` file, the `.tofu` file wins and the `.tf` file is ignored entirely**.

```hcl
# compatibility.tf — only Terraform will read this, as long as the .tofu twin exists
locals { my_engine = "terraform" }
```

```hcl
# compatibility.tofu — OpenTofu reads this instead
locals { my_engine = "tofu" }
```

```hcl
output "engine" { value = local.my_engine }    # "terraform" or "tofu"
```

The substitution is **per file, not per block**, which is the practical constraint: the `.tofu` file must restate everything its `.tf` twin declared, not just the parts that differ. So keep the engine-specific declarations in their own small file rather than shadowing a large one.

!!! info "OpenTofu — `.tofu` arrived in 1.8.0, and the rule extends past `.tf`"
    Confirmed in the OpenTofu 1.8.0 changelog in `repos/opentofu`: *"Added support to new .tofu extensions to allow tofu-specific overrides of .tf files"* ([opentofu#1738](https://github.com/opentofu/opentofu/pull/1738)). The same shadowing applies to `.tf.json`/`.tofu.json` and to the test extensions `.tftest.hcl`/`.tofutest.hcl`.

    ⚠️ **`.tofurc` is not part of this feature**, despite being listed with it in a lot of material. It is the renamed `.terraformrc` CLI-config file and dates to the **1.6** fork baseline — see the E3 correction in the learning path.

    This is one-directional by construction: OpenTofu can hide code from Terraform, Terraform has no way to hide code from OpenTofu. A module that must exploit an OpenTofu-only feature — state encryption, provider `for_each`, dynamic `prevent_destroy` — puts it in a `.tofu` file and keeps a working `.tf` fallback for Terraform users. Divergence list in [[version-facts]]; migration mechanics in [[opentofu-migration-mechanics]].

## 10.8 When Terraform isn't appropriate

The most reusable section in the chapter. One theme runs through all four cases: **Terraform deploys; it does not package.**

### 10.8.1 Kubernetes

The split is clean:

- **Terraform for the platform.** A module per cloud that builds the cluster, its controllers, and the integrations between the cluster and the rest of the cloud account. Platform engineers get all the IaC benefits.
- **Kubernetes tools for what runs on it.** `kubectl` in CI, or Helm / ArgoCD for anything complex.

Using the Kubernetes provider to manage deployments technically works and is a bad idea, because it stacks **an abstraction on an abstraction** — Terraform over Kubernetes over the cloud. Debugging then means unwinding all of it to find which layer is lying.

### 10.8.2 Container image building

Two reasons not to build images inside the apply:

- **Time.** Builds are slow, and it compounds — more dependencies, more containers, longer every deploy.
- **Coupling.** Container and infrastructure are loosely coupled by nature. Build them together and you tighten that into a hard link, so routine infrastructure work — more replicas, a different log destination, a bigger database — rebuilds and redeploys an application that did not change.

Give images their own CI/CD, and let Terraform **refer to a version**:

```hcl
variable "api_service_version" {
  type    = string
  default = "latest"
}

module "api_service" {
  source = "./modules/api_service"
  image  = "gcr.io/my-project/api-service:${var.api_service_version}"
}
```

Upgrades become a Terraform change tracked in Git, and rollback is reverting the commit.

If a **separate deployment tool** owns the version instead — anything doing progressive delivery — tell Terraform to stop caring:

```hcl
resource "aws_ecs_task_definition" "this" {
  # …
  lifecycle {
    ignore_changes = [container_definitions]   # the version is now owned elsewhere
  }
}
```

> ⚠️ The trade in that `ignore_changes`: the version pinned in the config is now only the *initial* value, and Terraform will never update it again. The variable stays in the code looking authoritative while the truth lives in the deployment tool.

### 10.8.3 Machine image building

Machines need software **installed** and **configured**, and the second is the easy half.

**Configuration → Cloud-Init.** Nearly every cloud supports it, and the `cloudinit_config` data source renders it from Terraform:

```hcl
data "cloudinit_config" "node" {
  part {
    filename     = "cloud-config.yml"
    content_type = "text/cloud-config"
    content = yamlencode({                # object → YAML, controlled from Terraform
      users = {
        admin = { ssh_authorized_keys = ["ssh-rsa AAAAB3NzaC1yc2EAAAADAQABAAABAQC5"] }
      }
    })
  }

  part {
    filename     = "init.sh"
    content_type = "text/x-shellscript"
    content      = file("${path.module}/init.sh")
  }
}

resource "aws_instance" "node" {
  ami           = data.aws_ami.ubuntu.id
  instance_type = "t2.micro"
  user_data     = data.cloudinit_config.node.rendered
}
```

`yamlencode` is the useful part — the config is a Terraform object, so it can be built from variables and resource attributes instead of being a static blob. Multiple `part` blocks are allowed, though resources cap how large the whole payload may be.

!!! warning "⚠️ Listing 10.40 wires `rendered` to the wrong argument"
    The example above is the chapter's, and it does not survive a check against the two providers involved (both checked 2026-08-16).

    `cloudinit_config` defaults **`gzip = true`** and **`base64_encode = true`**, so `rendered` is gzip-compressed, base64-encoded output unless you turn those off — the provider's own example sets both to `false` explicitly. And the AWS provider says of `aws_instance.user_data`: *"Do not pass gzip-compressed data via this argument; see `user_data_base64` instead"*, with `user_data_base64` documented for exactly this case, since *"gzip-encoded user data must be base64-encoded and passed via this argument to avoid corruption"*.

    So either pair `rendered` with **`user_data_base64`** and keep the defaults, or set `gzip = false` and `base64_encode = false` and keep `user_data`. The chapter does neither.

**Installation → Packer.** Bake the software into an image ahead of time. Prebuilt images are easier to test and much faster to launch, which is the same immutable-infrastructure argument from §10.3.6 arriving from the other direction.

### 10.8.4 Artifact management

The generalisation: anything you can push to a registry — containers, machine images, libraries, compiled binaries — is **integration's** job, not deployment's. Terraform's role is to consume artifacts that already exist. Once you see it, the previous two sections stop being separate rules.

## Summary

- **Names should generate themselves.** Unique, readable, identifiable, sortable; assembled hierarchically from an application name plus environment, with each module appending a descriptor to the name it was handed. Domains are the same idea assembled in the opposite order, with the top-level domain as an input because you have to own it.
- **Resource-specific naming constraints belong inside the module.** A `random_string` suffix for `aws_secretsmanager_secret` and `aws_s3_bucket` is the module author's problem, not the user's.
- **A reusable network module is mostly arithmetic.** `cidrsubnet` splits by borrowed bits; splitting a half again is how you get "thirds" without waste; the number of AZs drives the bit count; leftovers get returned as an output rather than swallowed.
- **Identical interfaces make topologies swappable.** Two submodules with the same inputs and outputs, selected with `count` as a binary toggle and collapsed behind a `local` plus splat, and the caller never sees the switch.
- **Read §10.2's code as a design sketch, not a module to run.** Three defects, all measured: inverted toggles, a `count` that builds four locations for three zones, and a missing internet gateway. The *techniques* are sound and worth stealing; the listing is not.
- **Provisioners are a last resort, and the failure mode is the reason.** A failed provisioner taints a healthy resource; the connection block codes network topology into the module; `when = destroy` disappears with the code that declares it. Reach for immutable images and Cloud-Init instead, and treat `terraform output -json` as the handoff to a configuration tool.
- **The external provider is for data, not for actions** — JSON on stdin, JSON on stdout, exit zero or explain yourself on stderr. Bash for anything redistributable; if you were going to write it in Go, write a provider instead.
- **The `local` provider is a development tool.** The data sources are worth it for the hashes and for `depends_on`; the resources report drift forever anywhere state outlives the filesystem.
- **Conditions block, checks warn.** Variable `validation` for inputs (cross-variable since 1.9), `precondition`/`postcondition` where the rule belongs to the resource, and `check` with scoped data sources for continuous health — with `depends_on` so the first plan does not report a failure that means nothing.
- **`.tofu` files let one module serve both engines**, per file rather than per block, and only in the OpenTofu direction.
- **Terraform deploys; it does not package.** Kubernetes manifests, container images, machine images and artifacts all belong to integration — Terraform consumes the results.
