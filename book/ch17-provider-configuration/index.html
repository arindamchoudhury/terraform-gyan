Chapter 17 — Provider configuration in depth¶

Learning outcomes¶

By the end you can:

  • Say what a provider configuration is: a global, root-module-only object that resources are bound to statically, and a running process on the other end of a gRPC connection.
  • Give a provider more than one configuration with alias, and recognise the implied empty default that appears the moment you alias every block.
  • Choose a configuration with provider on a resource and with the providers map on a module, and explain why one is singular and the other is plural.
  • Deploy the same resource to two regions two ways: aliased providers, and the AWS provider's per-resource region argument. Migrate between them with an empty plan.
  • Cross an account boundary with assume_role, and name both halves of the permission that makes it work.
  • State why a reusable module must contain no provider block, using the lifecycle reason rather than the count one.
  • Pin providers where pinning belongs, read a constraint intersection, and say when terraform init needs -upgrade.
  • Explain what a provider configuration costs, and when an alias is the wrong answer.
  • Use OpenTofu's provider for_each, and structure it so a retirement can actually be destroyed.

1. One provider block is one region and one account¶

Every worked configuration in this book so far has had exactly one provider "aws" block, and that block is where three things were quietly decided: which region resources land in, which account they land in, and which credentials do the landing. Every one of those blocks set a region and nothing else, so the account and the credentials came from the provider's default credential lookup rather than from the configuration.

provider "aws" {
  region = "us-east-1"
}

Chapter 5 put a second, aliased block on the page and deferred its mechanics to this chapter.

provider "aws" {                 # second config, tagged with an alias
  alias  = "eu"
  region = "eu-west-1"
}

Nothing has needed to change any of those three mid-configuration.

Real work does. Four cases, and none of them is exotic:

  • A read replica or a backup bucket has to sit in a different region from the thing it protects. Putting both in the same region defeats the point.
  • CloudFront will only attach a TLS certificate that lives in us-east-1, no matter where the rest of the stack runs. That is ACM's requirement as CloudFront states it, not a Terraform one.
  • Account-wide detective controls such as GuardDuty are meant to run in every supported region, not just the ones you deploy to. AWS recommends enabling it everywhere precisely so that it reports activity in the regions you never use.
  • Staging and production live in separate accounts, because that is the boundary that actually stops a mistake in one from reaching the other.

The mechanism for all four is the same, and it is small: a provider can have more than one configuration, and every resource is bound to exactly one of them. Setting that up takes one argument. The rest of this chapter is about the consequences, which are where the difficulty lives. Provider configurations are global rather than scoped, where nearly everything else in the language belongs to the module that declares it. They must outlive every object they created, and the binding between a resource and its configuration is static, which quietly rules out some things you will reach for.

There is also a newer answer that did not exist when most of the advice about this topic was written. Since AWS provider 6.0, most AWS resources take a region argument of their own, and a great many configurations that used to need aliases no longer do. In 6.61.0 the provider ships that argument on 1,526 of its 1,709 managed resource types. Section 5 measures both routes side by side.

2. What a provider configuration actually is¶

Chapter 2 and Chapter 5 established the split: required_providers declares a provider so Terraform can install it, and a provider block configures it.

# terraform.tf — DECLARE: which provider, which version
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"
    }
  }
  required_version = ">= 1.2"
}

# providers.tf — CONFIGURE: how to connect
provider "aws" {
  region = "us-east-1"
}

This chapter needs four more facts about the second half.

It is global, and it lives in the root module¶

Most things in Terraform are scoped. A variable belongs to a module. An output belongs to a module. A resource address is relative to the module that declares it. Provider configurations break that pattern. HashiCorp's Providers Within Modules page states it directly:

"Provider configurations, unlike most other concepts in Terraform, are global to an entire Terraform configuration and can be shared across module boundaries. Provider configurations can be defined only in a root Terraform module."

Two rules:

  • Definitions go in the root module only.
  • What they define can be shared across the whole tree.

The second rule is a capability rather than a default. A child module automatically receives the default configuration and nothing else, so an aliased one reaches it only when the caller passes it in. Section 8 covers that boundary.

“Root module” means the directory you run the command in

The root module is wherever terraform apply is invoked, or wherever -chdir sends it. It is not a special file or a special name. A module becomes a child module when something calls it with a module block. The same directory can be a root module on Monday and a child module on Tuesday, and the provider rule follows that role rather than the files. This is why a no-code module in HCP Terraform is allowed to declare providers: HCP generates a workspace where that module is the root.

It is a process¶

Chapter 5 described the plugin model. It matters again here for a reason that is purely operational. Terraform core is one binary, each provider is a separate binary, and they talk over gRPC on a local connection. A provider configuration is what gets a plugin process started and handed its settings.

So the number of provider configurations is not a stylistic detail. It is a count of processes, each opening its own connections to a remote API. The unit is the configuration rather than the block, and the two come apart in both directions:

  • A process with no block. A configuration you never wrote still starts one the moment something uses it. That is the implied empty default, which the last part of this section covers.
  • A block with no process. A provider block nothing refers to is pruned out of the graph before it is ever configured. The trace log states it outright: pruning unused provider["registry.terraform.io/hashicorp/aws"].unused.

Section 10 puts a measured number on what happens when that count gets large.

Its arguments are evaluated early¶

A provider block may use expressions, but only over values that are known before anything is applied. Input variables are fine, and so is a local, as long as what the local itself resolves to is known that early. A computed attribute of a resource is not. Terraform has to configure a provider before it can create anything with it, so a provider argument that depends on a resource's output is a circular request.

“Early” here means before apply, not during init

Terraform uses early evaluation for something narrower: the configuration loading that happens during terraform init, where a module's source and version are resolved. A variable used in either of those must carry const = true, which is Chapter 13's subject. Provider arguments are not resolved that early. They are evaluated when Terraform builds the plan, by which point every root variable is known, so const is not required on a variable a provider block reads. Adding it costs something: a const variable with no default has to be supplied to init as well as to plan.

provider "aws" {
  region = var.region        # fine: a variable is known at plan time
}

provider "kubernetes" {
  host = aws_eks_cluster.main.endpoint   # a trap, even where it appears to work
}

The second shape does sometimes work, which is worse than if it never did. The Kubernetes provider's own documentation says not to do it: interpolating credentials from resources created in the same module "will lead to intermittent and unpredictable errors which are hard to debug and diagnose."

labs/chapter17/section2/early-eval/ reproduces the intermittency locally, with random standing in for EKS. The dependency is the same shape as the Kubernetes one, and it runs without a cluster:

resource "random_shuffle" "pick" {
  input        = ["us-east-1", "us-west-2"]
  result_count = 1
}

provider "aws" {                                # line 27
  region     = random_shuffle.pick.result[0]
  access_key = "test"
  secret_key = "test"
}

resource "aws_iam_role" "r" {
  name               = "ch17-early-eval"
  assume_role_policy = jsonencode({ Version = "2012-10-17", Statement = [] })
}

terraform validate reports Success! The configuration is valid. From clean state the plan then fails, and the error blames the wrong thing:

Error: invalid AWS Region: 

  with provider["registry.terraform.io/hashicorp/aws"],
  on main.tf line 27, in provider "aws":
  27: provider "aws" {

The value arrived empty, so the complaint is about the region rather than about the reference that produced it.

The reference resolves against state rather than against the file, so whether the identical configuration works is only a question of whether the dependency's attribute is already known when the plan is built:

  • Not in state yet. Unknown, and the provider is configured with an empty string. This is the first run, and it is also every fresh clone, new workspace and empty CI runner after it.
  • In state, unchanged. A plain known string. Apply that one resource on its own and the same file plans clean: Plan: 1 to add, 0 to change, 0 to destroy. That clean run is what makes the shape look supportable.
  • In state, but being replaced. Unknown again. Add -replace random_shuffle.pick to that clean plan and the identical error returns on a workspace that has been working: Plan: 1 to add, 0 to change, 1 to destroy. followed by Error: invalid AWS Region:.

The third case is the one that costs a day. Nothing about the configuration changed, the workspace has applied successfully for months, and a forced replacement upstream is enough to make the provider unconfigurable again.

The supported answer needs no paid product. Split the work into two configurations applied in sequence, and let the second read the first's outputs through a terraform_remote_state data source or a provider data source, which is Chapter 15's subject. Two smaller open-source moves shrink the problem without removing it:

  • Take the credentials out of the interpolation. The Kubernetes provider's exec block calls a helper such as aws eks get-token while the provider is being configured, so no token has to come from a resource attribute. Its documentation warns against combining exec with token or client_certificate, because "there is no guarantee about which credential will actually be used." The host still has to come from somewhere, so this halves the problem rather than ending it.
  • Sequence inside one configuration with -target. This section's own lab does exactly that to get past the failing plan. It is recovery, not a design, and Chapter 3 says why.

What open source does not have is the deferral itself. HCP Terraform's Stacks defer provider initialisation until such values exist, which is a real fix on a different configuration surface rather than a switch you turn on. Chapter 27 covers Stacks. Terraform's own deferral machinery is compiled in but closed off: terraform plan -allow-deferral on the released 1.15.8 binary answers The -allow-deferral flag is only valid in experimental builds of Terraform.

An orchestrator does not close that gap, and it is worth knowing why before reaching for one. Terragrunt automates the split rather than removing it: dependency blocks put its units in a DAG, and its documentation is explicit that run --all apply "will not attempt to deploy the config until all the units referenced in dependency blocks have been applied". A downstream unit therefore reads outputs that have already been applied, which is the two-configuration answer with the sequencing done for you. What it cannot do is plan a unit whose dependency does not exist yet, so it offers mock_outputs — placeholder values — and warns that you "might not want to use the defaults for a plan operation because the plan doesn't give you any indication of what is actually going to be created". For a provider argument that means planning against a fabricated endpoint. Terrakube, the open-source HCP Terraform alternative, is the platform half rather than this one: its templates sequence steps within a single workspace, and its documentation describes no ordering between workspaces. Terragrunt as an orchestrator is a topic of its own, and this book reaches it under large-scale state and repository architecture rather than here.

OpenTofu — -exclude, and a deferral that was deliberately withdrawn

OpenTofu decided against provider deferral rather than lacking it. Release 1.11.4: "Providers are not configured anymore with DeferralAllowed capability of OpenTofu since having that created unwanted behaviour from some providers." The capability still exists in the plugin protocol; what changed is that OpenTofu stopped advertising it. A separate note, quoted below, gives the underlying complaint: providers that report they cannot plan because of unknown values, when planning would in fact have succeeded.

What it offers instead is -exclude, the inverse of -target: name the resources to leave out rather than the ones to build. Measured on OpenTofu 1.12.5, tofu plan -help documents -exclude=resource; on Terraform 1.15.8 the flag does not exist, in plan -help or in the source. OpenTofu withdrew its automatic suggestion of the flag in 1.11.2 while keeping the technique: "Using -exclude still a valid workaround for these problems even though OpenTofu cannot accurately detect when it's useful to make that suggestion." The same release made planning with unknown provider configuration work again for the helm and kubernetes providers, "as long as the configuration is carefully written to avoid the plan phase actually depending on those values."

There is always a default configuration¶

If you never write a provider "random" block, Terraform does not conclude that you have no random provider. It assumes an empty default configuration and carries on. For random that is correct, because there is nothing to configure. For AWS the empty default sets nothing, which is not the same as having nothing: the provider still runs its own region and credential lookup. labs/chapter17/section2/env-default/ has no provider block at all, so what happens there is decided entirely by the environment. Supply AWS_REGION, credentials and the emulator endpoint as environment variables and terraform apply creates an aws_iam_role. Run terraform plan over the identical files with an empty environment and it fails on Invalid provider configuration and No valid credential sources found, cited at <empty> line 0, which is the diagnostic Section 3 walks through. State makes no difference to that: the plan fails the same way before the role exists and after it has been applied. So an empty default fails when the lookup behind it comes up empty, not merely because you did not write the block.

That assumption is the root of the trap in the next section, so it is worth stating in its strongest form. A provider you use always has a default configuration. The only question is whether you wrote it.

3. alias, and the default configuration you did not write¶

A second configuration for the same provider is one argument:

provider "aws" {
  region = "us-east-1"
}

provider "aws" {
  alias  = "west"
  region = "us-west-2"
}

The block without an alias is the default configuration. Any resource, data source or module that does not name a provider gets it. The aliased one is referenced as aws.west, and it is used only where something asks for it by name.

That is the whole syntax. The trap is in what "the block without an alias" means when there isn't one.

Alias every block and the default stops being yours¶

If every provider block for a provider carries an alias, Terraform does not promote one of them. It invents an implied empty default configuration, and every resource that never named a provider binds to that instead. So nothing is lost in the sense of going missing. The role of default is reassigned, from the block you wrote to a configuration that holds nothing, and the resources that never named a provider follow the role rather than the block.

This is measurable, and the diagnostic is more interesting than the rule. The configuration is committed at labs/chapter17/section3/implied-default/. Two aliased blocks, one bucket that names an alias, one that does not:

provider "aws" {
  alias  = "east"
  region = "us-east-1"
  # …emulator endpoints and dummy credentials…
}

provider "aws" {
  alias  = "west"
  region = "us-west-2"
  # …emulator endpoints and dummy credentials…
}

resource "aws_s3_bucket" "east" {
  provider = aws.east
  bucket   = "ch17-implied-east"
}

# No provider argument. Not east, not west: the implied empty default.
resource "aws_s3_bucket" "orphan" {
  bucket = "ch17-implied-orphan"
}

terraform plan                         # one bucket plans, the other cannot

Measured on Terraform 1.15.8 with AWS provider 6.61.0:

Plan: 1 to add, 0 to change, 0 to destroy.

Error: Invalid provider configuration

Provider "registry.terraform.io/hashicorp/aws" requires explicit
configuration. Add a provider block to the root module and configure the
provider's required arguments as described in the provider documentation.


Error: No valid credential sources found

  with provider["registry.terraform.io/hashicorp/aws"],
  on <empty> line 0:
  (source code not available)

Three things in that output are worth slowing down for.

Plan: 1 to add comes before the errors. The east bucket planned perfectly well. Only the resource bound to the invented default failed, which is what makes this trap survive review: adding an alias breaks the blocks you were not looking at.

The source position reads on <empty> line 0, with (source code not available) under it. Terraform is pointing at a configuration that exists in its own model and in no file you wrote. That line is the clearest possible statement of what an implied default is.

And the failure is lazy. The empty default was created either way. It only produced an error because a resource reached for it.

There is no switch to turn it off¶

No flag, argument, or setting suppresses the implied default. The transformer that creates it takes no such input: it walks the objects that consume a provider, and the one case it skips is a provider that already has an explicit default configuration in the root module. Since the error fires on use rather than on creation, an empty default that nothing binds to is inert, and the lever you actually have is binding.

Two ways to pull it, and they are not equally good.

Keep one unaliased block. This is what the docs prescribe. The default configuration still exists, and it is yours rather than empty. Appending exactly that block to the lab file above turns the plan into Plan: 2 to add, 0 to change, 0 to destroy.

Name a provider on everything. If every resource, data, import and module block sets provider or providers, nothing reaches for the default. This is airtight while it holds and fragile in a team, because the next block someone adds without a provider argument regresses silently and only surfaces at plan.

providers = {} on a module block is not a kill switch

It is tempting to read an empty or partial providers map as "this child gets nothing except what I listed". It does not work that way. The map overrides inheritance one provider at a time, for the entries you write, and changes nothing about the rest:

  • No providers argument. The child inherits every default configuration the root has.
  • providers = {}. Identical to writing nothing. Measured on Terraform 1.15.8: a child whose resource names no provider applies through the root's inherited default, with no warning.
  • A partial map, such as { aws.replica = aws.west }. The entry you wrote is remapped; every provider you did not name still inherits. Section 8 measures this one, and the two buckets land in different regions to prove it.

The exception that makes the map necessary at all is the aliased configuration, which is never inherited under any of the three.

4. Choosing a configuration: provider singular, providers plural¶

Two meta-arguments select a configuration, and the difference between them is not arbitrary.

Block Argument Value Why
resource, data, import provider one reference: aws.west a resource is created in exactly one place by exactly one configuration
module providers a map: { aws = aws.west } a module may hold many resources using many providers
Stacks component, removed providers a map same reason, different configuration surface

Both sides of the map are unquoted references, not strings. A default configuration is written as the provider's bare local name (aws), and an alternate as <PROVIDER>.<ALIAS> (aws.west). The same applies to the singular provider argument.

One docs page quotes the value, and it is wrong

The import block reference writes provider = "<provider>.<alias>" in its specification table, with quotes. A quoted value is a string, and a provider selection is a reference. The worked example lower down the same page writes it unquoted, as provider = aws.east. Copy the example.

The map is a remap, not an injection¶

This is the part worth memorising, because the obvious reading is wrong. In providers = { aws = aws.usw2 }:

  • the key aws is a configuration name as used inside the child module;
  • the value aws.usw2 is a configuration name in the calling module.

So the argument does not hand the child an extra provider. It rewrites what the child's own aws means. The module keeps declaring plain aws_s3_bucket resources with no provider argument, and the caller decides which region or account those land in.

That is the whole reason the argument exists: it retargets a module without editing it. The same module source, called twice with different maps, produces two different deployments.

Which way round the map goes

Every reader gets this backwards once. The mnemonic that sticks: the key is the child's word, the value is your word. A providers map is a translation table you hand across the boundary, so the left-hand side is written in the language spoken on the other side.

5. Two regions, two ways¶

The milestone for this topic is deploying the same resource to two regions from one configuration. There are two ways to do it now, and the newer one did not exist when most of the writing about this topic was done.

Way one: aliased providers¶

The classic route. One default configuration, one aliased configuration, and a provider argument on anything that must leave the default region. The configuration is at labs/chapter17/section5/two-region/:

provider "aws" {
  region = "us-east-2"
}

provider "aws" {
  alias  = "west"
  region = "us-west-2"
}

resource "aws_s3_bucket" "east" {
  bucket = "ch17-alias-east"
}

resource "aws_s3_bucket" "west" {
  provider = aws.west
  bucket   = "ch17-alias-west"
}

data "aws_region" "east" {}

data "aws_region" "west" {
  provider = aws.west
}

output "regions" {
  value = {
    east = data.aws_region.east.region
    west = data.aws_region.west.region
  }
}

terraform apply -auto-approve                                 # two buckets
awslocal s3api get-bucket-location --bucket ch17-alias-east   # where did they land
awslocal s3api get-bucket-location --bucket ch17-alias-west

Measured on 1.15.8 with provider 6.61.0:

Apply complete! Resources: 2 added, 0 changed, 0 destroyed.

Outputs:

regions = {
  "east" = "us-east-2"
  "west" = "us-west-2"
}
Bucket LocationConstraint
ch17-alias-east "us-east-2"
ch17-alias-west "us-west-2"

LocationConstraint is S3's own record of which region a bucket lives in, and nothing Terraform writes. The provider sets it once, as a parameter of the CreateBucket call it makes through whichever configuration the resource is bound to, and get-bucket-location reads it back. That is what makes it the right check here. Terraform state would only tell you what Terraform sent; this answer comes from the service that stored the bucket, so it settles which provider configuration actually did the work.

Two values, two regions, neither of them empty. That is the whole check: if provider = aws.west were decorative, both rows would read alike.

Why the default region here is us-east-2 and not us-east-1

Set the default configuration to us-east-1 and the first row comes back null rather than a region name. That is not a failure and not a Terraform statement about defaults. The API reference gives the rule outright: "Buckets in Region us-east-1 have a LocationConstraint of null." us-east-1 was S3's original region, so a bucket there carries no constraint element at all, and the CLI renders that absence as null.

It makes a poor teaching column, though, because null reads as nothing happened exactly where the section needs to show that something did. Worse, section 3 spends several pages on an implied empty default configuration, and a null sitting in a table three pages later invites the reader to connect two things that have nothing to do with each other. One is a configuration Terraform invents when you leave the role vacant; the other is a field AWS omits for historical reasons. us-east-2 removes the collision and costs nothing.

Two more caveats before reusing this call elsewhere, both measured in the lab README: eu-west-1 has a legacy spelling of EU, and AWS now recommends HeadBucket over this operation, which names us-east-1 outright instead of returning nothing.

Note that the data source needs its own provider argument, for exactly the same reason the resource does. A lookup happens in one region too.

Way two: the per-resource region argument¶

AWS provider 6.0.0, released 2025-06-18, added a top-level region argument to most resources, data sources and ephemeral resources. The provider's own Enhanced Region Support guide opens with what it is for:

"Version 6.0.0 of the Terraform AWS Provider adds region to most resources making it significantly easier to manage infrastructure across AWS Regions without requiring multiple provider configurations."

The same two buckets, with one provider block. This is labs/chapter17/section5/region-argument/:

provider "aws" {
  region = "us-east-2"
}

resource "aws_s3_bucket" "east" {
  bucket = "ch17-region-east"
}

resource "aws_s3_bucket" "west" {
  region = "us-west-2"
  bucket = "ch17-region-west"
}

The rules, all four from the guide and two of them measured:

Rule Detail
Default The argument is Optional and Computed. Omit it and you get "the Region specified in the provider configuration". Measured: ch17-region-east sets no region and lands in us-east-2, the provider's.

Which is correct, and worth internalising: a bucket does not move between regions. Editing that argument is a request to destroy one object and build another somewhere else.

The fan-out only one of them can do¶

The two routes look interchangeable until you try to iterate. The resource-to-provider-configuration association is static, so no amount of for_each will vary the configuration per instance. But region is an ordinary argument, so each.key reaches it:

variable "shard_regions" {
  type    = set(string)
  default = ["us-east-2", "us-west-2", "eu-west-1"]
}

resource "aws_s3_bucket" "shard" {
  for_each = var.shard_regions
  region   = each.key
  bucket   = "ch17-region-shard-${each.key}"
}

terraform apply -auto-approve

Apply complete! Resources: 5 added, 0 changed, 0 destroyed.
Bucket LocationConstraint
ch17-region-shard-us-east-2 "us-east-2"
ch17-region-shard-us-west-2 "us-west-2"
ch17-region-shard-eu-west-1 "eu-west-1"

One provider configuration, one resource block, three regions, driven by a variable. That is the shape aliases cannot produce in Terraform, and section 11 covers the two tools that attack the same problem from the provider side instead.

The bug neither route removes¶

Region-scoped identifiers are the classic multi-region mistake, and it survives both routes. AMI IDs are per-region: the same Ubuntu image has a different ID in us-east-1 and us-west-2, so a two-region configuration that hardcodes one ami value is wrong in one of its regions and will not tell you. The rule is broader than AMIs. Any identifier a provider hands you is scoped to the region that produced it, so a value fetched in us-east-1 has no meaning in us-west-2.

The fix is always one lookup per region. What differs is how each route spells it. With aliases, it is one data source per configuration, each carrying the provider argument way one already put on data.aws_region.west:

data "aws_ami" "east" {
  # …owners and filters…
}

data "aws_ami" "west" {
  provider = aws.west
  # …owners and filters…
}

Data sources took the region argument in 6.0 alongside resources, so the other route fans the lookup out the same way the buckets above were fanned out. Checked against the provider's own docs at tag v6.61.0: aws_ami carries the injected argument, described in the same words as on a resource and defaulting to the provider configuration's region.

data "aws_ami" "per_region" {
  for_each = var.shard_regions
  region   = each.key
  # …owners and filters…
}

A resource iterating the same set then reads data.aws_ami.per_region[each.key].id, and the pairing is correct by construction rather than by review.

Migrating from one to the other, with an empty plan¶

The guide gives a three-step migration, and step 2 is the one people skip:

  1. Upgrade to v6.0.0.
  2. Run terraform apply -refresh-only, so state is refreshed before the configuration is edited.
  3. Replace the provider meta-argument with a region argument on the affected resources.

Lab 1 runs exactly that sequence, and the result is the proof this book keeps asking for after a refactor:

No changes. Your infrastructure matches the configuration.

An empty plan is not an empty apply

Run the apply after that empty plan and Terraform still writes state. Measured in labs/chapter17/lab1/, the replica bucket's entry reads provider["registry.terraform.io/hashicorp/aws"].replica before the apply and provider["registry.terraform.io/hashicorp/aws"] after it. The plan reported nothing because no remote object changes. The binding recorded in state is a different thing, and it moves. This is the same lesson as Chapter 16's zero-destroy plans: "no changes" is a statement about infrastructure, not about the state file.

So which one¶

Prefer region when all three hold: the provider is AWS, the difference between the two places is only the region, and the resource is region-aware.

Reach for an alias when any of them fails:

  • Different credentials. region moves the region and nothing else. A second account needs a second configuration with its own assume_role, which is section 6.
  • A different provider entirely. region is an AWS provider feature. Every other provider still uses aliases for multiple configurations.
  • A resource that is not region-aware. The guide lists three exclusions: resources that already had a region argument, whole global services (IAM, CloudFront, Route 53, Organizations, WAF Classic, Global Accelerator, Cost Explorer and more), and a table of individually global resources inside otherwise regional services, such as aws_s3_account_public_access_block and aws_dx_gateway.
  • Other provider-level settings that must differ, such as a different default_tags set or different endpoints.

Aliases are not deprecated

"Pre-v6.0.0 configurations that use provider blocks per Region remain valid in v6.0.0 and are not deprecated." There is no forced migration here, and a working aliased configuration is not technical debt. What has changed is the default answer for new code.

6. Crossing accounts¶

Regions are the easy axis. Accounts are the one worth separating environments on, and they fail differently.

Three reasons to split, each independent of the others:

  • Isolation. An attacker who reaches staging has no path to production. A developer working in staging is far less likely to break production by accident.
  • Authentication and authorisation. Permissions granted in one account cannot leak into another, so fine-grained control gets easier rather than harder. The under-appreciated half is human error. With one account it is easy to believe you are dropping tables in staging when you are in production, and separate accounts put a separate authentication step in the way.
  • Auditing and billing. One audit trail per environment, plus consolidated billing with a per-account breakdown, which is how finance budgets by team without asking anyone.

Every AWS account needs a unique root email

Which sounds like a blocker for anyone creating a handful of accounts. Gmail and Google Workspace ignore everything after a +, so platform+stage@example.com and platform+prod@example.com are two addresses to AWS and one inbox to you.

The Terraform side is one block. A configuration that assumes a role is just another aliased configuration:

provider "aws" {
  region = "us-east-1"
}

provider "aws" {
  alias  = "child"
  region = "us-east-1"

  assume_role {
    role_arn     = "arn:aws:iam::222222222222:role/OrganizationAccountAccessRole"
    session_name = "terraform-ch17"
  }
}

data "aws_caller_identity" "parent" {}

data "aws_caller_identity" "child" {
  provider = aws.child
}

The demonstration is two account IDs from one apply. It is testable locally because Floci implements AssumeRole: post the call to the emulator's STS and it answers with temporary ASIA… credentials, a session token, an expiry, and an AssumedRoleUser ARN of arn:aws:sts::222222222222:assumed-role/OrganizationAccountAccessRole/terraform-ch17. The configuration is labs/chapter17/section6/assume-role/, and it creates nothing:

tflocal apply -auto-approve

accounts = {
  "child" = "222222222222"
  "parent" = "000000000000"
}

The arguments worth knowing¶

assume_role takes considerably more than role_arn, and two of its arguments are how a platform team keeps a blast radius small:

Argument What it does
role_arn the role to assume
session_name names the session, so CloudTrail attributes actions to a person or pipeline
external_id the shared secret a third party's role requires, guarding against the confused-deputy problem
source_identity propagates an immutable caller identity through the chain
duration how long the session lasts, as a duration string such as 1h, 2h45m or 30m15s. From 15 minutes up to the role's maximum, except when this block is chaining, where AWS caps it at one hour regardless (see the warning below)
tags, transitive_tag_keys session tags, and which of them survive further hops
policy, policy_arns further restrict the assumed role's permissions for this session

Repeating the block chains roles in order, which the provider documents as "IAM Role Chaining is supported by specifying the roles to assume in order." That is how a platform role hops into a tenant account without either side holding the other's long-lived keys. The web-identity equivalent, assume_role_with_web_identity, takes the same arguments and is limited to one block: OIDC establishes the base identity, and any further hops are ordinary assume_role blocks on top.

Chaining costs the session its length, and the provider reference never says so

The AWS provider gives duration one identical description on assume_role and assume_role_with_web_identity alike, "a value from 15 minutes up to the maximum session duration setting for the role". That holds for a single hop and fails for the chain this section just built. AWS's IAM roles reference states the limit under Roles terms and concepts: "Role chaining limits your AWS Management Console, AWS CLI or AWS API role session to a maximum of one hour. It applies regardless of the maximum session duration configured for individual roles." The AssumeRole API reference adds that an over-long request is refused rather than quietly shortened: "if you assume a role using role chaining and provide a DurationSeconds parameter value greater than one hour, the operation fails."

So duration = "4h" on a second assume_role block fails at credential acquisition, and the provider reference teaches chaining without ever mentioning the ceiling. The escape is that a web-identity exchange is not chaining at all, because its base is a token rather than a role session. The AssumeRoleWithWebIdentity reference puts its own DurationSeconds at "up to the maximum session duration setting for the role", as much as 12 hours, and the word chaining appears on that page only in its session-tag paragraph. A pipeline whose apply runs long should therefore let each consumer exchange the identity token for its own role directly, rather than assuming one bootstrap role and chaining onward from it. Chapter 23 builds that arrangement, and Chapter 24 explains why the backend and the provider are two such consumers.

Cross-account access is double opt-in, and one missing half looks like the other

Both accounts have to agree, and AWS files every cause under a single symptom. Its Troubleshoot IAM roles page answers I can't assume a role with a checklist covering trust, permissions, tags, conditions and case-sensitive names, rather than with a distinct message per cause. The two grants that must both exist:

  1. In the account that owns the role, the role's trust policy must allow the other account to assume it. AWS Organizations creates OrganizationAccountAccessRole with that trust already in place, which is why examples using it appear to work with no IAM code at all. A role you create yourself needs sts:AssumeRole granted explicitly. The same page is blunt about how little the other half can do for you: "If your account number is not listed in the Principal element of the role's trust policy, then you cannot assume the role. It does not matter what permissions are granted to you in access policies."
  2. In the account you assume from, your own principal needs permission to call sts:AssumeRole, with the role you want named in the statement's Resource. Tutorials skip this because their user is an administrator. A real user is not.

The apply above proves neither of them, and the reason is worth knowing before you trust a green local run. The emulator ships with IAM authorization switched off, so it issues a session for a role nobody created and no policy trusts. Probed directly, it returns credentials for arn:aws:iam::222222222222:role/OrganizationAccountAccessRole while no such role exists. So take this lab for what it is: it proves the wiring, and it proves that an alias carries a different identity. It says nothing about permissions until authorization is enabled, which is what Lab 5 does at the end of the chapter, one missing grant at a time.

One identity, many accounts

A separate IAM user per account is an antipattern: it is one more long-lived credential set to rotate and leak. Every major cloud supports one identity that authenticates into any account it is permitted to reach, and on AWS that mechanism is assuming roles. The same logic extends to CI, where the right answer is no stored key at all. An assume_role_with_web_identity block, or the AWS_ROLE_ARN and AWS_WEB_IDENTITY_TOKEN_FILE environment variables, lets a runner exchange a short-lived OIDC token for temporary credentials. Chapter 20 sets that up for real pipelines and Chapter 23 covers secrets end to end.

7. Provider-wide settings that do not port¶

Some of the most useful things in a provider block have no equivalent anywhere else, and no equivalent in other providers. Two examples make the point, and the point is that the provider block is the vendor-shaped part of Terraform.

AWS: default_tags¶

Tagging every resource is a governance requirement almost everywhere and a chore to write out. default_tags sets a tag map once, on the configuration, and the provider merges it into everything that configuration manages:

provider "aws" {
  region = "us-east-1"

  default_tags {
    tags = {
      ManagedBy = "Terraform"
      Chapter   = "17"
    }
  }
}

The result shows up as a second attribute rather than as an edit to the one you wrote. From labs/chapter17/section7/default-tags/, a bucket that sets one tag of its own:

resource "aws_s3_bucket" "own" {
  bucket = "ch17-tags-own"

  tags = {
    Owner = "platform"
  }
}

Planning it:

      + tags                        = {
          + "Owner" = "platform"
        }
      + tags_all                    = {
          + "Chapter"   = "17"
          + "ManagedBy" = "Terraform"
          + "Owner"     = "platform"
        }

tags is what the resource asked for. tags_all is what the object gets. A resource that sets no tags at all has no tags in state and still carries both provider tags in tags_all. When you go looking for why a tag exists that nothing in the resource block mentions, tags_all is the attribute that answers it.

One resource type is exempt, and it is a common one

The provider's own documentation carries the exception in a parenthesis: default_tags "is supported in all resources that implement tags, with the exception of the aws_autoscaling_group resource." Autoscaling groups model tags as a propagating list rather than a map, so a governance rule enforced through default_tags silently does not reach them. Tag them explicitly.

default_tags interacts with drift, and ignore_tags is its counterpart

If something outside Terraform adds tags to your resources, such as an AWS Backup policy or a cost-allocation automation, every plan will propose removing them. The ignore_tags block on the same provider configuration tells the provider to leave named tags or tag prefixes alone. Reach for it when the drift is legitimate and owned by someone else.

Google Cloud: quota-project routing¶

The Google provider has no tag-all argument, because GCP labels are per-resource. What it has instead is a pair of arguments with no AWS parallel at all. user_project_override and billing_project decide which project is billed for the API quota a request consumes, which matters when a service account operates on resources in projects other than its own.

The generalisation is the useful part. provider block arguments are defined by the provider author, so the declare half of provider usage is identical everywhere and the configure half is not portable at all. Reading the specific provider's registry page is not optional, and a pattern you learned on one provider may have no counterpart on the next.

8. The module boundary¶

This is where provider configuration stops being syntax and starts being design.

The rule¶

"A module intended to be called by one or more other modules must not contain any provider blocks."

Every tutorial on modules states it. Most of them give the wrong reason.

The real reason is destruction, not count¶

A provider configuration is used for all operations on the resources bound to it, including destroying them. Terraform records in state which configuration last applied each resource, precisely because that record is what remains once a resource block has been deleted from the configuration. The consequence, in HashiCorp's words:

"because a provider configuration is required to destroy the remote object associated with a resource instance as well as to create or update it, a provider configuration must always stay present in the overall Terraform configuration for longer than all of the resources it manages."

A module that holds both its resources and their provider breaks that, because deleting the module block removes the two at the same instant. State then points at a configuration that no longer exists.

You can watch this happen without a module at all, which is the clearest way to learn it. labs/chapter17/section8/orphan-provider/ ships the starting file, and the two blocks that matter are the ones you are about to delete together:

provider "aws" {
  alias  = "west"
  region = "us-west-2"
}

resource "aws_s3_bucket" "west" {
  provider = aws.west
  bucket   = "ch17-orphan-west"
}

Apply that, then delete both of them:

tflocal apply -auto-approve            # one bucket via aws.west
                                       # now delete the provider block AND the resource
tflocal plan

Error: Provider configuration not present

To work with aws_s3_bucket.west (orphan) its original provider configuration
at provider["registry.terraform.io/hashicorp/aws"].west is required, but it
has been removed. This occurs when a provider configuration is removed while
objects created by that provider still exist in the state. Re-add the
provider configuration to destroy aws_s3_bucket.west (orphan), after which
you can remove the provider configuration again.

The error names the fix, and the order matters. Put the provider block back but leave the resource deleted, and the plan becomes what you wanted in the first place:

Plan: 0 to add, 0 to change, 1 to destroy.

Apply that, and only then delete the provider block. So the general rule, which reaches well past modules: never delete a provider block while anything in state still references it. Destroy first, then remove the configuration.

The count conflict is the enforcement, not the reason¶

Terraform v0.13 added count, for_each and depends_on to module blocks, and that implementation conflicted with the legacy pattern of a module carrying its own providers. So the legacy pattern kept working, but only for module calls that use none of the three.

From labs/chapter17/section8/legacy-module/, a child module with its own provider block, called with count = 2:

# child/main.tf — the legacy pattern
provider "aws" {
  region = "us-east-1"
}

resource "aws_s3_bucket" "b" {
  bucket = "ch17-legacy-module"
}

# main.tf
module "child" {
  source = "./child"
  count  = 2                           # line 18
}

On 1.15.8, init alone is enough:

Error: Module is incompatible with count, for_each, and depends_on

  on main.tf line 18, in module "child":
  18:   count  = 2

The module at module.child is a legacy module which contains its own local
provider configurations, and so calls to it may not use the count, for_each,
or depends_on arguments.

If you also control the module "./child", consider updating this module to
instead expect provider configurations to be passed by its caller.

The docs quote an older error than the one you will see

Providers Within Modules reproduces a transcript headed Error: Module does not support count, with the body "Module "child" cannot be used with count because it contains a nested provider configuration". That text was still on the page when it was re-fetched on 2026-08-24, and it is not what 1.15.8 prints. The current message covers all three meta-arguments in one summary and names the module by its address. The advice is unchanged; only the transcript is stale.

What is inherited, and what is not¶

Three rules, and the asymmetry between them is the thing to memorise.

Thing Inherited by a child module?
Default provider configurations Yes, automatically
Aliased provider configurations Never. They must be passed with providers
Provider source and version requirements Never. Every module declares its own

The third one catches people because a child module that declares no required_providers still appears to work: the configuration it needs was inherited, so resources apply. What it lost is the source address. For a provider outside the hashicorp namespace, Terraform falls back to assuming hashicorp/<name> and either fails to find it or silently resolves a different provider that happens to share a short name. The docs are blunt that this "is especially important for non-HashiCorp providers".

There is a second reason each module declares its own requirements, and it is the one section 9 builds on: those declarations are inputs to a single global resolution, so Terraform can guarantee "a single version of the provider that is compatible with all modules".

configuration_aliases: the contract¶

A module that needs a configuration the caller must supply declares the name it expects, inside its own required_providers:

terraform {
  required_providers {
    aws = {
      source                = "hashicorp/aws"
      version               = ">= 6.0"
      configuration_aliases = [aws.replica]
    }
  }
}

That creates no provider. It creates an obligation. Inside the module, provider = aws.replica now works exactly as an ordinary alias would. Outside it, the caller must supply one:

module "pair" {
  source = "./mod"
  name   = "ch17-modboundary"

  providers = {
    aws.replica = aws.west
  }
}

Omit the map and the failure arrives at init, before any plan. Measured in labs/chapter17/section8/config-aliases/:

Error: Missing required provider configuration

  on main.tf line 30:
  30: module "pair" {

The child module requires an additional configuration for provider
hashicorp/aws, with the local name "aws.replica".

Refer to the module's documentation to understand the intended purpose of
this additional provider configuration, and then add an entry for
aws.replica in the "providers" meta-argument in the module block to choose
which provider configuration the module should use for that purpose.

Which gives the rule for when providers is optional. It is optional only while the child declares no configuration_aliases. Declaring one makes it mandatory, because non-default configurations are never inherited and there is no other way for the child to receive it.

The docs contradict themselves, and the measurement settles it¶

The providers reference says that supplying the argument "cancels the default behavior", so the child "only has access to the provider configurations you specify". Read literally, that makes any providers map an inheritance kill switch. Providers Within Modules says something narrower on the same subject: "Setting a providers argument within a module block overrides the default inheritance behavior for that provider."

The narrower one is right, and the lab above proves it. Its module declares one configuration alias and its caller supplies only that one, never mentioning aws:

providers = {
  aws.replica = aws.west
}

The module's aws_s3_bucket.primary names no provider. If inheritance had been cancelled, it would fall back to the implied empty default configuration described in section 3. So the lab's root default is deliberately eu-central-1, a region nothing else in the environment supplies:

Bucket LocationConstraint Which configuration
ch17-modboundary-primary "eu-central-1" the root's inherited default
ch17-modboundary-replica "us-west-2" aws.west, passed explicitly

That first row is the whole argument. lab-env exports AWS_DEFAULT_REGION=us-east-1, so an empty default configuration would have put the bucket in us-east-1 and the row would have read null. It reads eu-central-1, which only the root's provider "aws" block supplies. Inheritance survived a providers map that never mentioned aws.

Terraform issue #35781 was filed against the broader wording and closed once the other page was corrected. The correction never propagated to the reference page, so the two disagree as they stand. Read it per-provider.

The limitation no wiring fixes¶

"Since the association between resources and provider configurations is static, module calls using for_each or count cannot pass different provider configurations to different instances."

The static association is not a phrase to skim. Try to route around it and the error explains why better than the sentence does. Putting for_each on a module call and trying to vary the map per instance:

module "pair" {
  source   = "./mod"
  for_each = { east = aws, west = aws.west }
  name     = "ch17-modboundary-${each.key}"

  providers = {
    aws.replica = each.value
  }
}

Error: Provider type mismatch

  on main.tf line 32, in module "pair":
  32:     aws.replica = each.value

The local name "each.value" in the root module represents provider
"hashicorp/each", but "aws.replica" in module.pair represents
"hashicorp/aws".

Terraform did not evaluate each.value and find the wrong type. It never evaluated it at all. The right-hand side of a providers entry is a reference to a provider configuration, so each.value was parsed as the provider local name each with alias value, and Terraform went looking for hashicorp/each. That is what "static" means here: the association is resolved from the syntax, before any expression evaluation happens.

So multi-provider fan-out is one module block per provider set, by design rather than by omission:

module "us" {
  source    = "./modules/bucket-pair"
  name      = "ch17-lab2-us"
  providers = { aws.replica = aws.west }
}

module "eu" {
  source    = "./modules/bucket-pair"
  name      = "ch17-lab2-eu"
  providers = {
    aws         = aws.europe    # remaps the child's *default*
    aws.replica = aws.west
  }
}

Lab 2 applies exactly that. Four buckets across three regions, from one module called twice, and the aws = aws.europe entry in the second call is the remap semantics from section 4 doing real work: the child's unqualified resources land in eu-west-1 without a line of the module changing.

Constraints belong in required_providers¶

The docs say you cannot combine alias and version. 1.15.8 lets you

Success! The configuration is valid, but there were some validation warnings

Do not lean on it either way: the argument is going, and a per-configuration version constraint is not a thing the language supports even where the parser tolerates the syntax.

Every module's constraints are intersected¶

Terraform resolves one version of each provider for the whole configuration, and it must satisfy every module that requires it. Root modules pin a range, shared modules pin a floor¶

Intersection is also why the version advice differs depending on which side of the module call you are on:

"If you are writing a shared Terraform module, constrain only the minimum required provider version using a >= constraint."

A shared module names the oldest provider that has the features it uses, and stops there. A root module pins a range it has actually tested, most often ~> 6.0, which allows minor and patch releases but blocks the next major. A ceiling in a shared module becomes every consumer's ceiling for their whole configuration, so they wait on a module release before they can move the provider forward for unrelated reasons. A configuration with no constraint takes whatever is newest at the moment of the first init, which is a decision made by the calendar rather than by you.

The lock file decides what actually gets installed¶

terraform init resolves the constraints, then records the exact selection and its checksums in .terraform.lock.hcl. Commit that file. Afterwards, plan and apply use what the lock records, not the newest version the constraint would allow. HCP Terraform and Terraform Enterprise install providers on every run, and honour the lock file the same way.

Which raises the question that trips everyone up at least once: when does init change the lock?

Situation What plain terraform init does
Locked version still satisfies the constraint keeps the locked version. Use terraform init -upgrade to move up
Locked version now violates the constraint re-selects and rewrites the lock on its own. No -upgrade needed

So -upgrade means "ignore the lock, re-resolve every provider to the newest allowed version, rewrite the file". Reach for it when the locked version is still valid but stale. Bumping ~> 6.0 to ~> 7.0 needs no flag at all, because the lock has become illegal and init is forced to act.

Lock files are per-platform unless you make them otherwise

The lock records checksums for the platforms it has seen. A lock file created only on Windows carries no linux_amd64 hashes, and a Linux CI runner will then either fail the checksum verification or quietly re-resolve. terraform providers lock -platform=linux_amd64 -platform=windows_amd64 -platform=darwin_arm64 records them all up front. Running a lab through labs/tf-docker.sh has the same side effect, because the container is Linux and its init appends the missing hashes.

10. What a provider configuration costs¶

Everything above treats provider configurations as free. They are not, and the cost is worth a section because it is the argument behind almost every design recommendation in this chapter.

Each provider configuration in use starts a plugin process, which talks gRPC to core and HTTPS to a remote API. Brikman's Terraform: Up & Running supplies the only measured example of what happens when the count grows. Five reusable modules for account-wide security services, each meant to run in every AWS region, each carrying one provider block per region at roughly 25 regions. One root module combining all five meant 125 provider blocks, so an apply started 125 processes, each making hundreds of API and RPC calls. A single plan took 20 minutes, the CPU thrashed, and the overloaded network stack produced intermittent API failures and sporadic apply errors.

That story is from 2022. HashiCorp's own reasoning for enhanced Region support, published in 2025, is the same argument from the other side:

"This approach led to complex and repetitive configurations, especially for large infrastructures—AWS currently operates in 36 Regions, with more announced. Additionally, each provider configuration adds overhead in terms of memory and compute resources."

The region count has gone from 25 to 36 and the arithmetic has got worse. configuration_aliases was the language's answer, moving the blocks up to the one root module that needs them. The per-resource region argument is the provider's answer, removing most of them entirely.

Aliases are a coupling decision¶

The subtler cost has nothing to do with processes. A module with an alias into two regions cannot plan or apply while either region is unreachable. So the outage you built multi-region infrastructure to survive is exactly the moment your deployment tooling stops working.

The general rule is the state-isolation argument applied to providers: manage each region in its own configuration, with its own state, and let a failure in one leave the other operable. Chapter 24 is where that question gets answered properly, since it is really a question about how many state files you should have.

When an alias is genuinely the right shape

Reach for one when the infrastructure is inseparable, so that splitting it would create a dependency across two state files rather than removing one.

  • CloudFront with an ACM certificate. AWS requires the certificate in us-east-1 regardless of where anything else lives, and the distribution cannot be created without it. One configuration holds the primary-region provider and a second hardcoded to us-east-1. Note that this case is not solved by the region argument, because both CloudFront and ACM certificates for it are global or pinned by the service itself.
  • Detective controls that must exist everywhere. GuardDuty in every region you use is a single logical thing expressed once per region.

Outside cases like these, the common reason to want two configurations of one provider is not regions at all. It is that they authenticate differently, which is section 6, and which no region argument will ever replace.

11. Provider iteration: OpenTofu's for_each, Terraform's reserved word¶

Section 8 established that a module call cannot vary its providers per instance, and section 5 showed the AWS provider sidestepping the problem by making the region an argument. The third approach is to iterate the provider configuration itself, and it is where the two tools visibly diverge.

OpenTofu — an aliased provider block can take for_each (since 1.9)

OpenTofu lets an aliased provider configuration take for_each, producing one provider instance per element. The default configuration must still be exactly one instance, so that OpenTofu can select it automatically.

provider "aws" {
  alias    = "by_region"
  for_each = var.regions
  region   = each.key
}

resource "aws_s3_bucket" "shard" {
  for_each = setsubtract(var.regions, var.retired)
  provider = aws.by_region[each.key]
  bucket   = "ch17-tofu-${each.key}"
}

The for_each value must be a map, an object, or a set of strings, and it must be resolvable statically from variables and locals. The configuration reference stays static and only the instance key in brackets is dynamic, which is how OpenTofu still wires dependencies before evaluating expressions.

Measured on OpenTofu 1.12.5 in labs/chapter17/section11/for-each/: Apply complete! Resources: 3 added, one bucket per region, from one aliased block.

The trap is the obvious way to write it¶

The natural instinct is to drive both the provider and its resources from one collection. That is the one arrangement that breaks, and OpenTofu now warns about it before it does. One word changes on line 45 of the lab file:

provider "aws" {
  alias    = "by_region"
  for_each = var.regions
  region   = each.key
}

resource "aws_s3_bucket" "shard" {
  for_each = var.regions               # was setsubtract(var.regions, var.retired)
  provider = aws.by_region[each.key]
  bucket   = "ch17-tofu-${each.key}"
}

Nothing about that is wrong yet, and the very first apply creates all three buckets. It also prints:

Warning: Provider configuration for_each matches resource

  on main.tf line 45, in resource "aws_s3_bucket" "shard":
  45:   for_each = var.regions

This provider configuration uses the same for_each expression as a resource,
which means that subsequent removal of elements from this collection would
cause a planning error.

OpenTofu relies on a provider instance to destroy resource instances that are
associated with it, and so the provider instance must outlive all of its
resource instances by at least one plan/apply round. For removal of instances
to succeed in future you must structure the configuration so that the
provider block's for_each expression can produce a superset of the instances
of the resources associated with the provider configuration. Refer to the
OpenTofu documentation for specific suggestions.

To destroy this object before removing the provider configuration, consider
first performing a targeted destroy:
    tofu apply -destroy -target=aws_s3_bucket.shard

Apply complete! Resources: 3 added, 0 changed, 0 destroyed.

Remove a region and the warning comes true:

Error: Provider instance not present

To work with aws_s3_bucket.shard["eu-west-1"] its original provider instance
at provider["registry.opentofu.org/hashicorp/aws"].by_region["eu-west-1"] is
required, but it has been removed. This occurs when an element is removed
from the provider configuration's for_each collection while objects created
by that the associated provider instance still exist in the state.

This is section 8's lifecycle rule, instance by instance: a provider instance must outlive the resource instances it created. Drop an element from a shared collection and the same plan deletes the resource instance and the provider instance needed to destroy it.

It is worth being precise about what the constraint is, because it is usually summarised wrongly, and the warning's own “superset” phrasing is where the wrong summary comes from. It is not a static rule that the resource's collection must be a subset of the provider's. It is a rule about ordering, and OpenTofu states it as one: "To successfully remove an instance of a resource it must be possible to remove the corresponding element from the resource's for_each collection while retaining the corresponding element in the provider's for_each collection." Two collections that happen to be identical are not illegal. Driving both from one variable is what makes removal impossible.

The fix is the shape the lab ships. The provider iterates the full set, the resource iterates a subtracted set, and retiring a region means adding it to var.retired:

TF_CMD=tofu tflocal apply -auto-approve -var 'retired=["eu-west-1"]'

Plan: 0 to add, 0 to change, 1 to destroy.
Apply complete! Resources: 0 added, 0 changed, 1 destroyed.

One round, clean, because the provider instance for eu-west-1 still exists to perform the destroy.

Terraform on the same file¶

The committed lab is labs/chapter17/section11/for-each/, and the two lines Terraform objects to are the two that make provider iteration work:

provider "aws" {
  alias    = "by_region"
  for_each = var.regions               # line 40
  region   = each.key
}

resource "aws_s3_bucket" "shard" {
  for_each = setsubtract(var.regions, var.retired)

}

Run that file under Terraform 1.15.8 and it never reaches a provider. init refuses first, because a configuration has to be valid before Terraform can work out what to install, and it reports each problem twice. A bare plan in an uninitialised directory states them once each, in a way that says something about the roadmap:

Error: Reserved argument name in provider block

  on main.tf line 40, in provider "aws":
  40:   for_each = var.regions

The provider argument name "for_each" is reserved for use by Terraform in a
future version.

Error: Invalid provider configuration reference

  on main.tf line 46, in resource "aws_s3_bucket" "shard":
  46:   provider = aws.by_region[each.key]

The provider argument requires a provider type name, optionally followed by a
period and then a configuration alias.

The second error is the static association again, stated from the parser's point of view: an indexed reference is not a provider configuration reference.

The first is more interesting. for_each is not merely unsupported in a provider block; it is reserved. Terraform already has provider for_each, in Stacks, where a component configuration may iterate providers. So the divergence between the two tools here is about which configuration surface exposes the capability rather than whether it exists. OpenTofu put it in the core language, usable in any root module. Terraform put it behind a separate configuration type that runs in HCP Terraform, covered in Chapter 27.

What this enforces, and what it still does not

Two gates stand between this lab and a real cross-account grant, and both default to open. Authorization is off unless FLOCI_SERVICES_IAM_ENFORCEMENT_ENABLED is set, and even with it on, a role the emulator has never seen is allowed through deliberately, which is why section 6's fictional role never produces an AssumeRole denial. What is genuinely evaluated, once the role exists, is the trust policy's AWS principals: *, a bare account ID, an account-root ARN, and an exact or wildcard principal ARN, with an assumed-role session resolved back to its role first. A trust policy naming a Service principal is not evaluated at all, and neither is NotPrincipal. That gap matters the moment a lab copies a Lambda or EC2 execution role's trust document and expects it to be checked.

Authorization is not authentication

A wrong secret key is still accepted, enforcement or no enforcement. The emulator identifies the caller from the access key ID in the Authorization header and evaluates that principal's policies, without verifying the SigV4 signature on a header-signed request. So this lab teaches how a policy is evaluated. It teaches nothing about credential security.

Common pitfalls¶

  • Adding alias to your only provider block. It does not name that configuration. It demotes it, and every resource that never asked for a provider now binds to an invented empty default. Keep one unaliased block.
  • Assuming providers = {} cuts off inheritance. It overrides inheritance per provider, for the providers you list, and nothing else.
  • Deleting a provider block while its resources are still in state. Destroy first, then remove the block. The plan-time error names the missing configuration and there is no way past it except putting the block back.
  • Putting a provider block in a reusable module. It makes the module own dozens of vendor settings, forces callers to duplicate them, multiplies processes, and makes the module impossible to delete cleanly. Use configuration_aliases.
  • Expecting a child module to inherit required_providers. Configuration is inherited. Source addresses and version constraints are not, and the failure mode for a non-HashiCorp provider is a wrong provider rather than an error.
  • Pinning a ceiling in a shared module. Constraints intersect across every module, so a module's ~> 6.0 blocks every consumer from moving to 7 until you release.
  • Reaching for for_each on a module call to fan out across regions. The resource-to-provider association is static. Write one module block per provider set, or use the AWS provider's region argument.
  • Hardcoding a region-scoped identifier in a two-region configuration. AMI IDs and most other provider-issued IDs mean nothing in the other region. One data source per region.
  • Driving OpenTofu's provider for_each and its resources from one variable. Removal then deletes the provider instance and the resource instance in the same plan, and you cannot destroy your way out without re-adding the element first.
  • Leaving a version argument inside a provider block. It is deprecated and it will be removed. Constraints belong in required_providers, which is also the only place they are actually resolved from.

Summary¶

A provider configuration is a global object, defined only in the root module, backed by a process, and bound to each resource statically and recorded in state. Almost every rule in this chapter is a consequence of one of those four properties.

alias gives a provider more than one configuration, and the block without an alias is the default. Alias all of them and Terraform invents an empty default that reports itself at <empty> line 0. Resources select a configuration with provider; modules receive a remap through the providers map, whose keys are the child's names and whose values are yours.

Two regions is now two questions rather than one. For AWS, the per-resource region argument added in provider 6.0 covers most cases with a single provider configuration, iterates with for_each where aliases cannot, forces replacement when changed, and migrates from aliases with an empty plan. Aliases remain the answer whenever the credentials differ, the provider is not AWS, or the resource is not region-aware. Crossing accounts is always an alias, because assume_role changes identity rather than location, and it needs permission granted on both sides.

A reusable module holds no provider block, and the reason is that a provider configuration must outlive every object it created. The count incompatibility is the enforcement that came later. configuration_aliases is how a module declares what its caller must supply, and the caller's providers map overrides inheritance one provider at a time rather than all at once.

Version constraints belong in required_providers, are intersected across every module, and are resolved once into .terraform.lock.hcl. A root module pins a range; a shared module pins a floor. Every provider configuration costs a process, and every alias couples your ability to deploy to the availability of both places it reaches.
