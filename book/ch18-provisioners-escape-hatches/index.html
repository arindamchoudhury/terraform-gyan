Chapter 18 — Provisioners, terraform_data and escape hatches¶

Learning outcomes¶

By the end you can:

  • Say what an escape hatch is, name the four Terraform ships, and explain what each one is actually for.
  • Rank the alternatives to a provisioner in order, and justify skipping the rungs above the one you land on.
  • Write local-exec, remote-exec and file provisioners, and find the arguments the usage page never lists.
  • Place a connection block in each of its three positions, and configure a bastion host with one argument instead of seven.
  • State what a failed provisioner does to a healthy resource, and show it happening in a plan.
  • Name the four holes in when = destroy, and pick the removed-block route out of the first one.
  • Use terraform_data as a provisioner host, and tell input, triggers_replace and store apart by what a change to each one does.
  • Explain why a provider action is not a provisioner, and why its on_failure default is the opposite of the provisioner one.
  • Use data "external" within its contract, and say what it hands the program you point it at.
  • Recognise why local_file produces a permanent diff on ephemeral runners.
  • Design the handoff to a configuration management tool, and choose between publishing outputs and sharing state.

Which binary the transcripts came from

Every command output in this chapter was captured on Terraform 1.15.8, and the OpenTofu ones on 1.12.5, from the configurations committed under labs/chapter18/. Terraform 1.16.0 shipped on 2026-08-26 and changes three things this chapter argues about. Each of those is in its own !!! info box, source-verified at tag v1.16.0, rather than folded silently into the text.

1. The gap: Terraform has nouns, not verbs¶

Seventeen chapters of this book have been about describing things that exist. A bucket exists. A role exists. A module is a package of things that exist. The plan is a diff between the things you described and the things that are out there, and apply is the work of closing that gap. Nothing in that model has a place for do this once, now.

Real work keeps asking for it anyway:

  • A server is up, and a package has to be installed on it.
  • A cluster's first node has to be told about the other two before any of them is useful.
  • A deployment finishes and a CDN cache has to be invalidated, or a Lambda invoked, or a deregistration call made to something that will otherwise keep routing traffic at a machine you just deleted.
  • A value you need lives in a system that has no Terraform provider — an internal inventory API, a script that knows how to compute the thing.
  • A rendered configuration file has to end up on disk, next to the configuration, for something else to pick up.

Every one of those is a verb, and Terraform's language is a language of nouns. Escape hatches are the parts of Terraform that let a verb in anyway, and this chapter is about all four of them: the provisioner block, terraform_data as its host, the external data source, and the local provider. It is also, unavoidably, about not using them. HashiCorp's own Use provisioners to perform post-apply operations page opens by arguing against its own subject:

"You should exhaust all alternatives before using provisioners in your configurations. This is because Terraform cannot predictably model provisioner behaviors represented in the configuration. Additionally, most provisioners require direct network access to your servers and credentials to install and configure external software, which introduces complexity and potential security issues."

That is two separate objections wearing one sentence. The first is that the plan becomes a lie: Terraform prints a diff that describes creating a server and says nothing about the twenty minutes of shell that follows, because it cannot see inside a command. The second is about blast radius: to run a command on a machine you need a route to it and a credential for it, and now your Terraform runner holds both.

Two more objections come from elsewhere, and they are the ones that decide real cases.

Terraform in Depth argues from portability. A remote-exec needs a connection, a connection needs to know whether there is a bastion in the way, and the moment your module knows that, it has a network topology baked into it. Either you decide for every future consumer whether a jump host is used, or you thread a pile of variables through the interface to let them decide. Either way the module has stopped being reusable outside the network it was written in.

Terraform: Up & Running argues from operational visibility, and autoscaling. A remote-exec needs SSH or WinRM open to the runner; User Data needs only the cloud API access you already have. User Data is visible in the EC2 console afterwards and leaves a log at /var/log/cloud-init*.log; a provisioner leaves neither. And the killer:

"Provisioners take effect only while Terraform is running and don't work with ASGs at all."

An instance that an autoscaler launches at three in the morning was never provisioned, because nobody ran terraform apply at three in the morning. HashiCorp says the same thing in stronger words on the sibling page most readers never open, Perform post-apply operations:

"This approach is required when you use your cloud provider to automatically launch and destroy servers in a group because individual servers will launch unattended when Terraform is not available to provision them."

The one advantage running the other way is worth stating, because it is real: User Data is capped at 16 KB on EC2 and provisioner scripts are not.

The argument and the manual live on different pages now

During the v1.14 documentation cycle HashiCorp consolidated six provisioner pages into one, and in the same restructure moved the case for the alternatives out to a separate page. The commit is dated 2025-12-04 and it removed 187 lines from provisioners.mdx while adding a 114-line post-apply-operations.mdx beside it.

So the page you land on when you search for provisioner syntax now carries the objection with the replacement removed: its Overview tells you to ask your provider for a post-apply mechanism and, failing that, to open a feature request. The sentence about autoscaling groups quoted above is on the other page. Read both, or read this chapter's section 2, which is the ladder they describe between them.

And then there is the fourth objection, which is not in either book or on either page as a stated argument, and which is the one that changes behaviour rather than taste. A failed provisioner does not merely fail. It taints the resource it was attached to, so the next plan destroys a perfectly healthy server and builds a new one. Section 5 measures it.

2. The ladder, and where a provisioner sits on it¶

The useful form of "don't use provisioners" is not a prohibition, it is an ordering. Work down this list and stop at the first rung that fits. Each row costs more than the one above it.

Rung Reach for Why it beats the rung below
1 A resource or data source in a provider you already use Terraform models it, diffs it, and destroys it. Nothing is a special case.
2 A provider-defined action (action block + action_trigger) The provider declares the operation, so a failure is understood rather than guessed at. Terraform 1.14+; section 8.
3 Data passed at creation time (cloud-init, user_data, custom_data, metadata) Runs on every boot including autoscaler launches; needs no route from the runner to the machine, and no credential.
4 A pre-built machine image (Packer or equivalent) The work happens once, in advance, where it can be tested — and the machine boots configured, so there is nothing to wait for.
5 A handoff to configuration management Re-converging does not need Terraform at all, and a failed configuration step is not a tainted server. Section 11.
6 A provisioner Nothing above fits.

Two things about that table are worth pausing on.

Rung 4 is a provisioner too, and that is the point. HashiCorp's own Provision infrastructure with Packer tutorial builds its image with two Packer provisioner blocks, file and shell. The same word, the same shell script, a completely different lifecycle: it runs once against a throwaway instance and yields an artifact, so nothing runs during an apply and none of section 1's objections attach. The alternative to a Terraform provisioner is very often a provisioner somewhere else.

Rung 3 does not remove the wait, it moves it. HashiCorp's Provision infrastructure with Cloud-Init tutorial says so itself:

"Cloud-Init runs after the instance is provisioned, and may take a few minutes to complete."

The apply finishes when the instance exists, not when the machine is ready. If something downstream needs a working machine, cloud-init has relocated the problem rather than solved it — which is exactly why rung 4 exists, since an image boots configured.

Rung 3 in practice: user_data, and the data source that assembles it¶

The simple form is one argument. Azure's, from HashiCorp's own page:

resource "azurerm_linux_virtual_machine" "example" {
  # ...
  custom_data = base64encode(file("custom-data.sh"))
}

The argument name is per-cloud — user_data and user_data_base64 on AWS, custom_data on Azure, metadata on Google Cloud and OCI — but the mechanism is the same, and on Linux images it is cloud-init on the other end.

When one script is not enough, the cloudinit_config data source from the separate hashicorp/cloudinit provider assembles several files of different types into one multi-part MIME payload. This is also where Chapter 7's templatefile() finally writes something out:

data "cloudinit_config" "node" {
  gzip          = false
  base64_encode = false

  part {
    content_type = "text/cloud-config"
    filename     = "cloud.conf"

    content = yamlencode({
      "write_files" : [
        { "path" : "/etc/foo.conf", "content" : "foo contents" },
        { "path" : "/etc/bar.conf", "content" : file("bar.conf") },
        { "path" : "/etc/baz.conf", "content" : templatefile("baz.tpl.conf", { SOME_VAR = "qux" }) },
      ],
    })
  }
}

Those three entries are a deliberate progression: a literal string, a file read verbatim, and a rendered template.

The attribute you actually pass to user_data is rendered, and neither HashiCorp page names it

The example above is where HashiCorp's Post-apply operations page stops — at the closing brace of the data block. It never shows the consuming half, and the Cloud-Init tutorial does not either, because that one takes the file() route instead. The attribute is data.cloudinit_config.node.rendered, and it is documented only in the provider's own reference.

The two falses in that example are not decoration either. gzip and base64_encode both default to true, and base64_encode "cannot be disabled if gzip is true" — so turning either off means turning both off, in that order. That default is a real trap on AWS, where the provider says not to pass gzip-compressed data to user_data and to use user_data_base64 instead. Two ways out: set both to false and use user_data, or leave the defaults and use user_data_base64. Terraform in Depth's Listing 10.40 takes neither and is miswired as printed.

A rung nobody lists: check whether the provider grew a function

Since Terraform 1.8 and OpenTofu 1.7, providers can ship functions, callable as provider::<name>::<fn>(). The thing you were about to shell out to compute may already exist as one. The local provider's direxists is the standard example, and it exists precisely because fileexists() was built in and had no directory counterpart. Section 10 has it.

Where the AWS argument table has aged

The Post-apply operations page carries a table of the argument each cloud uses for creation-time data. Four of the thirteen resources it names should not be copied as they stand. aws_launch_configuration is discouraged by its own provider in favour of aws_launch_template, which is already in the same row. azurerm_virtual_machine is feature-frozen and azurerm_virtual_machine_scale_set is deprecated, both superseded by _linux_ and _windows_ variants — and the page's own example, two paragraphs above the table, uses the replacement it does not list. google_compute_instance_group has no metadata argument at all; it is an unmanaged group, a list of instances that already exist, and the resource that takes metadata beside google_compute_instance is google_compute_instance_template.

Use the table as a map of which argument name each cloud chose, which is what it is good for, and check the resource against its own provider documentation.

3. The three provisioners, and where their arguments live¶

A provisioner block goes inside a resource block. There are three built-in types:

  • local-exec runs a command on the machine running Terraform.
  • remote-exec runs a command on the resource Terraform just created, over SSH or WinRM.
  • file copies a file or directory from the runner to that resource.

The shape is the same in all three cases:

resource "aws_instance" "web" {
  ami           = data.aws_ami.ubuntu.id
  instance_type = "t3.micro"

  provisioner "local-exec" {
    command = "echo The server's IP address is ${self.private_ip}"
  }
}

Three rules govern all of them:

  • They run in the order they are written. Terraform runs only the ones valid for the current operation, still in file order.
  • They cannot name their own resource. aws_instance.web.private_ip inside aws_instance.web would be a reference, a reference is a graph edge, and an edge to yourself is a cycle. self exists for exactly that reason, and HashiCorp's page states it in one sentence: "You must use the self object to reference the resource because using references in the configuration creates dependencies, and referring to a resource by name within its own block would create a dependency cycle." Under count or for_each, self is the instance, not the block.
  • They are creation-time by default. They run when the resource is created and never again — not on later applies, not when an attribute changes. Section 7 is about how to get a re-run when you want one.

The arguments are documented on a different page than the usage¶

This trips people up because both halves look complete. The provisioners page is placement and behaviour. It names arguments in passing — the seven bastion attributes as a flat list, script_path, when, on_failure — and gives no types, no defaults, and no complete set for either block. The normative reference is the resource block reference, under its #provisioner and #connection anchors, which is where the usage page's own "provisioner block reference" and "connection block reference" links resolve.

The gap that costs most: both HashiCorp's page and Terraform in Depth show local-exec with command and nothing else. Both local-exec and remote-exec also take four more arguments, and one of them matters a great deal.

Argument Applies to What it is for
command local-exec The command. There is no script argument; invoke your script from the command.
inline remote-exec A list of command strings, run in order. Best for one-liners.
script remote-exec One path, relative to the defining file. Uploaded, then run.
scripts remote-exec A list of paths, uploaded and run in the order given.
environment both A map of environment variables for the command.
interpreter both Run something other than the platform default shell.
working_dir both The directory to run in.
quiet both Suppress echoing the command into the log.

inline, script and scripts are mutually exclusive: one per provisioner block.

environment is the difference between passing a secret and printing it¶

The two ways of getting a value into a command are not equivalent, and the difference shows up in the log. labs/chapter18/section4/environment/ is two terraform_data resources that do the same job two ways:

variable "token" {
  type    = string
  default = "s3cr3t"
}

resource "terraform_data" "interpolated" {
  provisioner "local-exec" {
    command = "echo deploying with ${var.token}"
  }
}

resource "terraform_data" "in_environment" {
  provisioner "local-exec" {
    command     = "echo deploying"
    environment = { DEPLOY_TOKEN = var.token }
  }
}

terraform init
terraform apply -auto-approve

Measured on 1.15.8:

terraform_data.interpolated (local-exec): Executing: ["cmd" "/C" "echo deploying with s3cr3t"]
terraform_data.in_environment (local-exec): Executing: ["cmd" "/C" "echo deploying"]
terraform_data.interpolated (local-exec): deploying with s3cr3t
terraform_data.in_environment (local-exec): deploying

Interpolating puts the value in the command line, which Terraform echoes, which your CI system keeps. The environment map does not appear in that line at all. The value still reaches the process; it just stops being part of the string everything logs.

terraform destroy -auto-approve

Mark the variable sensitive as well, and the whole provisioner goes quiet

Add sensitive = true to var.token and Terraform replaces both output lines of whichever resource reads it with (output suppressed due to sensitive value in config). That is stronger than it sounds — it suppresses the command's own stdout too, so you lose the useful output along with the secret. Prefer environment, and reach for sensitive when the log is genuinely untrusted. Terraform 1.10 and later also accept ephemeral values in provisioner and connection blocks, which is the path that keeps the credential out of state as well as out of the log (→ Chapter 23).

file, and the trailing slash¶

file takes source (a local path) or content (a string), plus destination. Two things about it are easy to get wrong and neither is on the page:

  • The destination directory must already exist. Since provisioners run in written order, a remote-exec that runs mkdir -p before the file block is the standard pairing.
  • A trailing slash on source changes what is uploaded. With no trailing slash the source directory itself is created inside the destination; with one, the directory's contents are copied into the destination. So source = "conf/" into /etc/nginx/ gives /etc/nginx/<files>, and source = "conf" gives /etc/nginx/conf/<files>.

There is also a requirement the docs list and everyone skips: to upload files over SSH, the scp service program must be installed on the remote system. That applies to file and to every remote-exec that uploads a script, which is most of them.

4. connection: three positions, and two pages that disagree¶

Anything remote needs a connection block, and where you put it decides its scope. HashiCorp states two positions:

"Add a connection block to either the provisioner block or to the resource block. All provisioners in the configuration can use connection settings defined in the resource block. Connection settings defined in the provisioner block are specific to that provisioner."

There is a third that neither the provisioners page nor either book mentions: a connection block on a removed block, which supplies defaults for provisioners running during removal. Section 6 uses it.

resource "aws_instance" "web" {
  # ...

  connection {                       # position 1: every provisioner in this resource
    type        = "ssh"
    user        = "ubuntu"
    private_key = file("~/.ssh/id_rsa")
    host        = self.public_ip
  }

  provisioner "remote-exec" {
    inline = ["sudo apt-get update", "sudo apt-get install -y nginx"]
  }
}

A connection does not have to point at its own resource. A terraform_data has no machine behind it, so its connection must name one; and Terraform in Depth hangs a provisioner on an aws_route53_record and connects to aws_instance.other.public_ip, which is worth knowing before assuming host must be self.

There are 29 arguments and they are all on the resource page¶

Counted from the resource block reference's table: type, user, password, host, port, timeout, script_path, private_key, certificate, agent, agent_identity, host_key, target_platform; WinRM's https, insecure, use_ntlm, cacert; seven bastion_*; and five proxy_*. The old /language/resources/provisioners/connection URL redirects to the provisioners page, which documents none of them.

The bastion set is one argument, not seven¶

The provisioners page says:

"bastion_host: Set to true to enable the bastion host connection."

The resource block reference types the same argument as a string and describes it as the bastion's address. They contradict each other inside one documentation set, and the source settles it. In internal/communicator/ssh/provisioner.go at tag v1.15.8, decodeConnInfo does connInfo.BastionHost = v.AsString() and takes the bastion path when the value is non-empty. Following the usage page literally is not a type error, because HCL coerces the bool — it produces a connection attempt to a host named true.

The same function carries the fact that turns seven arguments into one. Five of the seven bastion attributes fall back to their non-bastion counterparts:

// Default all bastion config attrs to their non-bastion counterparts
if connInfo.BastionHost != "" {
    // ...
    if connInfo.BastionUser == "" {
        connInfo.BastionUser = connInfo.User
    }
    // BastionPassword, BastionPrivateKey, BastionCertificate and
    // BastionPort follow the same shape; BastionHostKey does not appear.
}

So for a jump host that takes the same credentials as the target — the common case — bastion_host alone is the whole configuration:

connection {
  type         = "ssh"
  user         = "ubuntu"
  private_key  = file("~/.ssh/id_rsa")
  host         = self.private_ip      # reachable only from inside the network
  bastion_host = var.bastion_address  # and that is the entire bastion setup
}

bastion_host_key is the one with no fallback: it is absent from that block, so an unset bastion_host_key stays empty rather than inheriting host_key. The resource reference does document all five defaults in its Default column; only the provisioners page's flat list of seven implies otherwise.

SSH host key validation is off by default

HashiCorp's own words: "Because the SSH connection type is most often used with newly-created remote resources, SSH host key validation is disabled by default." The reasoning is sound — the machine was created seconds ago and there is no known host key to check — but the consequence is that a remote-exec against a fresh instance trusts whatever answers on that address, while handing it the credential in the same block. Setting host_key against a specific key or a signing CA is the opt-in, and it needs a key distribution mechanism you have to build separately.

This is the concrete form of the "potential security issues" in the Overview quoted in section 1.

agent's documented default is wrong, and the real one depends on your machine

The resource reference's table gives agent as type string, default false. It is a boolean, and at tag v1.15.8 provisioner.go sets it true when the argument is unset and SSH_AUTH_SOCK is present:

// To default Agent to true, we need to check the raw string, since the
// decoded boolean can't represent "absence of config".
//
// And if SSH_AUTH_SOCK is not set, there's no agent to connect to, so we
// shouldn't try.
agent := v.GetAttr("agent")
if agent.IsNull() && os.Getenv("SSH_AUTH_SOCK") != "" {
    connInfo.Agent = true
}

A laptop with an agent running and a CI runner without one therefore behave differently on identical configuration, and neither page says so. Set agent explicitly in anything that runs in both places.

Where the uploaded script lands¶

remote-exec over SSH uploads the script and runs it with the default shell rather than piping commands in, and HashiCorp gives the reason:

"Provisioners use this strategy because it allows you to use all of the typical scripting techniques supported by that shell, including preserving environment variable values and other context between script statements."

The defaults are /tmp/terraform_%RAND%.sh and C:/windows/temp/terraform_%RAND%.cmd, chosen by target_platform, and script_path overrides them. The reason script_path exists at all rather than something adaptive is the same reason provisioners are awkward generally: "Provisioners cannot react directly to remote environment variables, such as TMPDIR, or use functions such as mktemp because they run on the system where Terraform is running, not on the remote system."

On Windows, write it with forward slashes, because the Terraform language uses backslash as the string escape character.

Two things the reference gets wrong about script_path

Both checked against the source at tag v1.15.8.

%RAND% is a full 31-bit integer, expanded in internal/communicator/ssh/communicator.go as strconv.FormatInt(int64(randShared.Int31()), 10). So the digit count varies between runs. Nothing in the docs says how wide it is, and "randomly-chosen decimal digits" invites the assumption that it is fixed.

The Windows default above is the SSH communicator's, not WinRM's. The resource reference's script_path row lists both ssh and winrm in its applies-to column and gives the target_platform-dependent value for each. But internal/communicator/winrm/provisioner.go sets DefaultScriptPath = "C:/Temp/terraform_%RAND%.cmd" and contains no target_platform handling at all — which the table's own next row concedes by listing target_platform as ssh-only. A WinRM connection's script lands in C:/Temp.

OpenTofu — the winrm connection type is being removed

OpenTofu 1.12 deprecated winrm for the remote-exec and file provisioners (opentofu#3899), on the grounds that the Go WinRM libraries are unmaintained. It still works and warns on every use. Measured on OpenTofu 1.12.5, against a config Terraform 1.15.8 validates in silence:

│ Warning: WinRM connection type is deprecated
│
│ The winrm connection type is deprecated and will be removed in a future
│ version of OpenTofu.
│
│ Modern Windows systems support SSH natively. Migrate your provisioners to
│ use SSH instead.

The removal has landed in a prerelease. v1.13.0-beta1 was published 2026-08-27 and its changelog states it: "The winrm connection type for provisioners is no longer supported" (opentofu#4012). Stable 1.13.0 is not out yet. Terraform has made no equivalent move, so if you provision Windows today this is a divergence that bites on an OpenTofu upgrade and not on a Terraform one. The migration is SSH: modern Windows Server ships OpenSSH.

5. Failure semantics: the objection that changes behaviour¶

Every argument in section 1 is about design. This one is about what happens on a Tuesday when a package mirror is slow.

on_failure takes one of two bare keywords. fail is the default and stops the apply. continue ignores the error. What the default also does is the part worth internalising, and HashiCorp explains the reasoning:

"Terraform taints resources when a creation-time provisioner fails because a failed provisioner can leave a resource in a semi-configured state. Because Terraform cannot model the provisioner behavior, the only way to ensure proper creation of a resource is to recreate it."

The logic is sound and the consequence is brutal. A flaky script does not merely fail the apply; it condemns a healthy server to destroy-and-recreate on the next plan, and nothing about the configuration changed to cause that.

  input = "keep-me"

  provisioner "local-exec" {
    command = var.fail ? "exit 1" : "echo ok"

}

6. when = destroy has four holes¶

A destroy-time provisioner runs before the resource is destroyed, and it is how people implement deregistration, backup-on-teardown, and licence release:

resource "aws_instance" "web" {
  # ...

  provisioner "local-exec" {
    when    = destroy
    command = "bash ${path.module}/deregister.sh '${self.id}'"
  }
}

Two properties are documented and unsurprising: on failure Terraform errors and reruns the provisioner on the next apply, so it must be safe to run more than once; and create_before_destroy interacts with it. Four properties are surprising, and together they mean a destroy-time provisioner is not a guarantee. HashiCorp's own advice, in its own words, is to use them "sparingly and with care".

Hole 1 — deleting the resource block deletes the provisioner¶

The instruction lives in the configuration. Remove the resource block and you remove the teardown step in the same commit, so Terraform destroys the resource and runs nothing.

labs/chapter18/section6/hole1-delete/ starts from main.tf.before:

resource "terraform_data" "registered" {
  input = "service-b"

  provisioner "local-exec" {
    when    = destroy
    command = "echo DEREGISTER ${self.output}"
  }
}

cp main.tf main.tf.after && cp main.tf.before main.tf
terraform init && terraform apply -auto-approve
cp main.tf.after main.tf && rm main.tf.after    # main.tf is now an empty configuration
terraform apply -auto-approve

The removed block is the modern route out of hole 1

Terraform 1.7 introduced removed blocks (Chapter 16, §5) for forgetting a resource without destroying it. With destroy = true and a when = destroy provisioner inside, the same block becomes the supported way to delete a resource block and run its teardown, in one apply.

  provisioner "local-exec" {
    when    = destroy
    command = "echo DEREGISTER ${self.output}"

The restriction covers the connection block too. So a destroy-time remote-exec cannot take its user, its private key, or its bastion address from a variable: those values have to come off self or be written literally into the module.

That is a strong argument for keeping destroy-time work to local-exec, and a stronger one for not depending on it at all. It is also a second-order form of section 1's portability objection — the one mechanism you cannot parameterise is the one that needs credentials.

Terraform 1.16 moved the line under all four holes

Released 2026-08-26, and it changes the standing argument rather than adding to it.

Through 1.15, the action_trigger block (section 8) accepted only create and update events, so a destroy-time provisioner was the only way to hook teardown, holes and all. Measured on 1.15.8:

Where a provider ships the action you need, none of the four holes applies. An action_trigger is not deleted along with the resource block, is not suppressed by create_before_destroy, does not care whether the object is tainted, and has no restriction on what its configuration may reference. The catch governs the whole ladder: the provider has to have implemented it.

7. terraform_data: the host, not a fifth hatch¶

A provisioner must live inside a resource. When nothing real is a sensible owner — a cluster bootstrap that belongs to three instances at once, a registration step that belongs to the deployment rather than to any one object — terraform_data is where it goes.

It is not a hatch of its own. It is a resource that implements the standard lifecycle and takes no other action, from the built-in provider terraform.io/builtin/terraform, so it needs no required_providers entry and downloads nothing. That is also why every lab in this chapter except four runs offline.

Two arguments store a value, and the difference between them is the whole point of the resource:

  • Change input → the resource is updated in place. Its output attribute changes.
  • Change triggers_replace → the resource is replaced, which is what re-runs any provisioner it hosts.

labs/chapter18/section7/input-vs-trigger/ puts them side by side:

resource "terraform_data" "by_input" {
  input = var.rev

  provisioner "local-exec" {
    command = "echo by_input ran"
  }
}

resource "terraform_data" "by_trigger" {
  triggers_replace = var.rev

  provisioner "local-exec" {
    command = "echo by_trigger ran"
  }
}

terraform init
terraform apply -auto-approve                # both created, both provisioners run
terraform apply -auto-approve -var rev=2     # the interesting one

        id     = "9fae4f6c-6613-8bbd-435d-cc0e5144f95c"

The canonical shape: keyed on what should re-trigger it¶

HashiCorp's own example is the cluster bootstrap, and it is worth reading for its dependency mechanics rather than its shell:

resource "aws_instance" "cluster" {
  count = 3
  # ...
}

resource "terraform_data" "cluster" {
  triggers_replace = aws_instance.cluster[*].id

  connection {
    host = aws_instance.cluster[0].public_ip
  }

  provisioner "remote-exec" {
    inline = [
      "bootstrap-cluster.sh ${join(" ", aws_instance.cluster[*].private_ip)}",
    ]
  }
}

Referencing the instance IDs inside triggers_replace does two jobs at once. It creates the implicit dependency edge, so no depends_on is needed and the bootstrap runs after all three instances exist. And it makes replacement of any instance replace the terraform_data, which re-runs the script — several triggers collapsing into one run rather than one per resource.

That is what triggers_replace buys over hanging the provisioner off a real resource: the run is keyed on whatever actually should re-trigger it, rather than on the lifecycle of whichever object you happened to attach it to.

One loose sentence in HashiCorp's version of this example

The page describes aws_instance.cluster[0] as "the first instance provisioned". [0] is first by index. The three instances have no dependency on one another, so Terraform creates them in parallel and index order is not creation order. Nothing in the example depends on which one it is, which is what the sentence was reaching for.

terraform_data also launders a plain value into a resource address¶

A second, unrelated job, and the reason this resource exists at all for people who never write a provisioner. Chapter 11's replace_triggered_by accepts only resource addresses — HashiCorp: "Plain data values, such as local values and input variables, aren't valid" — because replacement is decided from the planned operations of the things you reference, and a variable has no planned operations.

Since a terraform_data plans an action whenever its input changes, wrapping a variable in one turns it into something replace_triggered_by can legally point at:

resource "terraform_data" "replacement" {
  input = var.revision
}

resource "example_database" "test" {
  lifecycle {
    replace_triggered_by = [terraform_data.replacement]
  }
}

Bump var.revision and the database is replaced. Note that this use wants input, not triggers_replace: an in-place update is a planned action and that is all replace_triggered_by needs.

Migrating off null_resource¶

null_resource, from the third-party null provider, did both of these jobs before Terraform 1.4, using a triggers map. Every older example uses it. terraform_data supersedes it with no provider dependency and a triggers_replace that takes any value rather than a map of strings.

Terraform 1.16 gave terraform_data a third job: the store block

Unrelated to provisioners, and it belongs as much to Chapter 23 as to here. The store block "can hold ephemeral and sensitive values across plan and apply" (terraform#38298) — that is, it exists to deliberately write an ephemeral value into state, for the case where regenerating a secret would rotate the live credential.

ephemeral "random_password" "test" {
  length = 16
}

resource "terraform_data" "test" {
  store {
    input     = ephemeral.random_password.test.result
    sensitive = true
    version   = 1
  }
}

Four arguments. input is write-only, which is what lets it accept an ephemeral value. sensitive routes the result to store.sensitive_output instead of store.output. replace makes an output change replace the resource rather than update it. And version is the one that makes the pattern work: without it a freshly generated value differs every run and the stored output churns; with it, the value is pinned until you bump the number. Rotate on demand rather than on every plan.

Source-verified at tag v1.16.0 in internal/builtin/providers/terraform/resource_data.go: store is declared configschema.NestingSingle, so there is at most one per resource, input carries WriteOnly: true in the schema, and with no version set, "input will be compared directly against output". As of 1.16 the resource has two independent replacement triggers, triggers_replace and store.replace, and the store path is the only one with a deliberate gate in front of it.

8. Actions: the provider-native replacement¶

Terraform 1.14 added the top-level action block: a provider-declared operation that sits outside the create/read/update/delete lifecycle. HashiCorp's Invoke an action page puts the design in three sentences:

"Actions are preset operations built into providers that let Terraform perform day-two operations. Invoke actions to trigger automations outside of Terraform, such as Ansible playbooks and Lambda jobs. Actions do not affect resource state."

That last clause is the whole difference. A provisioner's failure taints a resource precisely because Terraform cannot model what the provisioner did. An action is declared by the provider, so Terraform knows what it is and does not have to assume the worst.

Declaring one looks like a resource, except that the provider's own arguments go inside a nested config block so they cannot collide with Terraform's meta-arguments:

action "aws_lambda_invoke" "example" {
  config {
    function_name = "my_function"
    payload = jsonencode({
      key1 = "value1"
      key2 = "value2"
    })
  }
}

Firing it is a action_trigger block inside a resource's lifecycle:

resource "aws_lambda_function" "example" {
  # ...

  lifecycle {
    action_trigger {
      events     = [after_create, after_update]
      actions    = [action.aws_lambda_invoke.example]
      on_failure = halt
    }
  }
}

events and actions are required. condition gates whether the trigger fires at all, and on_failure decides what happens when it does not work.

The action block takes exactly three meta-arguments — count, for_each and provider — and notably not depends_on and not lifecycle. Ordering is not something you declare on an action: one fired from an action_trigger inherits its position from the resource that triggered it, and ordering beyond that comes from references inside config, which are implicit edges like any other.

There is also a CLI form, and it is a mode rather than a modifier:

terraform apply -invoke=action.aws_lambda_invoke.example

"When you invoke an action using the CLI, Terraform runs only the action and excludes all other configurations."

The on_failure inversion is the sharpest contrast in this chapter¶

Terraform 1.16 gave action_trigger its own on_failure, and the vocabulary deliberately does not overlap with the provisioner argument of the same name:

provisioner action_trigger
Values continue, fail halt, continue, taint
Default fail halt
Does the default taint the resource? yes no
Opt into tainting not possible; it is the default taint

Source-verified at tag v1.16.0, in internal/configs/action.go. ActionOnFailureHalt is the iota zero value, so an unset on_failure is halt, and the enum's own comments say what each one does:

const (
    // Halt stops all further processing of actions and dependencies
    ActionOnFailureHalt ActionOnFailure = iota

    // Taint stops all further process of actions and dependencies. If the
    // resource was just created, the state will be marked as tainted for
    // replacement.
    ActionOnFailureTaint

    // Continue saves all action diagnostics as warnings, allowing processing to
    // continue.
    ActionOnFailureContinue
)

Note the conditional in the middle one: taint marks the resource only if it was just created, which is narrower than the provisioner default it replaces.

Read that table next to section 5 and the design intent is unmistakable. A failed provisioner condemns a healthy server by default. A failed action stops the run and leaves the resource alone by default, because the provider declared the operation and Terraform therefore knows the resource was not left half-configured. Tainting stays reachable for the cases where it genuinely is the right response; it is no longer the assumption.

What 1.16 added, and what 1.15 refuses¶

labs/chapter18/section8/action-trigger/ is a validate-only directory. It names an action that does not exist, which is the point: the event is checked before the action is resolved, so the error tells you which of the two you got wrong.

terraform init
terraform validate

With events = [after_create] on 1.15.8, validation reaches the action lookup:

│ Error: action_trigger actions references non-existent action

Change it to [before_destroy] and it does not get that far:

│ Error: Invalid "event" value before_destroy
│
│ The "event" argument supports the following values: before_create,
│ after_create, before_update, after_update.

Four events on 1.15, six on 1.16. The other two things 1.16 added are worth knowing before you write anything against this feature:

  • caller is self for actions. A config block can read caller.<attribute> to reach the resource instance whose action_trigger fired it, which lets one action block serve many instances of a counted or for_eached resource without a reference per instance (terraform#38668).
  • -invoke now combines with -target to say which caller, which is the natural companion to caller and which the documentation page does not yet mention (terraform#38845).

One feature, three pages, and a typo you will copy

Nothing tells you this, so it is worth writing down: what actions are and how to fire them is on the Invoke an action page; the action block's own arguments are on the action block reference; and action_trigger itself is documented on the resource block reference, because the trigger lives inside lifecycle. Neither of the first two mentions condition at all.

And on the page that does document it, the specification snippet spells it conditions, which Terraform rejects as an unsupported argument, while the same page's summary list spells it condition. Measured on 1.15.6 and unchanged in the v1.16 copy of the page. It is condition.

9. data "external" — the hatch for fetching, not doing¶

Terraform in Depth draws the cleanest line in this whole area in five words: provisioners run commands; they cannot fetch data. When a value you need lives in a system with no provider and no data source, the external data source shells out to a program and reads its answer back as an attribute.

The provider's own documentation calls it an escape hatch, twice, before documenting anything:

"This mechanism is provided as an 'escape hatch' for exceptional situations where a first-class Terraform provider is not more appropriate. Its capabilities are limited in comparison to a true data source, and implementing a data source via an external program is likely to hurt the portability of your Terraform configuration by creating dependencies on external programs and libraries that may not be available (or may need to be used differently) on different operating systems."

The protocol¶

Four rules, and the last two are where implementations break:

  1. program is a list, command first, arguments after. Terraform does not run it through a shell, so there is nothing to escape and no quoting to get right. That is why the canonical form is ["bash", "${path.module}/script.sh"] rather than one command string.
  2. query is a map(string), serialised to JSON and sent on stdin. Omit it and the program receives an empty JSON object {} — not an array, which matters if your parser type-checks its input.
  3. Success is a JSON object of strings on stdout and exit zero. The object surfaces as result.
  4. Failure is a human-readable message on stderr and a non-zero exit. Anything on stdout is ignored in that case, and the stderr text is what your users see in the Terraform error.

labs/chapter18/section9/external/:

data "external" "probe" {
  program = ["sh", "${path.module}/probe.sh"]

  query = {
    name = "world"
  }
}

output "result" {
  value = data.external.probe.result
}

#!/bin/sh
echo "ran" >> runs.log

name=$(sed -e 's/.*"name":"//' -e 's/".*//')

printf '{"greeting":"hello %s","saw_secret":"%s"}\n' "$name" "${DEPLOY_SECRET:-<unset>}"

terraform init
DEPLOY_SECRET=hunter2 terraform apply -auto-approve

Outputs:

result = tomap({
  "greeting" = "hello world"
  "saw_secret" = "hunter2"
})

Two findings sit in that output and in the file the script wrote.

The program inherits every environment variable Terraform can see

The configuration above passes the program exactly one thing: name = "world". It read DEPLOY_SECRET anyway, and the provider documentation says why: "All environment variables visible to the Terraform process are passed through to the child program."

Nothing scopes that. The script inherits AWS_SECRET_ACCESS_KEY, every TF_VAR_* holding a secret, and whatever else your runner exports. So an external data source is a credential-exposure surface as wide as the Terraform process itself, and choosing whose script to run is a decision about who gets to see your environment. Neither book raises it.

It runs on every plan and every refresh, not once per apply

The provider states the contract: "Terraform expects a data source to have no observable side-effects, and will re-run the program each time the state is refreshed."

Measured by having the program append a line to runs.log. Starting from a completed apply:

Command Lines in runs.log
terraform apply -auto-approve 1
terraform plan 2
terraform plan 3
terraform refresh 4

One invocation per operation, plans included. A script that costs money, consumes a rate limit, or writes anything is being used against the contract — and the contract is stated in the provider docs and in neither book.

terraform destroy -auto-approve
rm -f runs.log        # written by the program; nothing tracks it and destroy will not remove it

Terraform Enterprise guarantees no language runtimes

From the same page: "Terraform Enterprise does not guarantee availability of any particular language runtimes or external programs beyond standard shell utilities, so it is not recommended to use this data source within configurations that are applied within Terraform Enterprise."

That rules the whole technique out on TFE regardless of how well the script is written, and it has no equivalent in either book. Terraform: Up & Running arrives at the neighbouring point independently: its example "relies on Bash, which means you won't be able to deploy that Terraform module from Windows."

Work down the alternatives first¶

  • The http provider, if the script is really an API call. It builds HTTP requests directly in the language.
  • Provider-defined functions (Terraform 1.8, OpenTofu 1.7) — the thing you were about to compute may already exist as provider::x::fn().
  • A data source you missed, in a provider you already have.
  • Writing a provider (→ Chapter 26), which is the right answer if the team knows Go and the integration is going to last. The external provider is the worse version of the same thing.

If it stays a script, the provider recommends jq for any shell implementation, and ships the boilerplate. Two idioms carry it: @sh formats jq's output for safe eval, and jq -n --arg builds the response without string-concatenating JSON, which is where hand-written versions break on a value containing a quote.

#!/bin/bash
set -e

eval "$(jq -r '@sh "FOO=\(.foo) BAZ=\(.baz)"')"

FOOBAZ="$FOO $BAZ"

jq -n --arg foobaz "$FOOBAZ" '{"foobaz":$foobaz}'

10. The local provider — the hatch for writing a file here¶

Provisioners write files on remote machines. The local provider handles the machine Terraform is running on, and it comes in three parts.

As data sources, local_file and local_sensitive_file read a file. They beat a bare file() call in two ways: a data source can carry depends_on and conditions, and it exposes derived checksums — content_md5, content_sha1, content_sha256, content_sha512, plus content_base64sha256 and content_base64sha512. A checksum alongside the content is the usual trigger for redeploying something, and computing it here is shorter than doing it yourself.

Read the content_base64* names in the right order

content_base64sha256 is, in the provider's words, "Base64 encoded SHA256 checksum of file content" — hash the raw content, then base64 the digest. That is what base64sha256() produces and what AWS arguments such as source_code_hash expect. Hashing the base64 text would give a different value and break them, and it is an easy misreading of the name.

Binary content is silently corrupted, not rejected

"Files that do not contain UTF-8 text will have invalid UTF-8 sequences in content replaced with the Unicode replacement character." No error, no warning — a mangled string you discover somewhere downstream. Use content_base64 for anything that is not text.

As a function, the provider ships direxists, which exists because fileexists() was always built in and had no directory counterpart:

locals {
  file_exists = fileexists("${path.module}/example.txt")
  dir_exists  = provider::local::direxists("${path.module}/scripts/")
}

Two behaviours to know: it errors rather than returning false if the path is a file, and unlike fileexists it does not expand ~, so pair it with pathexpand(). And a provider function needs a required_providers entry even in a configuration that uses no local resources or data sources, plus Terraform 1.8 or OpenTofu 1.7.

As resources, the same two names write files — and this is where the escape-hatch costs land. This is also the other half of Chapter 7: templatefile() renders a template into a string and nothing in that chapter ever puts one on disk. local_file is the piece that does, and it carries every cost below for the privilege.

labs/chapter18/section10/local-file/:

resource "local_file" "note" {
  content  = "written by terraform\n"
  filename = "${path.module}/generated/note.txt"
}

terraform init
terraform apply -auto-approve

The plan shows the problem before the apply does:

  # local_file.note will be created
  + resource "local_file" "note" {
      + content              = <<-EOT
            written by terraform
        EOT
      + content_base64sha256 = (known after apply)
      + ...
      + directory_permission = "0777"
      + file_permission      = "0777"
      + filename             = "./generated/note.txt"
      + id                   = (known after apply)
    }

file_permission and directory_permission both default to 0777

Before umask, so the effective mode depends on the runner — but the declared default on a resource whose entire purpose is writing files to disk is world-writable. A configuration that renders a config file, or worse a key, and never sets file_permission is relying on whatever umask the machine happens to have.

Set it explicitly. file_permission = "0600" for anything private. Neither Terraform in Depth nor HashiCorp's own examples mention it, and the section of TID where this belongs is the one whose example writes a tls_private_key to disk.

Now delete the file, which is what happens the moment a different runner picks up the next apply:

rm generated/note.txt
terraform plan

  # local_file.note will be created
  + resource "local_file" "note" {
      ...
Plan: 1 to add, 0 to change, 0 to destroy.

Not ~, not -/+: +. The refresh found no file, dropped the object from state, and planned a creation. On a CI runner that is a fresh container every time, that plan is the plan on every run, forever. A local_file resource and a remote state file simply disagree about what reality is.

Where it genuinely works is local development: generating a client config for the environment you just built, on your own machine. Terraform in Depth's example is a dev-VPN module that stands up an AWS VPN and drops the OpenVPN client config into the module directory — useless in production, genuinely handy while debugging.

terraform destroy -auto-approve      # removes the file; `generated/` stays
rm -rf generated

Writing a key to disk writes it to state as well

resource "tls_private_key" "main" {
  algorithm = "ECDSA"
}

resource "local_sensitive_file" "key" {
  content         = tls_private_key.main.private_key_pem
  filename        = "${path.module}/private_key.pem"
  file_permission = "0600"
}

Both resources put that key in state. local_sensitive_file marks the content sensitive, which hides it from CLI output; it does not encrypt anything. Whoever can read the state file can read the key. That is Chapter 23's subject, and OpenTofu's state encryption is Chapter 28's.

11. The handoff, and where the seam sits¶

HashiCorp's case against provisioners ends at "use a purpose-built solution". Its Post-apply operations page lists "Use configuration management tools" as method 4 of 4 and then never mentions it again — no seam, no inventory, no example. That gap is worth closing, because the handoff is the answer for most of what people actually reach for a remote-exec to do.

The seam is terraform output -json. Terraform builds the hosts and publishes their addresses as a root output. The configuration tool reads that output as its inventory and takes over. Nothing runs inside the apply.

pyinfra is the smallest clear illustration — agentless configuration management in Python, with a @terraform inventory connector that reads exactly that:

# Terraform publishes; the config tool consumes. Two runs, one seam.
pyinfra @terraform/server_group.value.server_group_node_ips apt.packages iftop _sudo=true

Ansible is the incumbent in the same position, through the Red Hat-certified cloud.terraform collection. The tool is not the point; the boundary is.

What the handoff buys is precisely the objections from section 1, answered:

  • A failed configuration step is not a tainted resource. It is a failed configuration run, which you re-run.
  • Re-converging does not need Terraform at all — that is what the configuration tool's idempotence is for.
  • The plan stops pretending to describe work it cannot diff.

The cost is real and worth naming: two tools, two runs, and an ordering dependency that a human or a pipeline has to enforce.

Outputs versus state is a blast-radius choice, not a style choice

The two ways of getting a host list out of Terraform are not equivalent in what they expose.

pyinfra's @terraform connector reads terraform output -json — only what the root module deliberately published. Ansible's terraform_provider inventory plugin builds its inventory from the state file — every attribute of every resource, plaintext secrets included. Same job, very different grant: the outputs-only consumer can be given terraform output without being handed the state snapshot.

This is Chapter 15's access-boundary rule showing up somewhere new. "Who may read this state" is the real permission boundary, not "which outputs do I expose". And before publishing an output for a tool to consume, remember that -json bypasses sensitive redaction — the consumer reads it in plaintext by design.

Not a reason to prefer one tool over the other, either. Ansible reads outputs too, through terraform_output and the tf_output lookup; it is the inventory plugin specifically that wants state.

There is a third direction, and it is vendor-supported

Both mechanisms above are pull: something downstream reads what Terraform published. HashiCorp's validated pattern Integrate Terraform with Ansible Automation Platform runs the seam the other way. An AAP provider gives Terraform aap_inventory, aap_job_template and aap_job resources, so an apply writes the Ansible inventory and launches the job as part of the same graph.

That puts the work back inside the apply — wait_for_completion = true blocks it exactly as a remote-exec would — but a provider models the operation, so a failure is a failed resource rather than a taint on a healthy machine. The aap_job resource even runs once by default with a triggers map deciding when it runs again, which is terraform_data's shape exactly.

Two caveats. The pattern is explicit that it addresses the enterprise editions of both products: "relying on Terraform Community Edition or Ansible OSS is not recommended." And it rules out the HCP Terraform run-task route for a reason worth carrying beyond Ansible: run tasks have a hard 10-minute limit on responses from the external system (→ Chapter 22).

Its tool-division table is the part to keep regardless of direction. Terraform is declarative, stateful, built on immutable infrastructure, and optimised for "a small number of high-level control points"; Ansible is procedural, stateless, mutable, and built to operate "across large inventories". The hybrid it recommends — Packer for the image, Terraform to provision from it, AAP for post-provision configuration — is this chapter's ladder one layer up. The question is never whether to shell out. It is where the handover boundary sits and who owns each side of it.

12. Where provisioners still earn their place¶

Both books land in the same place, and it is narrower than the volume of documentation suggests.

  • Platforms with no cloud-init support. Windows is the common case, and it is why the WinRM connection type exists at all — which makes OpenTofu's removal of it (section 4) a real constraint rather than a tidy-up.
  • Genuine edge cases: an operation with no provider, no data source, no image-time equivalent, and no action.
  • Local-only work. A local-exec that writes a report, kicks a local build, or runs a smoke test against something you just created carries none of the remote-access objections, because there is no remote access.

And one place they never earn it: anything behind an autoscaling group. A provisioner runs only while Terraform runs. The instance the autoscaler launches at 3am gets nothing.

Terraform in Depth's rule is the one to keep: read the alternatives before writing the provisioner, not after. This chapter's section 2 is that list.

Terraform: Up & Running closes the same argument in a sentence worth keeping:

"be conservative with your use of external data sources and all of the other Terraform 'escape hatches,' since they make your code less portable and more brittle."

Common pitfalls¶

  • Putting the trigger in input. input updates in place, so the provisioner never re-runs. triggers_replace is the one that replaces the resource, and replacement is what re-runs a provisioner.
  • Treating a destroy-time provisioner as a guarantee. It is skipped when the block is deleted, when the object is deposed by a create_before_destroy replacement, and when the resource is tainted — all three silently.
  • Writing a destroy-time remote-exec that reads its credentials from variables. It fails at validation, and there is no way around it except hard-coding them or taking them off self.
  • Interpolating a secret into command. It lands in the Executing: line and in your CI log. Use environment.
  • Reaching for on_failure = continue to make a flaky step tolerable. It does, and it reports nothing at all. Make the script surface its own failure.
  • Copying on_failure = "abort" from Terraform: Up & Running. It is not a valid keyword. The pair is continue and fail.
  • Following bastion_host = true from the provisioners page. HCL coerces the bool and you connect to a host named true. It is the bastion's address, and it is usually the only bastion argument you need.
  • Renaming triggers to triggers_replace and flattening the value in the same edit. The moved block works; the plan is a replacement. Carry the map across, confirm the empty plan, simplify separately.
  • Using local_file in CI. Ephemeral runners do not have the file, so the plan proposes to create it on every run, forever.
  • Doing anything expensive in an external program. It runs on every plan and every refresh, not once per apply.
  • Assuming a provisioner will configure autoscaled instances. It runs only while Terraform runs. Use creation-time data.
  • Assuming Terraform's answers apply to OpenTofu here. No actions, no action_trigger, and winrm on its way out.

Summary¶

Terraform's language describes things that exist. An escape hatch is a way to let a verb in anyway, and Terraform ships four: the provisioner block, terraform_data as its host, the external data source for fetching what no provider models, and the local provider for writing a file next to the configuration.

The case against provisioners is four separate arguments. HashiCorp's is modelling and blast radius — the plan describes work it cannot diff, and the technique needs a route to your servers plus a credential for them. Terraform in Depth's is portability: a connection bakes a network topology into a module. Terraform: Up & Running's is visibility and autoscaling: User Data is logged, visible in the console, and runs on instances the autoscaler launches when Terraform is nowhere. The fourth is failure semantics, and it is the one that changes behaviour: a failed creation-time provisioner taints the resource, so the next plan destroys a healthy server. Measured, that plan reads is tainted, so must be replaced against a configuration that did not change.

when = destroy is not a guarantee, four times over. Deleting the resource block deletes the provisioner; create_before_destroy suppresses it on replacement but not on destroy, because the deposed object is torn down by a path that never calls provisioners; a tainted resource skips its own cleanup, which means a failed creation-time provisioner disables the destroy-time one; and a destroy-time provisioner may reference only self, count.index, each.key, path.* and terraform.* — which bites hardest on connection. The removed block with destroy = true is the supported way out of the first hole, in one apply instead of two.

terraform_data is a host, not a fifth hatch. input updates in place; triggers_replace replaces, and only replacement re-runs a provisioner. Referencing another resource's id inside triggers_replace creates the dependency edge and the re-run trigger in one expression. Migration from null_resource is a moved block, and it produces an empty plan only if the trigger keeps its map shape.

Provider actions are the modern answer to most of this. The provider declares the operation, so Terraform understands it, and the on_failure default is inverted: halt, which does not taint, against the provisioner's fail, which does. Terraform 1.16 added destroy events, caller, and on_failure itself, which closes all four holes wherever a provider ships the action. OpenTofu has none of it, so on that engine the argument stands as it did.

The alternative to a provisioner is usually a handoff, and the seam is terraform output -json. Publishing outputs and sharing state are not the same grant, and the difference is the whole state file in plaintext.

The connection is closer than it looks. Half of what people reach for a provisioner to verify is a postcondition, and the reason a flaky script is so expensive here is that Terraform has no way to assert the outcome separately from the action. Chapter 19 gives it one.
